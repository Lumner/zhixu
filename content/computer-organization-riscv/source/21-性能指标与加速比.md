# 21 性能指标与加速比

## 21.1 先确定“快”指哪一件事

前一章已经能计算一条lw经过几个周期。现在把问题扩大：同样完成一次求和，机器A频率更高，机器B指令更少，到底谁先结束？

本章只用四则运算、比例、第07章的时钟与第13章的循环。学完应能把指令数、周期、秒连接起来，独立数出循环执行次数，正确计算平均CPI、加速比和局部优化上限。不要求安装性能测试软件。

建议五次小课：先学单位和统计范围，再数循环，然后比较机器，最后处理局部优化及实验。每次先写“同一任务、输入、起点、终点”，再代数字；任务不同，两个漂亮的时间也不能直接比较。

## 21.2 响应时间与吞吐量的分母不同

**响应时间**是一个任务从开始到结束经过的时间，也常称该任务的延迟。例如提交一次计算后，0.8秒拿到答案。**吞吐量**是单位时间完成多少任务，例如每秒完成20次计算。

一家店一份餐需10分钟，五个环节流水工作后，每2分钟可交出一份；这不表示某一份餐只做2分钟。CPU的流水线也会出现类似区别，第22章用精确时序表代替比喻。

测量单个请求时看延迟；持续处理许多请求时还要看吞吐。并发增加后平均吞吐变高，单次等待却可能变长。此处只建立指标含义，不由餐厅比喻推出硬件周期数。

## 21.3 墙钟时间、CPU时间和模拟器时间

**墙钟时间**像拿秒表测“点击开始到出现结果”；可能包括等磁盘、网络、被系统暂停等。**CPU时间**关注CPU执行该任务所消耗的时间。先约定单核、单线程的简单范围，不把多个核的CPU时间相加后和墙钟时间混用。

RARS在宿主电脑运行了多少毫秒，是“模拟软件完成工作花多久”。教学模型打印了多少周期，是“我们规定的被模拟流水线经过多少离散时刻”。真实芯片时间还需要对应芯片、频率、缓存等信息。三者不是同一个测量值。

因此本阶段用RARS核对指令结果，用附带模型核对指定时序。Node脚本运行快了，不自动表示RISC-V程序被优化。正文的ps、GHz全部来自题设，不冒充本机处理器的测量参数。

## 21.4 频率是“每秒多少周期”

时钟频率f的单位Hz表示周期/秒。周期时间T表示秒/周期，两者互为倒数。先把单位写全：

| 量 | 含义 | 本章换算 |
| --- | --- | --- |
| 1 MHz | 每秒一百万周期 | 10⁶周期/秒 |
| 1 GHz | 每秒十亿周期 | 10⁹周期/秒 |
| 1 ms | 一毫秒 | 10⁻³秒 |
| 1 ns | 一纳秒 | 10⁻⁹秒 |
| 1 ps | 一皮秒 | 10⁻¹²秒 |

2 GHz的周期为1/(2×10⁹)秒=0.5 ns=500 ps。不要把2 GHz直接当作“2秒”，也不要把2这个裸数代入以秒为单位的除法。

反过来，周期250 ps=250×10⁻¹²秒；频率1/T=4×10⁹ Hz=4 GHz。这只是互换同一时钟的两种表示，不说明每周期能完成几条指令。

## 21.5 动态指令数不是文件有几行

**静态指令数**看程序中放了多少条机器指令；**动态指令数IC**看本次运行实际执行了多少次。同一条add循环执行5次，动态计5次；没有走到的分支路径计0次。

标签、注释和`.text`等指令伪操作不作为CPU指令执行。`li`、`la`等伪指令先展开，再数真正机器指令；一行源代码不固定等于一条。不同输入会改变循环次数，IC必须连同输入记录。

先做一个比完整统计器更小的例子：求0至N−1的和，N取非负整数。下面是[count-loop.s](示例代码/06-pipeline/count-loop.s)的**计数区域片段**，完整文件还包含打印与退出；不要把片段单独当成完整可运行程序。

```asm
main:
    addi t0, zero, 0       # i=0
    addi t1, zero, 5       # 本次N=5
    addi a0, zero, 0       # sum=0
loop:
    beq t0, t1, done       # 达到N时退出
    add a0, a0, t0
    addi t0, t0, 1
    jal zero, loop         # 无条件回到loop，不保存返回值
done:
    # 计数区域在这里结束，打印尚未执行
```

`jal zero,loop`是基础跳转，链接值丢给x0；本例不用可能展开的`j`，便于直接按机器条数数。N必须非负且限制在本课小输入范围，不把负数当成会正常结束的实验。

## 21.6 一步一步数N=5与N=0

初始三条各执行1次。每轮到loop先判断；i=0、1、2、3、4时不退出，体执行。i最后更新为5，跳回再判断一次，这次才退出。

| 位置 | N=5次数 | 一般N≥0次数 | 原因 |
| --- | --- | --- | --- |
| 三条初始化合计 | 3 | 3 | 进入循环之前只做一次 |
| beq | 6 | N+1 | 每次体之前检查，结束还检查一次 |
| add累计 | 5 | N | 每个合法i一次 |
| addi更新i | 5 | N | 每次体后更新 |
| jal回跳 | 5 | N | 本例包括最后一次回到结束判断 |
| 计数区域合计 | 24 | 4N+4 | 3+(N+1)+3N |

N=5时累计过程0→0→1→3→6→10。N=0时初始化3条后，首次beq立即退出；结果0，计数4。不能把N=0代入“体执行N次，所以程序0条”，也不能少数最后一次beq。

如果换成先做体再检查的循环，N=0行为可能完全不同。动态计数必须对应这一份具体程序，不能把4N+4当成所有循环的通式。

## 21.7 CPI是平均每条消耗多少周期

**CPI**是Cycles Per Instruction，定义为“统计区间内周期总数÷该区间内完成的机器指令次数”。平均数可以带小数；CPI=1.5不是一条指令物理上走了半个时钟，而是多条合计后的平均。

给定IC和CPI，总周期C=IC×CPI。再乘周期时间，或除以频率，得到CPU时间：

```text
C = IC × CPI
CPU时间 = C × T = IC × CPI × T = IC × CPI / f
```

检查单位：指令×周期/指令=周期；周期÷(周期/秒)=秒。若结果单位还剩“指令/秒”，很可能把公式颠倒了。

IC、CPI与f要属于同一个工作与同一种实现。把RARS的功能指令数、另一颗芯片的频率、未说明模型的CPI拼起来，只能构成假设题，不能声称测出了本机耗时。

## 21.8 完整算例：100万条需要多久

设IC=1,000,000条，平均CPI=1.5，频率2 GHz。先算周期：1,000,000×1.5=1,500,000周期。

再换频率：2 GHz=2,000,000,000周期/秒。时间=1,500,000/2,000,000,000秒=0.00075秒=0.75 ms。

反算一次：0.00075秒×2,000,000,000周期/秒=1,500,000周期，除以100万条回到CPI1.5。正算与反算能发现漏掉10⁹等数量级错误。

对照：同样的程序若频率仍2 GHz、CPI变3，总周期300万，时间1.5 ms；若CPI仍1.5、频率降为1 GHz，也需1.5 ms。不能只看频率而忽略每条指令等待多少周期。

## 21.9 加权CPI必须按实际执行次数

假设本次100条里，A类60条各1周期，B类30条各2周期，C类10条各4周期。先算总周期：60×1+30×2+10×4=160；平均160/100=1.6。

也可用比例：0.6×1+0.3×2+0.1×4=1.6。比例必须以同一批动态指令为分母，且合计1。把(1+2+4)/3算成2.333，会偷偷假设三类次数相等。

这里“每类周期”是题设的计费模型。实际流水线的停顿、缓存缺失可能重叠；这时不能不加说明地把每种事件成本独立相加。短程序还受填充与排空影响，第22章会说明为何CPI不必正好1。

## 21.10 加速比的方向与百分数

**加速比S=旧时间/新时间**，比较相同工作。旧1秒，新0.8秒，S=1.25，表示性能成为原来的1.25倍。

时间减少比例是(1−0.8)/1=20%；性能增加比例是1.25−1=25%。20%和25%都可以正确，但描述对象不同，不能把“时间少20%”写成“性能只多20%”。

若S=0.8，表示新方案反而慢，完成时间变为旧的1/0.8=1.25倍。比值没有单位，不要把加速1.25倍写成1.25 ms。

## 21.11 两台机器与一次优化，分别比较

机器A：IC=10亿、CPI=1、2 GHz，时间0.5秒。机器B：同一工作编译后IC=8亿、CPI=1.5、3 GHz，时间0.4秒。B相对A加速0.5/0.4=1.25倍。频率比1.5不是总加速比，因为IC与CPI也变了。

再看同一机器上的代码优化：IC减少20%，CPI从1.6升到2，频率不变。新/旧时间比=0.8×2/1.6=1，所以不加速。减少了一些指令，同时每条更贵，收益正好抵消。

若优化还使频率变动，应再乘旧频率/新频率。最稳的方法是分别计算两份总时间，再作比，而不是只挑一个变好的指标。

## 21.12 Amdahl：先把原时间切成两块

**Amdahl定律**讨论“只加速一部分工作”时的整体收益。设原任务10秒，其中6秒不受影响，4秒可优化。把可优化部分变快4倍后，它从4秒变1秒，其余仍6秒，总共7秒。

于是总加速=10/7≈1.429。不能因为某一块快4倍，就说整个任务快4倍。用原时间比例p=0.4、局部加速s=4，可以把刚才算式写为：

```text
新时间 / 旧时间 = (1−p) + p/s
整体加速比 = 1 / ((1−p) + p/s)
```

p是**原时间中**受影响部分的比例，不是源码行数比例、指令条数比例或优化后的新比例。新程序的可优化部分只占1/7，不能拿1/7重新代入这个以原时间为基准的公式。

## 21.13 极限、反例和优化选择

仍是6秒不变、4秒可优化。如果那4秒理想地降到0，任务仍需6秒，最大加速10/6≈1.667。这是该假设下的上限，不是说真实机器一定能把某部分做到0秒。

另一个任务原来80%时间可优化，局部只快2倍：新时间比例0.2+0.8/2=0.6，总加速约1.667。覆盖更大时间的温和优化，可能比覆盖很小时间的巨大优化更有效。

如果优化还增加新的通信、检查或内存开销，必须把新增部分加入总时间。Amdahl的“其他部分不变”是前提；不满足时重新分账，不能靠套公式抹掉新增成本。

## 21.14 可复现实验：把计数边界写在纸上

先手算count-loop.s的N=0、1、5，记录结果0、0、10与区域指令数4、8、24。把完整文件与RARS JAR放在自己的练习目录，在**Windows PowerShell、该目录**运行：

```powershell
java -jar .\rars1_6.jar nc me sm ic a0 .\count-loop.s
```

默认N=5打印10。需要第09章已准备的Java/RARS；只修改t1初始化中的5来换N，每次保存再运行。该程序使用RARS打印与退出服务，不用于直接测流水周期。

本批实际核对RARS v1.6：N=0、1、5的`ic`显示7、11、27，**不是计数区域的4、8、24**。打印/退出区域还有四条，v1.6在终止ecall处返回，未执行之后的计数更新，因而其显示值等于本例区域数加3。这里解释这个特定工具版本的观测，不改写区域边界，也不把差值当CPU流水气泡。实现依据见[RARS启动器](https://raw.githubusercontent.com/TheThirdOne/rars/v1.6/src/rars/Launch.java)与[模拟循环](https://raw.githubusercontent.com/TheThirdOne/rars/v1.6/src/rars/simulator/Simulator.java)，核验于2026-11-05。

## 21.15 常见错误怎样查

| 现象 | 第一处应核对 |
| --- | --- |
| 结果大或小10⁶、10⁹倍 | MHz/GHz是否换成Hz，毫秒是否换成秒 |
| 循环恰好多一条或少一条 | 结束检查、无条件回跳、计数起止地址 |
| 文件8行却统计27 | 静态/动态、伪指令、输出区域、工具口径 |
| CPI很小就认为机器一定快 | IC与周期时间有没有同时变化 |
| 局部快4倍就报总快4倍 | 哪些原时间仍不变 |
| Node计时变快就报告芯片加速 | 测的是宿主软件还是规定的目标模型 |

每次报告至少写任务/输入、代码版本、IC范围、周期或CPI来源、频率来源、计算过程与单位。没有实测频率，就写题设，不把模型输出装成基准测试。

## 21.16 自测与参考过程

先独立答：①2 GHz周期几ns；②200万条、CPI2、1 GHz需多久；③N=0区域几条；④N=5的beq执行几次；⑤三类次数60/30/10、周期1/2/4的CPI；⑥1秒降0.8秒的加速比和时间减少比例；⑦80%原时间快2倍的整体加速；⑧本机运行RARS的毫秒能否直接当RISC-V周期。

参考：①1/(2×10⁹)秒=0.5 ns；②400万周期/10亿=0.004秒=4 ms；③三条初始化加一次判断=4；④6次；⑤总160周期除100=1.6；⑥1.25倍、20%；⑦剩余0.2加优化后0.4，得1/0.6≈1.667；⑧不能，模拟软件耗时与目标实现时序不同。
