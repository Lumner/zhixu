## 三类错误分别处理

**语法错误**让解释器无法理解代码，如漏冒号。**运行时错误**发生在执行中，如除以零、找不到文件。**逻辑错误**允许程序执行完，但结果不符合题意，如把增长率分母写成新值。

看报错时先从最后一行读异常类型与说明，再向上找到自己文件中的行号。不要先改系统环境，也不要一遇到错误就重装Python。**最小复现**是保留触发问题所需的最少输入与代码，减少无关因素。

## 可复现故障一：文字没有转换

下面是**故意出错的独立片段**，可在交互模式逐行执行：

```python
price = "24"
revenue = price * 72
print(revenue)
```

结果会把字符串24重复72次，甚至不会报错。这是逻辑错误，不是解释器失灵。若改成 `price + 1`才会因字符串和整数相加触发TypeError。修复为 `price = float("24")`，再计算得到1728.0。先检查类型再解释经济结论。

## 可复现故障二：增长率分母

错误公式 `(100-80)/100`得到0.2，却把20%误称为从80到100的增长率。手算已知答案为25%，所以应写 `(100-80)/80`。**已知答案**必须独立于被检查的代码，不能用同一错误公式生成期待值。

## 可复现故障三：索引越界

列表`[20,24,30]`只有索引0、1、2。`prices[3]`会触发IndexError。若只是想取最后一个，写`prices[-1]`；若要处理所有项，用 `for price in prices`，避免自己维护多余索引。

## 用断言保存检查

**断言**用 `assert 条件`表达“这个开发检查必须成立”。失败会触发AssertionError。完整文件[debug_demo.py](示例代码/debug_demo.py)如下：

```python
from functions import demand

assert demand(0) == 120
assert demand(24) == 72
assert demand(60) == 0
assert demand(70) == 0
print("Four demand checks passed.")
```

`from functions import demand`导入同目录functions.py中的函数，不写`.py`后缀。因为原文件有入口保护，导入不会自动执行它的演示。

在示例目录的PowerShell执行 `python debug_demo.py`，预期显示 `Four demand checks passed.`。四个点分别检查截距、普通值、零需求边界和截断范围。它们不是对真实需求规律的证明。

浮点结果常用近似比较，例如导入math后 `math.isclose(0.1+0.2, 0.3, rel_tol=1e-9, abs_tol=1e-9)`。两种容差分别考虑相对误差和接近0的绝对误差。不要对一般浮点计算一律要求`==`。

## 验证与输入校验不同

断言适合开发检查，不用它保护用户输入：Python的优化运行选项可能移除assert。用户输入错误应使用明确条件并raise或提示，前面的CSV程序正是如此。本课后续自动验证用unittest保留明确检查。

良好的验证分层：公式手算、函数已知值、坏输入、完整程序输出、文件读写和经济解释。本阶段只验证本地教学程序，尚未进行数据来源核验、统计识别或宏观模型实验。

## 常见错误

- 只查“没有报错”，不查答案、单位和输入含义。
- 改了一行后不重跑原来通过的边界案例。
- 为迎合错误输出而改期待值，失去独立基准。
- 将文件命名为`csv.py`或`math.py`，遮蔽Python同名标准模块。

## 练习与参考答案

1. 把练习副本的需求函数故意改成 `120+2*price`，哪项检查会失败？答：24、60、70等检查失败，价格0的截距检查仍通过；一个通过点不够。
2. 总收益用整数参数得到1728，能称为利润吗？答：不能，成本尚未扣除。正确代码也可能被错误解释。
3. 输入校验能用assert代替吗？答：不能依赖可能被优化移除的开发检查；使用if与明确异常。
