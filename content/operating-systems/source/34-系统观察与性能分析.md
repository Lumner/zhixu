## 34.1 从问题形成假设

现在能理解系统大部分主线。面对“程序慢”，先写可验证问题：是计算耗时、等锁、等磁盘、等网络，还是启动和输出占了时间？同样的总耗时可以来自完全不同原因，不能先认定“CPU 不够”。

| 工具/接口 | 主要观察 | 不应直接推断 |
| --- | --- | --- |
| `ps`、`top` | 进程、线程与资源快照 | 一次高 CPU 就是故障 |
| `time` | 实际、用户态、内核态耗时 | real 必须等于 user+sys |
| `/proc` | Linux 进程与系统状态接口 | 所有系统都存在相同文件 |
| `strace` | 系统调用与信号交互 | 能直接看出所有 C 逻辑 |
| `free`、`df` | 内存/文件系统使用概况 | 缓存都属于浪费 |

## 34.2 一组可复现观察

在例程目录编译后运行：

```bash
./process
time ./mutex
strace -f -e trace=process,read,write,close ./pipe-demo
ps -p $$ -o pid,ppid,stat,comm
cat /proc/self/status
```

`$$` 在 Bash 中表示当前 Shell 的 PID；`/proc/self` 指访问该路径的进程，所以最后一行通常看到 cat 的信息，并非 Bash 或你的某个 C 例程。strace 的 -f 用来跟踪派生子进程，避免漏看实际工作所在分支。

输出量和执行时间依环境变化。跟踪会增加开销，不能用跟踪时的时间直接代表未跟踪性能。短小例程可能快到计时精度不足，不为追求好看数字而编造固定毫秒数。

## 34.3 分清时间口径

real 是墙上经过时间，user 是进程在用户态消耗的 CPU 时间，sys 是内核态 CPU 时间。等待 I/O 或调度时，real 会推进但本进程未必消耗 CPU。多个线程真正在多核并行时，累加 CPU 时间可能大于 real。工具是否统计子进程也要看具体接口和用法。

## 34.4 实验记录模板

记录问题、系统/编译器版本、输入规模、编译参数、命令、原始输出、重复次数、结论和未验证项。对比实验每次只改变一个主要因素，例如相同输入下比较一次输出与大量逐条输出。不要让两组同时改编译优化、数据量和缓存状态，再把差异归给其中一项。

性能诊断从证据缩小范围：等待多则看资源与阻塞位置；CPU 多则定位热路径；内存多则分辨泄漏、缓存与工作集。修复后用相同负载再测，并检查正确性没有变。

## 34.5 练习、答案与完成条件

①`time` 中 real 明显大于 user+sys，可能原因？②strace 没显示数组循环，是否循环没有执行？③/proc/self/status 是静态文本文件的永久内容吗？

答案：①等待、调度、I/O 等，需要进一步证据；②不是，用户空间计算不必触发系统调用；③它是内核生成的接口视图，随读取者与时机变化。

完成条件：提交一份带真实命令和输出的短报告，结论只覆盖已经观察的现象，并写一个仍待检验的假设。
