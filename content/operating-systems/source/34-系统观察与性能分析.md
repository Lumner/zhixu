# 34 系统观察与性能分析

> **零基础详细版 · 已重写。** 先修：进程、阻塞、内存、文件I/O与第33章的环境边界。建议7—10小时。先问清问题，再选观察工具；本章不要求管理员权限或额外安装性能软件。

## 34.1 学习目标：把“慢”改写成可检验的问题

“程序慢”可以指启动久、一次请求久、很多请求做不完，或界面长时间没响应。这些不是同一个指标。学完本章，你要能写出输入、指标、假设、观察和结论，区别经过时间与CPU时间，提交一份含原始结果的小报告。

先回想一个真实场景：复制文件用了十秒。是文件很大、正在等待存储、输出太多，还是CPU计算繁重？只知道十秒无法区分。本章不从一大串工具名开始，而是把每次观察变成能支持或排除某个解释的证据。

## 34.2 三个词：指标、基线、对照

**指标**是要测量的量，例如完成一次任务的秒数、每秒完成的记录数或最大内存占用。**基线**是改变前用于比较的结果。**对照**是在可比条件下，只改变想研究的因素，再与基线比较。

例如同样输入、同样输出内容下，比较每条记录都刷新与最后统一刷新，可以研究刷新策略的影响。如果同时改变编译优化、数据量、硬盘和输出位置，差异就难以归因。观察到相关不代表已经证明了原因。

## 34.3 先写一张问题卡

```text
任务：处理哪份数据，完成到哪一步？
问题：我觉得哪项指标异常？
假设：可能是在计算、等待，还是输出？
预测：如果假设成立，我会观察到什么？
操作：保持哪些条件，只改变什么？
结果：原始输出、退出状态、重复次数。
结论：证据支持什么，还有什么没有验证？
```

不要先写“优化为零拷贝”再寻找证据。初学时可以把问题缩小到“等待是否也计入经过时间”，先用一个小实验把测量口径理解清楚，再分析大型程序。

## 34.4 经过时间与CPU时间

**经过时间**是从开始到结束过去多久，常称wall time。**CPU时间**是处理器为被统计任务实际执行所累计的时间。进程等待定时器、I/O或调度时，经过时间增加，本进程却未必消耗相应CPU时间。

工具中的user通常表示用户态CPU时间，sys表示内核态CPU时间；其统计对象可能包括被等待的子进程，具体看工具用法。多个线程同时在多核上执行时，累计CPU时间可能大于经过时间。所以`real = user + sys`不是所有程序必须满足的等式。

## 34.5 用一个手算例子分开口径

假设一个单线程任务先计算0.04秒，再等待0.20秒，最后计算0.01秒。理想化模型中，经过时间至少约0.25秒，CPU执行约0.05秒；实际还有调度、系统调用和测量开销。本段是演算，不是本机跑出的固定结果。

再设两个线程各用CPU执行0.10秒，完全并行且忽略开销。经过时间可能约0.10秒，累计CPU约0.20秒。由此可见，两个口径的差值和比例只能帮助提出假设，不能单独定位某块磁盘、某把锁或某个函数。

## 34.6 工具各自回答什么

| 工具或接口 | 主要用途 | 一次观察不能说明什么 |
| --- | --- | --- |
| `ps` | 某时刻的进程状态与关系 | 整段运行期间一直如此 |
| `top` | 连续观察活动概况 | 所有百分比口径都相同 |
| Bash的`time` | 命令或管道的时间汇总 | 直接定位C代码某一行 |
| `/proc` | Linux生成的系统与进程视图 | 普通静态文件的永久内容 |
| `strace` | 系统调用、信号与部分进程状态交互 | 看见所有用户态计算 |
| 程序内计时 | 测量自己选定的代码区间 | 自动消除测量开销 |

先选最能回答问题的一个工具。比如要确认`cd`是否改变父Shell目录，用`pwd`对照就足够，不需要先跟踪整台机器。

## 34.7 只观察自己启动的进程

在**Ubuntu/WSL的Bash，任意目录**执行：

```bash
ps -p $$ -o pid,ppid,stat,comm
sleep 3 &
observe_pid=$!
ps -p "$observe_pid" -o pid,ppid,stat,comm
wait "$observe_pid"
```

`$$`在这里展开为Bash的PID；`&`让这个sleep在后台启动；`$!`取得刚启动的后台任务PID；`wait`等待自己的任务结束。后台只是这次观察方法，不表示第35章的小Shell已经支持后台语法。

`STAT`常见R表示正在运行或可运行，S表示可中断等待，Z表示已经终止但尚待回收等。状态是快照，具体组合还含附加标志；sleep太快结束时可能只剩表头。不要为了观察到某状态给无关进程发信号。

## 34.8 /proc/self到底是谁

在**Ubuntu/WSL的Bash，任意目录**执行：

```bash
cat /proc/self/status
cat /proc/$$/status
```

第一条由cat打开`/proc/self/status`，self指cat；第二条由Bash先把`$$`展开成自己的PID，cat据此读取Bash对应的条目。两条命令可能看到不同名称和编号，原因是路径所指进程不同，不是内核输出随机出错。

条目可能随进程生命期消失，权限也可能限制可读范围。本章只看自己环境中允许读取的记录。比较内存字段时先查单位与含义；虚拟地址空间、常驻内存和历史峰值不能当作同一数字。

## 34.9 单调时钟适合测一段间隔

`CLOCK_MONOTONIC`提供单调时间基准，适合相减得到经过的间隔，不把它当作年月日。`CLOCK_PROCESS_CPUTIME_ID`用于本进程的CPU时间，包含进程内线程累计执行，不能自动替代任意子进程的CPU统计。

`struct timespec`用秒与纳秒两个成员表示时间；一秒有十亿纳秒。两个时间相减时，纳秒部分可以先按有符号差计算，再与秒差组合。本章只处理很短的同机间隔，不把纳秒字段的存在等同于结果有纳秒级准确度。

## 34.10 完整程序：计算与等待的对照

保存为`measure-self.c`，平台Linux/POSIX。它只有两个固定模式：`cpu`进行有限无符号计算，`wait`请求等待200毫秒。没有用户控制的无限循环或大内存分配。

**完整程序：measure-self.c**

```c
#include <errno.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <time.h>

static double seconds(struct timespec after, struct timespec before) {
    return (double)(after.tv_sec - before.tv_sec) +
           (double)(after.tv_nsec - before.tv_nsec) / 1000000000.0;
}

int main(int argc, char **argv) {
    if (argc != 2 || (strcmp(argv[1], "cpu") != 0 && strcmp(argv[1], "wait") != 0)) {
        fputs("usage: measure-self cpu|wait\n", stderr);
        return 2;
    }
    struct timespec wall_start, cpu_start, wall_end, cpu_end;
    if (clock_gettime(CLOCK_MONOTONIC, &wall_start) < 0 ||
        clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &cpu_start) < 0) {
        perror("clock start"); return 1;
    }
    uint32_t value = 1;
    if (strcmp(argv[1], "cpu") == 0) {
        for (unsigned int i = 0; i < 10000000; ++i) {
            value = value * UINT32_C(1664525) + UINT32_C(1013904223);
        }
    } else {
        struct timespec remaining = { .tv_sec = 0, .tv_nsec = 200000000 };
        while (nanosleep(&remaining, &remaining) < 0) {
            if (errno == EINTR) { continue; }
            perror("nanosleep"); return 1;
        }
    }
    if (clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &cpu_end) < 0 ||
        clock_gettime(CLOCK_MONOTONIC, &wall_end) < 0) {
        perror("clock end"); return 1;
    }
    if (printf("mode=%s checksum=%lu\nwall_s=%.9f\ncpu_s=%.9f\n", argv[1],
               (unsigned long)value, seconds(wall_end, wall_start), seconds(cpu_end, cpu_start)) < 0 ||
        fflush(stdout) == EOF) { return 1; }
    return 0;
}
```

## 34.11 逐句说明数值、等待和范围

`uint32_t`在本Linux实验环境提供32位无符号整数。计算按无符号规则进行，结果回到32位范围，避免用有符号溢出制造不可靠实验。checksum参与输出，让我们同时检查计算结果；本程序是教学负载，不是CPU性能认证工具。

`nanosleep`可能被信号中断，此时剩余请求时间写回remaining，程序继续等待。其他错误返回1。等待200毫秒是请求，不是承诺进程恰好在第200.000毫秒重新执行；调度可能让实际间隔更大。

两种时钟前后分别读取，因此区间端点并非完全重合。很短区间可能被时钟精度与调用开销主导。打印九位小数只规定显示形式，不证明九位数字都有测量意义。

## 34.12 编译、预测与运行

在**Ubuntu/WSL的Bash**建立个人目录并保存源码，然后执行：

```bash
mkdir -p ~/os-lab/batch09
cd ~/os-lab/batch09
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror -O0 measure-self.c -o measure-self
./measure-self wait
./measure-self cpu
time ./measure-self wait
```

先预测：wait模式的经过时间大约至少覆盖等待请求，而本进程CPU时间通常小很多；cpu模式会累积CPU时间，但具体数字取决于机器和负载。最后一条Bash time还包含程序启动、输出等区间，不能要求与程序内部时间完全相同。

应先检查退出状态为0和checksum稳定，再讨论时间。wait的checksum为1；cpu的具体值可以由同样的无符号递推独立计算验证。不要为了让比例好看，把不符合预测的真实运行删掉。

## 34.13 做三次记录，再提出有限结论

在**同一Bash目录**分别运行每个模式三次，手工复制原始三行结果到自己的报告，不需要学习脚本循环才能完成。保持同一二进制、输入和输出位置；同时记下`uname -r`和`gcc --version`。

可以比较三次中的最小、中间和最大值，观察波动。三次样本只能作为练习，不能据此宣称某类CPU优于另一类。若要比较`-O0`与`-O2`，另存二进制名、确认checksum一致，说明此时改变了编译优化，不把差异归于内核调度器。

## 34.14 可选strace：先确认工具是否存在

在**Ubuntu/WSL的Bash，batch09目录**先运行：

```bash
command -v strace
```

找不到时本章主线照常完成；记录“未安装，未执行”，不需要为了这一节调整系统。已经有strace且允许跟踪自己启动的程序时，可运行：

```bash
strace -o wait.trace -e trace=clock_nanosleep,nanosleep,write ./measure-self wait
cat wait.trace
```

跟踪写入自己的新文件。库函数名不一定与底层调用名完全相同，等待可能显示为clock_nanosleep。某些取时操作可走vDSO等用户态路径，因此没看到clock_gettime系统调用，不等于程序没读取时钟。

## 34.15 怎样读一行跟踪结果

把一行概念性示意`write(1, "...", 12) = 12`拆成调用名、参数、返回值：fd1表示标准输出，12表示请求字节数，右侧12是实际写入字节数。这是**示意格式**，不是从你机器复制的固定日志。

要观察第35章的父子进程，可使用`strace -f`启动自己的小Shell，`-f`追踪派生进程；只跟踪父进程可能漏掉真正执行的工作。跟踪会增加开销、改变调度，不能把跟踪时间直接当作未跟踪时的性能。未经授权不要附加到他人的进程。

## 34.16 一个从现象走向假设的案例

现象：运行管道后迟迟不结束。第一种假设是计算很重，另一种是等待EOF。先检查输入规模和输出是否还在增长，再根据自己创建的进程关系与fd设计检查是否仍有写端引用；如果有跟踪证据，可观察read是否在等待。

若父进程多保留了写端，修复是关闭不用的引用，然后以相同输入重跑，确认输出完整且能够结束。这个案例没有测到CPU频率，就不应给出“换更快CPU”结论。不要通过真实制造永久挂起来证明自己理解，先画等待关系就能识别很多错误。

## 34.17 常见测量错误

| 错误 | 为什么影响结论 | 修正方式 |
| --- | --- | --- |
| 两组输入大小不同 | 做的工作量不同 | 固定输入及预期结果 |
| 只比较一次运行 | 偶然调度与环境干扰 | 保留重复样本与范围 |
| 跟踪开启与关闭混比 | 工具改变了运行 | 分开记录工具条件 |
| 丢弃失败运行但不说明 | 只剩看起来好的样本 | 先查正确性和失败原因 |
| 把缓存都当内存泄漏 | 用途和生命周期不同 | 看分配、引用和重复行为 |
| 每次printf都放在计时核心 | 测到了输出成本 | 明确计时区间与测量目标 |

本课程不清空系统缓存、不关闭安全机制、不改变CPU调频。可复现实验不要求所有人得到相同毫秒数，而是要求过程与推理能够复查。

## 34.18 练习与参考答案

**A：** 等待模式wall约0.20秒、cpu约0.00003秒，能否确定是在等磁盘？**参考答案：** 不能。本程序明确调用了定时等待；时间比例本身只提示等待或未获CPU等可能性。

**B：** strace没显示一千万次乘法，是否编译器删掉了循环？**参考答案：** 不能据此判断。普通用户态算术无需每次系统调用，跟踪的观察范围不同。

**C：** `/proc/self/status`与`/proc/$$/status`名称不同，先检查什么？**参考答案：** 谁展开路径、谁打开文件、self对应谁。第一条常是cat，第二条指定Bash PID。

**D：** 完成时间缩短但checksum变了，是否算优化成功？**参考答案：** 不算同一任务的有效性能改进。先恢复正确结果，再比较相同工作。

## 34.19 交一份小报告

报告包含问题卡、环境、源码版本、编译参数、三次原始输出、成功状态及一段解释。至少写一个未验证项，例如“没有测实际磁盘等待”“没有统计任意子进程CPU”“未安装strace”。结论示例是“本机所测wait模式主要增加经过时间”，不是“所有慢程序都不消耗CPU”。

完成条件：能独立编译两种模式、解释两个时钟和一次快照、提交可复查报告，并为反常结果提出下一项观察。后续Shell出现故障时沿用这个流程，先缩小现象，不一口气改五个函数。
