# 15 信号与进程生命周期：通知、终止与回收

平台为Linux/WSL Ubuntu，Bash终端，练习目录`~/os-lab/processes`，需要同目录`lab.h`。编译仍用`-std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror -g`。实验仅向自己刚创建且记录了正PID的孩子发送信号，不猜系统中其他进程的编号。

## 2. 信号是什么

**信号**是操作系统向进程或线程传递某类事件的通知机制。例如终端中按Ctrl+C，通常会向前台进程组发送`SIGINT`。通知可能打断正常执行路径，转去执行处理函数，或按默认动作终止、停止等。

信号不是普通函数参数，也不是适合传输任意文本的数据管道。传统标准信号同类多次产生时可能合并，不能靠“每次通知加一”保证精确计数。需要可靠传递每条记录时，使用有明确协议的管道等机制。

## 3. 几个常见名字

| 信号 | 本章用途 | 常见默认含义 |
| --- | --- | --- |
| SIGINT | Ctrl+C通知 | 终止 |
| SIGTERM | 请求结束 | 终止，可由程序处理 |
| SIGKILL | 强制终止 | 不能捕获、忽略或屏蔽 |
| SIGSTOP | 强制停止 | 不能捕获、忽略或屏蔽 |
| SIGUSR1 | 本实验自定义通知 | 默认终止，必须先设处理策略 |
| SIGCHLD | 孩子状态变化通知 | 仍须按协议等待、回收 |

名字比数字可移植。不要在教材代码里到处写15、9来代替语义名称。`kill`这个函数名容易误导，它的职责是**发送信号**；发送一个被捕获的通知，不一定让目标终止。

## 4. 主线：按Ctrl+C后自行收尾

[完整源码：signal-demo.c](示例代码/signal-demo.c)

```c
#include "lab.h"
#include <signal.h>
#include <time.h>

static volatile sig_atomic_t stopped = 0;
static void on_stop(int signo) { (void)signo; stopped = 1; }

int main(void) {
    struct sigaction action = {0};
    action.sa_handler = on_stop;
    sigemptyset(&action.sa_mask);
    if (sigaction(SIGINT, &action, NULL) < 0) { die("sigaction"); }
    printf("ready pid=%ld\n", (long)getpid());
    fflush(stdout);
    while (!stopped) {
        struct timespec delay = {0, 100000000};
        if (nanosleep(&delay, NULL) < 0 && errno != EINTR) { die("nanosleep"); }
    }
    puts("stopped safely");
    return 0;
}
```

编译为`signal-demo`，执行`./signal-demo`。看到`ready pid=...`后，在**同一个运行终端**按Ctrl+C。预期随后出现`stopped safely`，程序正常返回0；再执行`echo $?`核对。

这个例程没有被默认SIGINT动作直接杀死，而是执行处理函数，把退出决定留给正常控制流。它为了便于初学者观察，周期性检查标志；后面会写真正等待通知而不轮询的版本。

## 5. 先看注册代码

`struct sigaction action = {0};`创建配置对象并零初始化。`action.sa_handler = on_stop;`把函数入口交给系统：这里是函数名，不是`on_stop(...)`立即调用。

**回调函数**就是把函数交给某个机制，在事件发生时由它调用。`on_stop`接收信号编号，返回`void`。`(void)signo`表示本例有意不使用这个参数，避免未使用参数的警告。

`sigemptyset(&action.sa_mask)`设置处理期间额外屏蔽集合为空；正在处理的信号本身通常会按默认规则暂时屏蔽，不能据此推断处理函数可以任意重入。`sigaction`注册处理策略，返回负值时立即报错。

## 6. 为什么是volatile sig_atomic_t

`sig_atomic_t`是适合在信号处理上下文中进行不可分割访问的整数类型；本例只做简单赋值和读取。`volatile`使这类访问不被当成永远不会异步变化的普通变量处理。

这个组合服务于本例“一个信号处理函数设置一个标志”的规则，不是通用线程安全方案。它不把复合操作变成锁，不保证多个线程之间的同步，也不适合凭空扩展为共享复杂数据结构。

`static`放在文件作用域表示这个名字限于本源文件，且对象从程序开始到结束都存在。处理函数不能保存指向已经结束的局部栈对象的地址来稍后使用，这与第09章生命期规则一致。

## 7. 为什么处理函数里不printf

信号可能恰好在普通代码执行stdio、分配内存或更新库内部状态时到达。处理函数再调用同一类不安全操作，可能遇到内部锁或尚未完成的状态，造成死锁或损坏。

因此本章采用最小规则：处理函数只赋标志，不printf、不malloc、不取得普通互斥锁；实际打印和资源收尾回到正常流程完成。POSIX列有异步信号安全函数，但“某个底层函数可用”也不等于任意组合都适合放进处理函数。

本课处理函数没有调用会改变`errno`的函数；若以后确实调用允许的接口，还需要考虑保存和恢复`errno`等约束。现在先把“短小、只通知”这个模式写对。

## 8. nanosleep在这里解决什么

`struct timespec delay = {0, 100000000};`表示0秒加100000000纳秒，也就是约0.1秒。循环用它避免无休止地占满CPU检查标志。收到SIGINT可以打断等待，随后检查`stopped`。

它没有用来证明另一个进程一定执行到某一步。信号恰好在检查后、nanosleep前到达，最坏可能多等待一次短间隔；对于这个演示可以接受，但不是严格的立即响应协议。不要把“睡短一点”当作消除竞态的通用解法。

**竞态**指结果依赖多个活动的时间交错，而程序没有建立所需的约束。下面把容易漏通知的交错具体写出来。

## 9. 检查再pause为什么会漏

以下是**错误思路的概念演算，不运行**：

```text
孩子检查 received == 0
父亲此时发送信号
孩子处理函数把 received 改成1，然后返回
孩子接着调用 pause，等待下一次信号
父亲以为通知已经发完，不再发送
```

即使标志已经是1，孩子仍可能睡下，因为“检查标志”和“开始等待”之间有空隙。换成两次检查也不能从根本上消除这个窗口。需要让“解除屏蔽并进入等待”成为一个不可插入漏通知空隙的操作。

## 10. 屏蔽、待处理、忽略的区别

**屏蔽**某信号表示暂不交付；它仍可能成为待处理信号，解除屏蔽后再处理。**忽略**表示采用忽略策略，不等于“先存着以后处理”。**待处理**表示事件已经产生但尚未按当前规则交付。

本章是单线程进程，使用`sigprocmask`管理当前执行线程的信号屏蔽集合；多线程环境应采用相应线程接口和设计，不能直接推广。

办法是：先注册处理函数，fork以前屏蔽SIGUSR1；孩子继承屏蔽状态，因此通知再早也先待处理；孩子调用`sigsuspend`，临时用允许SIGUSR1的集合替换屏蔽并进入等待。

## 11. 完整的早到通知实验

**完整程序：signal-handshake.c**

```c
#include "lab.h"
#include <signal.h>

static volatile sig_atomic_t received = 0;
static void on_notice(int signo) { (void)signo; received = 1; }

int main(void) {
    struct sigaction action = {0};
    action.sa_handler = on_notice;
    if (sigemptyset(&action.sa_mask) < 0) { die("sigemptyset"); }
    if (sigaction(SIGUSR1, &action, NULL) < 0) { die("sigaction"); }
    sigset_t block, oldmask;
    if (sigemptyset(&block) < 0 || sigaddset(&block, SIGUSR1) < 0) {
        die("signal set");
    }
    if (sigprocmask(SIG_BLOCK, &block, &oldmask) < 0) { die("block"); }
    if (fflush(NULL) == EOF) { die("fflush"); }
    pid_t child = fork();
    if (child < 0) { die("fork"); }
    if (child == 0) {
        sigset_t waiting = oldmask;
        if (sigdelset(&waiting, SIGUSR1) < 0) { _exit(1); }
        while (!received) {
            if (sigsuspend(&waiting) < 0 && errno != EINTR) { _exit(1); }
        }
        puts("child received SIGUSR1");
        if (fflush(stdout) == EOF) { _exit(1); }
        _exit(0);
    }
    if (kill(child, SIGUSR1) < 0) {
        perror("kill notice");
        (void)kill(child, SIGKILL);
        (void)wait_child(child);
        return 1;
    }
    if (sigprocmask(SIG_SETMASK, &oldmask, NULL) < 0) { die("restore mask"); }
    int code = wait_child(child);
    printf("parent child_exit=%d\n", code);
    return code;
}
```

编译为`signal-handshake`并反复运行。预期每次都是孩子收到通知、父亲取得退出0。父亲没有sleep，也没有先等孩子打印“我已经开始等”，而是创建成功后马上发送。正确性来自先屏蔽与原子等待，不来自机器速度。

## 12. 按三种到达时刻推演

| 到达时刻 | 为什么不漏 |
| --- | --- |
| 孩子开始循环前 | SIGUSR1仍被屏蔽，保留待处理状态 |
| 孩子检查后、sigsuspend前 | 仍被屏蔽，接下来原子解除并等待时可交付 |
| 孩子已在sigsuspend里 | 被允许的信号到来，执行处理函数并唤醒 |

处理函数返回后，`sigsuspend`通常以-1和EINTR返回，并恢复调用前的屏蔽集合。这里EINTR是预期的唤醒方式，不应当直接当作实验失败。循环重新检查标志，防止其他可捕获信号唤醒后误认为目标通知已经收到。

父进程恢复自己的旧屏蔽集合；孩子在本演示处理完后直接退出。若它还要继续工作，也应根据后续设计恢复适当集合，不能把演示末尾退出当作长期程序的完整生命周期管理。

## 13. 信号终止和正常退出怎样区分

**完整程序：signal-status.c**

```c
#include "lab.h"
#include <signal.h>

int main(void) {
    pid_t child = fork();
    if (child < 0) { die("fork"); }
    if (child == 0) {
        struct sigaction action = {0};
        action.sa_handler = SIG_DFL;
        if (sigemptyset(&action.sa_mask) < 0 ||
            sigaction(SIGTERM, &action, NULL) < 0) { _exit(99); }
        sigset_t set;
        if (sigemptyset(&set) < 0 || sigaddset(&set, SIGTERM) < 0 ||
            sigprocmask(SIG_UNBLOCK, &set, NULL) < 0) { _exit(99); }
        (void)raise(SIGTERM);
        _exit(99);
    }
    int status;
    while (waitpid(child, &status, 0) < 0) {
        if (errno != EINTR) { die("waitpid"); }
    }
    if (WIFSIGNALED(status) && WTERMSIG(status) == SIGTERM) {
        puts("terminated_by_signal=SIGTERM");
        return 0;
    }
    fputs("expected SIGTERM termination\n", stderr);
    return 1;
}
```

编译运行，预期`terminated_by_signal=SIGTERM`，父进程返回0。孩子先恢复SIGTERM默认策略并解除该信号屏蔽，再用`raise`向自己发送；若未按预期终止，回退退出99，让父亲发现异常。

父亲返回0表示“观察实验符合预期”，并不表示孩子正常退出0。这也是为什么测试报告必须描述验证目标，而不能只列一个绿色退出码。

## 14. 发送成功不代表已经结束

`kill(child, SIGTERM)`成功，只说明信号请求按接口被接受，不证明目标已执行处理函数，更不证明资源已全部释放。要确认孩子终止仍应wait。

SIGTERM允许程序自行处理，适合设计有序收尾；SIGKILL不能被处理，无法让应用执行自己的保存步骤。本批综合练习只在第二个孩子创建失败、需要避免遗留第一个实验孩子时，对这个已记录的正PID使用SIGKILL并回收。完整产品需要根据任务设计更温和的停止协议。

## 15. 僵尸、孤儿、停止各是什么

**僵尸进程**已经退出，不再执行普通代码，但父进程尚未领取退出信息。它不是还在后台计算的“幽灵程序”。父亲wait回收后，相关记录才能释放。向僵尸再发终止信号不能代替wait。

**孤儿进程**是原父进程已结束的孩子，可以仍在运行；系统会按环境把它交给接管者，例如子收割进程或相应命名空间的init。WSL、容器等环境下不要一概假定显示的父PID永远是1。

**停止进程**暂停执行，仍存在且未必已终止，可被相应继续信号恢复。前台作业、进程组和Ctrl+Z涉及Shell作业控制；第35章会说明简易Shell的能力边界，完整作业控制属于后续扩展。

## 16. EINTR是不是都应该重试

不是。必须看接口返回值和当前程序意图。第11章write循环遇到EINTR继续发送；本章`sigsuspend`的EINTR表示一次预期唤醒，随后应检查标志；主线nanosleep被中断后回到循环，若stopped已经设置就结束。

若程序已经收到退出请求，仍无限重试原本想取消的操作，就会违背收尾协议。也不要假定所有阻塞接口都会按同样方式中断或自动重启；处理策略、接口和系统约定共同决定行为。

## 17. 常见错误

处理函数里直接printf：改为只设标志，在正常控制流输出。

父亲先发送、孩子后安装处理函数：通知可能按默认动作终止孩子。先准备处理策略和屏蔽，再创建。

`if (!flag) pause()`偶尔卡住：存在检查与睡眠之间的窗口，使用明确的屏蔽和原子等待协议。

把SIGUSR1当精确计数队列：标准信号可能合并，换成记录传输机制。

只发信号不wait：发送与回收是不同责任。对自己的孩子保存PID并完成等待，不把结束工作交给猜测。
