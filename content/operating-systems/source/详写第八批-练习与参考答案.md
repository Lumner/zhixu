## 三、协议闭卷演算

约定仍是两字节高位在前长度、0—64字节负载、仅一帧并以输入结束收尾。先填写下表，再核对第32章的程序。

| 输入十六进制 | 判断 | 参考原因 |
| --- | --- | --- |
| 空输入 | 状态2 | 缺少头部 |
| `00` | 状态2 | 头部截断 |
| `00 00` | 成功 | 空负载合法 |
| `00 02 41 00` | 成功 | 两字节内容含NUL |
| `00 03 41 42` | 状态2 | 负载短一字节 |
| `00 41` | 状态2 | 长度65超上限 |
| `00 00 00` | 状态2 | 一帧后有额外字节 |

改造题：如果允许连续两帧，不能只去掉尾随检查，还应定义帧数、结束条件、每帧响应与累计资源上限。本批答案只实现单帧，不把这道改造题写成已交付多帧功能。

## 四、项目目标：把解析器变成子进程服务

项目名`local-request`。父进程创建AF_UNIX成对socket并启动一个子进程；子进程把一个端点接到标准输入与标准输出，再用`execl`运行第32章的`frame-read`；父进程发送长度头与一段至多64字节的命令行文本，半关闭发送方向，读取解析结果并回收子进程。

这组合了进程、exec、fd重定向、字节流和协议。它不读写外部业务文件，也不监听网络端口；不是远程命令执行服务。传给它的文本只是数据，子进程不会把内容当Shell命令执行。普通终端启动时标准输入0、输出1与错误2均已打开，这是本例fd重定向的运行前提。

## 五、先写清所有权与结束条件

```text
父：持有sv[0] → 发送头与内容 → shutdown写方向 → 读取响应直到EOF
子：关闭sv[0] → sv[1]复制到0和1 → 关闭原sv[1] → exec frame-read
解析器：读完整帧与EOF → 输出长度/hex → 退出
父：关闭sv[0] → waitpid自己的子进程 → 检查退出结果
```

为什么子进程必须关闭不用的端点？多留引用会延长生命周期，使本应出现的EOF不能按预期到来。为什么父进程用半关闭？它要告诉解析器输入结束，同时保留接收响应的方向。这里文本有64字节上限，响应也很小，避免双方大规模互等写缓冲；任意大流量需要重新设计双向推进。

## 六、完整参考程序

先独立尝试再看答案。平台Linux/POSIX，保存为`local-request.c`，与编译好的`frame-read`放在同一当前工作目录。代码不依赖公共头文件。

**完整程序：local-request.c**

```c
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

static int all(int fd, const unsigned char *data, size_t length) {
    while (length > 0) {
        ssize_t n = write(fd, data, length);
        if (n < 0 && errno == EINTR) { continue; }
        if (n < 0) { perror("write"); return -1; }
        if (n == 0) { fputs("write made no progress\n", stderr); return -1; }
        data += n;
        length -= (size_t)n;
    }
    return 0;
}

int main(int argc, char **argv) {
    if (argc != 2 || strlen(argv[1]) > 64) {
        fputs("usage: local-request TEXT_UP_TO_64_BYTES\n", stderr);
        return 2;
    }
    struct sigaction action = {0};
    action.sa_handler = SIG_IGN;
    if (sigemptyset(&action.sa_mask) < 0 || sigaction(SIGPIPE, &action, NULL) < 0) {
        perror("SIGPIPE"); return 1;
    }
    int sv[2];
    if (socketpair(AF_UNIX, SOCK_STREAM, 0, sv) < 0) {
        perror("socketpair"); return 1;
    }
    pid_t child = fork();
    if (child < 0) {
        perror("fork"); close(sv[0]); close(sv[1]); return 1;
    }
    if (child == 0) {
        if (close(sv[0]) < 0 || dup2(sv[1], STDIN_FILENO) < 0 ||
            dup2(sv[1], STDOUT_FILENO) < 0 || close(sv[1]) < 0) {
            perror("child descriptors"); _exit(126);
        }
        execl("./frame-read", "frame-read", (char *)NULL);
        perror("execl frame-read");
        _exit(127);
    }
    int result = 0;
    if (close(sv[1]) < 0) { result = 1; }
    size_t length = strlen(argv[1]);
    unsigned char header[2] = {
        (unsigned char)(length / 256), (unsigned char)(length % 256)
    };
    if (all(sv[0], header, sizeof header) < 0 ||
        all(sv[0], (const unsigned char *)argv[1], length) < 0) {
        result = 1;
        goto finish;
    }
    if (shutdown(sv[0], SHUT_WR) < 0) {
        perror("shutdown"); result = 1; goto finish;
    }
    for (;;) {
        unsigned char response[32];
        ssize_t n = read(sv[0], response, sizeof response);
        if (n < 0 && errno == EINTR) { continue; }
        if (n < 0) { perror("read response"); result = 1; break; }
        if (n == 0) { break; }
        if (all(STDOUT_FILENO, response, (size_t)n) < 0) {
            result = 1; break;
        }
    }
finish:
    if (close(sv[0]) < 0) { result = 1; }
    int status;
    pid_t waited;
    do { waited = waitpid(child, &status, 0); }
    while (waited < 0 && errno == EINTR);
    if (waited < 0) { perror("waitpid"); return 1; }
    if (!WIFEXITED(status) || WEXITSTATUS(status) != 0) {
        fputs("worker did not complete successfully\n", stderr);
        result = 1;
    }
    return result;
}
```

## 七、逐步解释程序边界

`SIGPIPE`在这个独立程序中被忽略，使写入已关闭连接时有机会检查`EPIPE`并回收子进程。这个设置也会由exec后的进程继承，不能把修改信号行为当作库函数无副作用的实现；它是本程序明确的选择。

子进程调用exec后，PID不因替换程序自动改变，fd0/1仍引用同一个双向socket端点。标准错误保持原来的终端或测试捕获位置，诊断不混进正常响应。`execl("./frame-read",...)`使用受控工作目录里的明确相对路径，不查PATH；目录和解析器可执行文件由你控制，是信任假设。

每条父进程失败路径最终关闭端点并wait自己的子进程。子进程在dup或exec失败时`_exit`，操作系统回收其剩余引用；没有声称每条子分支都手工关闭所有fd。本项目只连接受控且会结束的解析器，没有实现不可信工作进程的会话截止时间。自动测试用独立进程组超时兜底，不能把它说成程序本身的超时功能。

## 八、保存、编译和预期结果

在**Ubuntu/WSL的Bash，`~/os-lab/batch08`目录**，先保存第32章的`frame-read.c`与本页`local-request.c`，执行：

```bash
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror frame-read.c -o frame-read
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror local-request.c -o local-request

echo $?
./local-request ''
./local-request 'a b'
```

依次应得到长度5/hex `68656c6c6f`、长度0/空hex、长度3/hex `612062`。第一组状态0。单引号把含空格文本保留为一个Bash参数；传入的引号本身不属于数据。中文文本按当前编码占多个字节，`strlen`不是汉字计数器。

命令行参数不能包含NUL，所以这个项目入口只接受文本；协议解析器本身已能处理NUL负载，其独立测试包含这类输入。不要把入口限制与底层协议能力混为一谈。

## 十、跨章问题与参考答案

**1. 为什么父进程发送完不能立即close并希望再读响应？** 关闭自己的端点fd后不能再用它读取；需要半关闭发送方向，同时保留接收方向。

**2. 如果把请求文本交给`system`执行，是否仍属于本项目？** 不属于。那会引入命令解析和执行权限等新边界。本项目把文本当负载，只输出字节表示。

**3. 若某容器能运行项目，就证明它有独立内核吗？** 不能；普通Linux容器可以通过共享内核提供这些接口。还应区分fd、PID、网络视图与资源限制。

**4. 看到三次read就能说请求有三条消息吗？** 不能。调用次数受缓冲、就绪、调度和主动限制等影响，应用消息以协议为准。

**5. 为何观察PID 1、UID和namespace仍不足以声明服务安全？** 这些是部分环境证据；程序还需正确解析输入、检查业务授权、限制资源和处理失败。每项机制各管自己的边界。
