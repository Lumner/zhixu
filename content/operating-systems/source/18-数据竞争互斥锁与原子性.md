## 18.1 counter++ 为什么不够

先会线程创建与等待。两个线程都执行 counter++，逻辑上可能经历“读旧值 → 加一 → 写回”。若双方都读到 0 再写 1，一次更新就被覆盖。这个交错说明保护共享更新的必要性；更严格地说，C 中无同步的冲突访问至少一方写入时构成数据竞争，属于未定义行为，不承诺只是偶尔少加几次。

volatile 不能提供线程间互斥与完整同步，也不能把复合运算变成原子操作。把优化关闭同样不能修正语言层面的数据竞争。

## 18.2 完整例程 mutex.c

[完整源码：mutex.c](示例代码/mutex.c)

```c
#include "lab.h"
#include <pthread.h>

static long counter = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static void *work(void *unused) {
    (void)unused;
    for (int i = 0; i < 10000; i++) {
        thread_check(pthread_mutex_lock(&lock), "lock");
        counter++;
        thread_check(pthread_mutex_unlock(&lock), "unlock");
    }
    return NULL;
}

int main(void) {
    pthread_t a, b;
    thread_check(pthread_create(&a, NULL, work, NULL), "create a");
    thread_check(pthread_create(&b, NULL, work, NULL), "create b");
    thread_check(pthread_join(a, NULL), "join a");
    thread_check(pthread_join(b, NULL), "join b");
    printf("counter=%ld\n", counter);
    thread_check(pthread_mutex_destroy(&lock), "destroy");
    return 0;
}
```

运行 `make mutex`、`./mutex`，结果应稳定为 `counter=20000`。每个线程执行 10000 次。临界区是访问共享 counter 的那一小段，所有写入遵守同一把锁。

mutex_lock 成功后当前线程独占该临界区；若另一线程已持有锁，调用者等待。unlock 允许后来者继续，并配合同一同步协议建立可见性。main 在 join 后读取最终 counter，所以也没有和工作线程同时读写。

## 18.3 锁保护的是规则

只给“写入”加锁却让另一个线程无锁读取，同样可能有数据竞争。多个字段共同表达状态时，需让整个不变量在锁内保持一致，例如余额转移不能只保护两次赋值中的一次。

锁的范围过大，耗时 I/O 也占着锁，会降低并发；范围太小，把“检查 → 使用”拆开，又可能留下竞态。先明确不变量，再决定临界区。不要持锁执行等待另一个也需要这把锁才能完成的外部操作。

## 18.4 原子操作与边界

C 的 `stdatomic.h` 提供原子类型和操作。单个计数器可以用原子 fetch_add；多个变量的联合业务规则通常还需要更完整协议。无锁不等于无等待成本，也不等于初学者可以忽略内存顺序。本课主线用互斥锁，原子内存顺序作为延伸。

## 18.5 实验、练习与答案

连续运行正确例程 20 次，结果都应为 20000。重复运行能发现部分问题，但即使未观察到错误也不是形式证明。不要以“我的机器没错”证明删锁版本正确，理论上已经违反同步要求。

练习：增加第三个线程，正确结果？把加锁放到整个 10000 次循环外，正确性与并发有何变化？答案：30000；仍可保护总数，但两个工作循环基本串行，锁持有更久。是否更快需测量，不能只从锁调用次数下结论。
