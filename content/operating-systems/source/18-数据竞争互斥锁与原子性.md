# 18 数据竞争、互斥锁与原子性：把共享规则写进程序

> **零基础详细版 · 已重写。** 先用交错表解释共享更新，再运行有锁计数、关联状态和原子操作。错误模型与可运行程序分开，不执行普通变量的数据竞争来猜结果。建议8—11小时。

## 1. 本章要解决的变化

上一章每个工作者有自己的结果格子。现在两个人要更新同一个计数器，或者同时维护两份相关余额。问题不再只是“是否等线程结束”，还包括“工作期间谁可以看到或改变哪些状态”。

学完应能找到冲突访问，写出共享不变量，用同一锁保护完整操作，区分原子单步与完整业务协议，并解释为什么volatile和sleep不能代替同步。先修是第17章线程及join、第05章循环、第09章结构体。

## 2. 先定义数据竞争

**冲突访问**指访问同一内存位置且至少一方修改；若不同线程中的这类普通非原子访问缺少规定的同步顺序，就可能构成C语言的**数据竞争**。数据竞争导致未定义行为，语言不保证只是偶尔少算一次。

两个线程同时只读初始化后不再修改的数据，属于另一种情况；两个线程分别写不同普通整数对象也不等于写同一位置。不能只凭“变量在共享内存里”判错，也不能只凭“我跑了20次都对”判对。

这里的**同步顺序**指由语言或线程接口建立的先后与可见性关系，例如创建前初始化、join后读取，以及正确使用同一互斥锁。它不是看日志猜出的墙上时间先后。

## 3. 普通counter++的交错模型

以下是**解释丢失更新的概念模型，不是允许直接运行的C竞争程序**：

| 步骤 | 工作者A | 工作者B | 计数模型值 |
| --- | --- | --- | --- |
| 1 | 读到0 | | 0 |
| 2 | | 也读到0 | 0 |
| 3 | 算0+1，写1 | | 1 |
| 4 | | 算0+1，写1 | 1 |

两个人各加一次，本来期待2，模型却只剩1。这张表解释“读—改—写需要成为一个受保护操作”的动机。真实普通C变量出现数据竞争后，不承诺机器一定照这四行执行，更不能限定最终值只能是1或2。

## 4. 哪些常见补丁无效

`volatile long counter`不提供线程间互斥，也不把普通复合操作变成原子步骤。关闭优化不改变C的数据竞争规则；sleep只改变部分时机，不建立可靠同步；把打印放进去可能扰动调度，也不是修复。

主线程最后join两个工作者，只保证它晚于双方结束读取，不能让两个工作者之间原先重叠的无保护修改变安全。需要在实际冲突发生的阶段建立协议。

## 5. 互斥锁与临界区

**互斥锁**是一种同步对象，遵守协议的线程必须先成功取得它，才能访问相应受保护状态。一次只有一个持有者，其他争用者等待。**临界区**是需要作为整体保护的那段代码。

锁不是把某个变量物理封装起来：另一个线程若绕过锁直接读，硬件并不会因为源码中存在lock就自动阻止它。所有冲突读写都必须遵守同一协议；给同一变量的不同访问随手配不同锁，也不能互相协调。

本章使用普通非健壮mutex，不处理健壮锁持有者死亡恢复等另一类协议。pthread返回值按第17章规则检查。

## 6. 主线：正确共享计数

Linux/WSL Ubuntu的Bash，目录`~/os-lab/concurrency`，需要同目录lab.h。

[完整源码：mutex.c](示例代码/mutex.c)

```c
#include "lab.h"
#include <pthread.h>

static long counter = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static void *work(void *unused) {
    (void)unused;
    for (int i = 0; i < 10000; i++) {
        thread_check(pthread_mutex_lock(&lock), "lock");
        counter++;
        thread_check(pthread_mutex_unlock(&lock), "unlock");
    }
    return NULL;
}

int main(void) {
    pthread_t a, b;
    thread_check(pthread_create(&a, NULL, work, NULL), "create a");
    thread_check(pthread_create(&b, NULL, work, NULL), "create b");
    thread_check(pthread_join(a, NULL), "join a");
    thread_check(pthread_join(b, NULL), "join b");
    printf("counter=%ld\n", counter);
    thread_check(pthread_mutex_destroy(&lock), "destroy");
    return 0;
}
```

编译与执行：

```bash
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror -g -pthread mutex.c -o mutex
./mutex
```

预期`counter=20000`。先算2×10000，再说明每次加一都处在同一把锁保护下，最后主线程join以后才读。锁的存在与使用位置一起构成理由，不是仅凭这一次数字正确。

## 7. 沿一次加锁跟踪

A成功lock后进入临界区；B若此时请求同一锁，就等待。A修改counter再unlock；B随后成功取得锁时，能按同步规则看到前一持有者已发布的受保护修改。

A在临界区中也可能被CPU调度暂时切走，锁没有“禁止调度”。互斥的意思是其他遵守协议者不能同时进入，不是每条机器指令都不可中断。

解锁必须由合法持有者按接口规则执行。不要强行unlock别人的普通锁，不要复制pthread_mutex_t当作新锁，也不要在仍有人使用时destroy。静态初始化器建立一个初始可用的mutex，结束后由管理者销毁。

## 8. 锁内到底应放多少代码

先明确必须一起成立的规则，再选择范围。锁太小，把“检查库存大于0”和“扣减库存”拆开，另一个线程可能在两步之间改变状态。锁太大，把漫长文件I/O也包进去，会让别的工作者长时间无法推进。

锁保护“检查与依赖这个检查的更新”这个整体，不只是每条赋值。耗时处理若能先取得独立数据副本，再解锁处理，会更容易保持并发；但要说明副本是否还符合业务需要，不能为了减少锁范围拿过期信息做决定。

## 9. 关联状态需要不变量

**不变量**是程序在指定观察边界必须保持的关系。例如两个账户之间转移1，总额应不变，任何余额不应变负。若只保护扣款、不保护入账，其他遵守同一业务观察规则的人可能看到不完整状态。

下面用一把锁保护两个余额。它们只是小范围整数，不处理真实金融业务，也没有持久化或崩溃恢复承诺。

**完整程序：locked-pair.c**

```c
#include "lab.h"
#include <pthread.h>

static int left = 100, right = 100;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

static void *transfer(void *arg) {
    const int *direction = arg;
    for (int i = 0; i < 10000; i++) {
        thread_check(pthread_mutex_lock(&lock), "lock");
        if (*direction == 0 && left > 0) { left--; right++; }
        if (*direction == 1 && right > 0) { right--; left++; }
        if (left < 0 || right < 0 || left + right != 200) {
            fputs("invariant broken\n", stderr);
            exit(EXIT_FAILURE);
        }
        thread_check(pthread_mutex_unlock(&lock), "unlock");
    }
    return NULL;
}

int main(void) {
    int directions[2] = {0, 1};
    pthread_t workers[2];
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_create(&workers[i], NULL, transfer, &directions[i]), "create");
    }
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_join(workers[i], NULL), "join");
    }
    printf("total=%d nonnegative=%d\n", left + right, left >= 0 && right >= 0);
    thread_check(pthread_mutex_destroy(&lock), "destroy");
    return 0;
}
```

编译为`locked-pair`，预期`total=200 nonnegative=1`。具体left/right受交错影响，不要求最终各100，因为某些时刻可能因余额不足而跳过转移。验收的是声明的不变量，不是没有承诺的分配比例。

## 10. 建一张共享访问表

| 对象 | 写者 | 读者 | 规则 |
| --- | --- | --- | --- |
| left/right | 两个工作者 | 工作者与main | 工作者全部在lock下；main在全部join后 |
| directions各元素 | main创建前初始化 | 对应工作者 | 工作期间不再修改，持续到join |
| workers标识数组 | main | main | 管理线程独占 |

有锁代码也应能写出这张表。调试时如果发现某个“只用于日志”的读绕过协议，它仍可能构成冲突；不是只有业务赋值才需要关心同步。

## 11. 原子操作是什么

**原子操作**是按接口保证不可被其他相关访问观察为一半完成的操作。C的`stdatomic.h`提供原子类型及操作，适合例如单独计数这种小状态。

原子类型不会自动把任意多行操作组合成事务。先分别原子读取，再分别原子写入，仍可能有逻辑上的丢失更新；但这和普通非原子变量的数据竞争不同。我们可以用完全合法、可控的程序演示这个区别。

## 12. 原子计数的完整版本

**完整程序：atomic-counter.c**

```c
#include "lab.h"
#include <pthread.h>
#include <stdatomic.h>

static atomic_long counter = ATOMIC_VAR_INIT(0);
static void *work(void *unused) {
    (void)unused;
    for (int i = 0; i < 10000; i++) {
        (void)atomic_fetch_add(&counter, 1);
    }
    return NULL;
}

int main(void) {
    pthread_t workers[2];
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_create(&workers[i], NULL, work, NULL), "create");
    }
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_join(workers[i], NULL), "join");
    }
    printf("atomic_counter=%ld\n", atomic_load(&counter));
    return 0;
}
```

编译为`atomic-counter`，预期`atomic_counter=20000`。`atomic_fetch_add`把读取旧值和加一作为一次原子读改写，返回旧值；本例不需要旧值，所以显式忽略。它不是返回0成功的pthread接口，不能拿返回值送给thread_check。

本课使用这些函数的默认顺序一致语义，不引入更弱内存序。原子操作是否由硬件无锁指令实现取决于类型和平台；功能正确不等于已经证明性能更好。对原子对象的自增也有原子语义，本章第3节讨论的是普通非原子counter，不要混为一谈。

## 13. 可控实验：单步原子，整体仍错

**屏障barrier**让一组线程都到达某个检查点后才继续。本例参与者固定两个，不是让程序睡几毫秒猜对方读完。

**完整程序：atomic-split.c**

```c
#include "lab.h"
#include <pthread.h>
#include <stdatomic.h>

static atomic_int counter = ATOMIC_VAR_INIT(0);
static pthread_barrier_t both_read;

static void *work(void *unused) {
    (void)unused;
    int old = atomic_load(&counter);
    int code = pthread_barrier_wait(&both_read);
    if (code != 0 && code != PTHREAD_BARRIER_SERIAL_THREAD) {
        thread_check(code, "barrier wait");
    }
    atomic_store(&counter, old + 1);
    return NULL;
}

int main(void) {
    thread_check(pthread_barrier_init(&both_read, NULL, 2), "barrier init");
    pthread_t workers[2];
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_create(&workers[i], NULL, work, NULL), "create");
    }
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_join(workers[i], NULL), "join");
    }
    printf("split_result=%d\n", atomic_load(&counter));
    thread_check(pthread_barrier_destroy(&both_read), "barrier destroy");
    return 0;
}
```

编译为`atomic-split`，预期稳定`split_result=1`。接口针对本课Linux/POSIX平台，不能假设所有线程库都有barrier。屏障返回0或`PTHREAD_BARRIER_SERIAL_THREAD`都表示成功，不要把后者当成线程失败。

## 14. 为什么这里恰好是1

两个线程必须先完成读取才能通过屏障；在屏障以前没有任何写入，所以两个人的局部old都为0。屏障后每个人原子地写1，最后仍为1。

这里每次共享访问都使用原子接口，没有为了演示而执行普通变量的数据竞争；错误是把本应合并的“取旧值并加一”拆成两个原子操作。修复是使用单次原子读改写，或者用一把锁包住整个普通变量更新。不要把“没有数据竞争”误写成“业务逻辑一定正确”。

## 15. 多字段不变量为何不能只各自原子化

即使left和right分别变成原子整数，两次独立更新之间仍可能出现一边扣了、另一边尚未加的中间状态。如果观察者需要一致快照，就需要对完整协议另作安排。

本课优先用锁表达多字段规则。高级原子协议还涉及内存顺序、发布、对象回收等问题，不能把一个原子计数例子推广为任意结构都能无锁正确。volatile sig_atomic_t是第15章特定信号通知模式，也不替代这里的线程同步。

## 16. 重复运行能检查什么

在本批Bash目录运行：

```bash
for i in {1..20}; do ./mutex || break; done
for i in {1..20}; do ./atomic-split || break; done
```

前者应每次20000，后者每次1。这能检验所覆盖的执行与构建版本，不能穷尽所有交错。对正确性的解释还需要共享访问表、锁范围、原子接口及生命期。

不要用删锁版本的稳定结果作“机器够好”的证据。程序可能在换优化选项、换CPU或轻微修改后表现不同，语言层面的错误早已存在。

## 18. 常见错误的修正方向

只锁写不锁读：列出所有访问，让冲突读也遵守协议，或移到全部join以后。

两把不同锁保护同一个counter：统一保护对象与协议，不能只看函数名都叫lock。

提前解锁再扣减：把检查和依赖它的更新保持在同一临界区。

持锁等待需要同一锁的另一个线程结束：会阻碍推进，第20章画等待图分析。

用pthread错误码规则检查原子返回旧值：回到每个接口的返回契约，不混套。

## 19. 练习、提示与参考答案

1. 三个工作者各加10000，有锁最终多少？答案30000；还要join全部三个。
2. 把整个10000次循环包在一对lock/unlock中，数值还对吗？答案可保持正确，但工作段基本串行；是否更快需实际测量，不能只数锁调用。
3. locked-pair为何不要求最终各100？答案是余额不足时会跳过，一方推进顺序影响成功转移次数；总和与非负才是声明的不变量。
4. atomic-split为何不算数据竞争？答案是共享计数全部用原子访问，屏障控制顺序；但多个原子步骤未形成整体加一。
5. 只把普通counter声明volatile能修复第3节吗？不能，缺少线程同步。

动手改造：在atomic-counter里把循环次数改为7、工作者仍为2，预期14。另在mutex正确版本中增加第三个工作者并join，预期30000。不要同时改保护规则与任务数，让验证目标保持单一。
