# 03 第一份 C 程序与编译

## 3.1 这一章只做一个很小的程序

我们先让电脑显示一行文字：

```text
Hello, operating systems!
```

它没有按钮，没有网页，也不保存数据库。选择这样小的任务，是为了清楚地看见“写文字文件 → 转换成可执行程序 → 运行 → 得到结果”这条路线。

本章会遇到三种东西：你编辑的C源文件hello.c、帮你处理源代码的工具gcc、生成后可以运行的程序hello。它们的名字很接近，但各自承担不同职责。分清这三者，比先记住所有编译选项更重要。

## 3.2 开始之前，确认环境和目录

打开Ubuntu，在Bash中执行。先检查编译器存在：

```bash
gcc --version
```

应出现版本信息。如果显示command not found，返回第02章准备工具，不要先改C程序。

给本章建立独立目录，避免把笔记和练习混在一起：

```bash
mkdir -p ~/os-lab/lesson03
cd ~/os-lab/lesson03
pwd
```

如果主目录是 `/home/learner`，最后应显示 `/home/learner/os-lab/lesson03`。接下来的文件创建、编译与运行，都在这个目录完成。中途重新打开终端时，先重新执行cd和pwd。

**这里输入的是Bash命令。** 下一节的C代码要保存进文件，不要直接把 `int main(void)` 等内容粘贴到Shell提示符后面。

## 3.3 用nano创建文件：从打开到保存

在Ubuntu终端输入：

```bash
nano hello.c
```

nano会打开文字编辑区域。如果文件还不存在，它准备创建名为hello.c的新文件；如果已存在，先查看里面是否是自己的本章练习，再决定编辑。

把3.4节的完整程序输入或粘贴进去。为减少输入法问题，代码标点切到英文状态，文字先用教材里的英文。你不需要输入网页代码块上方的语言标签c，也不需要输入包围代码的三条反引号。

输入完成后，按下面顺序操作：

1. 按住Ctrl，再按字母O，然后松开。这是nano的写入/保存操作。字母O不是数字0，也不需要为了大写再按Shift。
2. 底部出现文件名确认时，检查是hello.c，按Enter确认。
3. 看见保存反馈后，按Ctrl+X退出编辑器。
4. 确认再次回到Ubuntu的Shell提示符，再输入后面的终端命令。

nano底部可能把Ctrl显示成 `^`，因此 `^O` 表示Ctrl+O，不是输入脱字符和字母O。不同版本和语言的提示文字可能不同，关键动作是保存、确认文件名、退出。

如果Ctrl+X时询问是否保存，说明有尚未写入的修改；按提示选择保存并确认文件名，不要无意选择丢弃。也可以取消退出，先按前面的Ctrl+O流程保存。

## 3.4 第一份完整程序 hello.c

[完整源码：hello.c](示例代码/hello.c)

```c
#include <stdio.h>

int main(void) {
    printf("Hello, operating systems!\n");
    return 0;
}
```

先照着输入。文字前的缩进使用四个空格，帮助人看清结构；空白行只是把内容分开。不要把本节末尾的解释一起存进文件。

退出nano后，在Bash输入：

```bash
cat hello.c
```

终端应显示与上面一致的源代码。这个检查很有用：它直接读出实际保存的文件，不依赖你以为“刚刚已经存好了”。

如果看见空文件、内容少一半或文件不存在，先回nano或检查pwd与ls。源文件本身还没有准备好时，编译器不可能凭教材网页补齐它。

## 3.5 源代码：给人读，也要遵守规则

hello.c是普通文字文件，其中内容采用C语言规则书写。C文件通常使用.c扩展名；把普通文档改名成.c并不会自动使其成为正确程序。

编译工具会分析里面的结构。漏分号、括号不成对、使用未声明的名字，都可能让它不能按要求生成程序。因此编程中的标点不像日常作文那样可以随意替换。

例如英文双引号是 `"`，中文排版引号是“”。它们看起来接近，却不是相同字符。`()`、`{}`、`;` 也应使用代码里的英文半角形式。

初学时先保留教材格式。不要为了让代码“更紧凑”把所有行挤成一行，清楚的排版能帮你发现哪里属于同一组。

## 3.6 逐行理解：第一行 include 在准备什么

第一行是：

```c
#include <stdio.h>
```

`#include` 是给预处理阶段的指示，要求引入指定头文件提供的信息。“头文件”可以先理解为写有接口声明等内容的文件；“声明”告诉工具某个名字代表什么、如何使用。

stdio.h是C标准输入输出相关头文件，名字中的stdio来自standard input/output。后面用printf输出文字，需要相应声明。你不需要自己创建stdio.h，也不应该把这行改成 `#include <hello.c>` 试图修复问题。

两边的 `<` 和 `>` 在这一行界定头文件名，不是在进行数学上的大小比较。这一行不加结尾分号，因为它不是后面那种普通C语句。

stdio.h不会把整套操作系统复制进你的程序。它在这里提供编译需要的信息，printf的实现等由后续工具与库安排。可以暂时先记“使用这类标准输出能力，要引入对应头文件”，库与链接在3.15节再建立初步认识。

## 3.7 逐行理解：main、括号与花括号

接下来是：

```c
int main(void) {
```

**函数**是一段有名字、能够按约定完成某项工作的代码。以后你会自己写函数；现在先把main看作程序进入你所写主要逻辑的约定入口。

这一行逐个部分看：

| 部分 | 在本例中表达什么 |
| --- | --- |
| `int` | 这个函数返回一个整数类型的结果 |
| `main` | 入口函数的约定名字，大小写必须正确 |
| `(` 和 `)` | 包围参数说明的位置 |
| `void` | 这里明确表示main不接收参数 |
| `{` | 函数内部代码块从这里开始 |

文件最后的 `}` 结束main的代码块。花括号需要成对出现，里面的两条语句属于main。如果随手删掉一个括号，工具就可能无法判断结构。

这里“返回整数”不等于“必须把一个整数印在屏幕上”。返回给运行环境的结果与显示给人看的内容是两个通道，3.12节会做实验区分。

不必现在研究程序装载后所有初始化步骤。对本章而言，你需要知道自己的主要语句放在main里面，并能够找到它的起点与终点。

## 3.8 逐行理解：printf、字符串和换行

main里面第一条语句是：

```c
printf("Hello, operating systems!\n");
```

printf是我们使用的输出函数。写出函数名，后面接括号和所需内容，叫作调用函数：让它按约定完成工作。

英文双引号内的内容叫字符串，可以先理解为一段文字数据。这里要求输出Hello, operating systems!。引号用于界定字符串，不会自己作为文字的一部分出现。

字符串末尾的 `\n` 是换行转义写法。在源文件里，你键入反斜杠和字母n这两个字符，C规则把它们解释成一个换行字符。因此输出后光标会到下一行，不是显示一个反斜杠再显示n。

末尾的 `;` 结束这条语句。可以把普通语句看作“完成一个明确操作的一句程序话”，分号帮助工具知道这一句到哪里结束。它不等于所有行都必须机械加分号，include和函数花括号就有不同规则。

先不在输出文字里随意加入百分号。printf把百分号用于格式规则，后面学习数字输出时会专门解释；如果此时确实要输出一个百分号，需要写成两个百分号。第一份练习先用简单文字，集中理解完整过程。

## 3.9 逐行理解：return 0 与顺序执行

main里面第二条语句是：

```c
return 0;
```

return结束当前函数，并交回一个结果。main返回0，表示按本例约定正常成功结束。这个结果交给启动程序的环境，Bash可以取得它。

它不会自动在屏幕上显示数字0。显示文字由printf完成，返回状态由return完成。程序可以输出很多文字但返回失败，也可以没有文字却返回成功。

在本例中，执行顺序是：进入main → 调用printf → 执行return → 结束本次运行。假如在return后面继续放普通输出语句，运行流程不会因为它写在文件里就自动回头执行。

“文件里写了什么”与“运行时实际走过哪些步骤”是两个问题。后面条件和循环会让路径更丰富，但现在先掌握按顺序执行。

## 3.10 第一次编译与运行

确认已退出nano、当前在lesson03，输入下面这一整行Bash命令：

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic -g hello.c -o hello
```

先别被长度吓到。它只有一个输入文件hello.c和一个输出名字hello，其余是选择处理规则与提示行为的选项。

| 部分 | 作用 | 现在要注意什么 |
| --- | --- | --- |
| `gcc` | 调用编译工具 | 不是写进C文件的名字 |
| `-std=c17` | 选择C17语言规则 | 跟着本课使用同一规则 |
| `-Wall` | 打开一组常用警告 | 名字虽含all，也不表示开启全部警告 |
| `-Wextra` | 增加另一组有用警告 | 帮助发现可疑代码 |
| `-Wpedantic` | 加入一些标准规则相关诊断 | 初学阶段保持它开启 |
| `-g` | 保留调试信息 | 后续用调试器时有帮助 |
| `hello.c` | 需要处理的源文件 | 必须确实存在于指定位置 |
| `-o hello` | 指定输出文件名 | 字母o，不是数字0 |

正常成功时，这条命令通常没有文字输出，直接回到提示符。用 `ls` 检查，应该能同时看到hello.c和hello。hello.c是你写的源文件，hello是工具生成的可执行文件。

现在运行：

```bash
./hello
```

预期输出：

```text
Hello, operating systems!
```

紧接着输入：

```bash
echo $?
```

预期显示0。`$?` 是Bash中上一条命令的退出状态，echo把它显示出来。这里的 `$?` 属于Shell，不要写进C源文件。

必须紧接着检查：若你先运行ls再echo，就看到了ls的状态，而不是hello的状态。观察对象一旦变了，数字的含义也就变了。

## 3.11 为什么运行时要写 ./hello

句点 `.` 表示当前目录，`/` 是路径分隔，因此 `./hello` 明确要求运行当前目录的hello。

直接写 `hello` 时，Shell通常会按PATH等查找规则寻找命令，当前目录不一定在其中。你可能明明用ls看见了hello，却仍得到command not found。这时先使用明确路径，不需要通过扩大搜索范围绕过问题。

`./hello.c` 也不对：它指向源文件，不是本次生成的可执行程序。即使给源文件加执行权限，也不会把C文字自动编译成机器代码。

总结这三个操作的区别：`nano hello.c` 编辑源文件，`gcc ...` 生成程序，`./hello` 运行生成结果。每次都先问“我现在要做哪一个动作”，可以避免很多混淆。

## 3.12 实验一：把输出改成两行

这次不要只换一个单词，要练习一次完整的修改循环。先预测结果，再编辑hello.c，把整个文件替换为下面这个**完整程序**：

```c
#include <stdio.h>

int main(void) {
    printf("I am learning C.\n");
    printf("I can run my first program.\n");
    return 0;
}
```

用 `nano hello.c` 编辑，按Ctrl+O、Enter、Ctrl+X保存退出。然后先 `cat hello.c` 核对，再运行3.10节同一条完整编译命令，最后执行 `./hello`。

预期是两行，顺序与源码里的两条printf一致：

```text
I am learning C.
I can run my first program.
```

如果仍然看到旧的Hello, operating systems!，按顺序检查：真的保存了吗？cat读到的是新内容吗？刚刚的gcc命令是否成功？运行的hello是否在你刚编译的目录？

修改源文件不会自动改变已经生成的hello。你必须重新编译。源代码与生成结果是不同文件，这是本章最重要的操作习惯之一。

## 3.13 实验二：显示内容与退出状态是两回事

建立另一个源文件，避免把上一个实验混掉。在同一个lesson03目录运行 `nano status.c`，保存以下**完整程序**：

```c
#include <stdio.h>

int main(void) {
    printf("This program returns 9.\n");
    return 9;
}
```

编译与运行：

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic -g status.c -o status
./status
echo $?
```

程序运行时显示This program returns 9.；后面的echo才显示退出状态9。这个9表示我们在本实验里选择的非零状态，不是所有程序对9都使用同一种业务含义。

再把return改为0、重新编译，保留输出文字不变。现在程序仍会打印原句，但echo显示0。这正说明：字符串说了什么，与程序实际返回什么，并不会被工具自动核对成一致。

正常教学程序通常用0表示成功，失败情况按接口约定使用非零值。后面编写文件工具时会用它把成功与失败告诉调用者。

## 3.14 实验三：故意制造一个可理解的编译错误

排错也是学习的一部分。用 `nano broken.c` 保存下面这个**故意写错的完整文件**，不要拿它覆盖已经工作的hello.c：

```c
#include <stdio.h>

int main(void) {
    printf("Can you find the missing symbol?\n")
    return 0;
}
```

运行：

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic -g broken.c -o broken
```

printf行结尾少了分号。GCC应报告编译失败，常见诊断包含“expected”和“;”，并指出某个位置。具体措辞与版本有关，不要求与你教材中的文字一模一样。

诊断可能指向下一行return附近，因为工具读到这里才确定前面的结构接不上。**报错位置是排查起点，不保证错误恰好就在该字符上。**

回到broken.c，在printf行末加上分号，保存，重新编译。只有修好并成功生成后，才运行 `./broken`。它应显示Can you find the missing symbol?。

这次请完整记录四项：出错命令、第一条诊断、实际漏写位置、修复后结果。这样练习的是定位原因，不是随机增删标点直到提示消失。

## 3.15 编译、链接与运行：先画一条路线

你还不必阅读汇编，也可以先建立大致路线：

```mermaid
flowchart LR
A[C源文件] --> B[预处理与编译]
B --> C[汇编产生目标文件]
C --> D[链接为可执行文件]
D --> E[系统启动为运行实例]
```

预处理处理include等指示；编译把C结构转换为目标代码所需的表示；汇编产生目标文件；链接把需要的目标代码等组合成可执行结果。平时这条gcc命令驱动多个步骤，所以我们常把整个过程统称为“编译”。[GCC处理阶段说明](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)

“库”可以先理解为已经准备好、供程序使用的一组实现。我们调用printf，不必自己从设备输出开始重新写一遍。头文件中的声明让工具知道怎样调用，实际实现的组合与运行还涉及链接和运行环境。

上面这张图已经是简化版，不意味着任何机器都按同一个固定地址装入代码。对于第一章的联系，你现在应该看到：文件准备好后，还需要操作系统建立运行实例，并在执行过程中提供所需服务。

## 3.16 错误排查：按阶段找原因

| 现象 | 先排查哪里 | 具体动作 |
| --- | --- | --- |
| `gcc: command not found` | 环境工具 | 回第02章确认安装与所处系统 |
| `hello.c: No such file or directory` | 路径与文件名 | pwd、ls、cat hello.c，检查大小写 |
| 提示缺少分号、括号等 | 源文件结构 | 从第一条诊断附近往前读，核对成对符号 |
| gcc报错后，旧hello仍能运行 | 旧生成文件 | 不把旧程序输出当作新代码编译成功 |
| 输出仍是旧文字 | 保存与重新编译 | cat实际源文件，确认编译目录与运行目录 |
| 出现 `Permission denied` | 对象与权限 | 先确认运行的是hello，不是hello.c |
| 屏幕显示很多文字但echo非零 | 程序返回状态 | 看return与失败路径，文字不等于成功 |
| 中文引号造成奇怪诊断 | 输入字符 | 改回英文半角，不只看视觉形状 |

警告warning和错误error也有区别：警告提示可疑点，工具仍可能生成程序；错误通常使相应步骤失败。不要为了安静把警告选项删掉，要先理解它指出什么。本章的正确例程应能在所给选项下不产生警告。

以后熟悉Shell后，可以用 `&&` 连接“前一步成功才执行后一步”。目前先逐条执行、确认编译成功，再运行，不需要为了少打一行而增加没理解的符号。

## 3.17 三个容易漏掉的细节

**没有换行会怎样？** 把字符串末尾的反斜杠n暂时去掉，程序仍可打印文字，但下一次提示符可能紧接在后面，看起来像粘成一行。这是输出格式变化，不一定是程序崩溃。练习后恢复换行。

**空白行和缩进都能删吗？** 本例很多空白用于可读性，不直接改变运算；但不能因此把所有空格都删掉。例如int与main需要按正确词法分隔，字符串里的空格也是实际内容。先保持清楚格式，再逐步理解哪些是结构、哪些是排版。

**注释是什么？** 注释是写给阅读代码的人看的说明，普通语句里的字符串输出和注释不同。例如在main中加入 `// print a greeting` 作为单独一行，是说明，不会自己显示到终端。注释也不能替代需要执行的语句。

## 3.19 参考答案与思路

练习一的完整思路：包含stdio.h，定义 `int main(void)`，在花括号内调用printf输出指定文字和换行，return 0。保存为一个.c文件，编译时指定对应输出名，再运行那个生成文件。

练习二：按main内的先后顺序执行，交换后先Second再First。只修改源码但没有重新编译，不会让旧生成文件按新顺序执行。

练习三：在Ubuntu Bash中运行程序后，立即执行 `echo $?`，应为5；若先运行ls，拿到的就不是同一次程序状态。非零值的具体含义由程序约定。

练习四：旧可执行文件没有被重新生成，通常仍执行旧逻辑。正确工作循环是“编辑 → 保存 → 核对 → 编译成功 → 运行验证”。

练习五：先确认有没有成功生成hello、是否仍处于生成目录；再区分直接写hello与明确路径 `./hello` 的查找方式。只有源文件存在，不代表可执行文件已经存在。
