## 33.1 三种“看起来独立”

虚拟机通过虚拟化硬件环境运行客户操作系统，客户通常有自己的内核。容器主要通过共享宿主内核下的隔离与资源管理机制提供独立视图。WSL 是 Windows 提供 Linux 环境的产品家族，WSL 2 使用 Linux 内核与轻量虚拟化环境；不能把所有 WSL 版本都归为同一种实现。

| 对比点 | 虚拟机 | Linux 容器 |
| --- | --- | --- |
| 内核 | 客户系统一般独立 | 通常共享运行容器的 Linux 内核 |
| 隔离基础 | 虚拟硬件、虚拟化层等 | 命名空间、权限、安全与资源机制等 |
| 启动和资源 | 通常较多系统初始化 | 通常围绕应用进程启动 |
| 兼容边界 | 可运行不同客户系统 | 需遵守共享内核接口边界 |

“通常”很重要：Windows 上运行 Linux 容器时，背后可能还有 Linux 虚拟机。产品组合不能仅凭界面像一个终端就判断。

## 33.2 视图隔离与资源限制

命名空间为进程提供不同的 PID、挂载、网络等视图；cgroup 等机制用于资源计量与限制。只改变可见 PID 不会自动限制 CPU、内存或文件权限。容器内看到 PID 1，也不能据此推断它是物理机器的第一个进程。

容器仍可能通过挂载、特权、设备或内核漏洞影响宿主。不能把容器当作无条件安全边界，也不能以“共享内核”为理由认为隔离毫无价值。需要根据威胁模型选择限制组合。

## 33.3 不额外安装的观察

在 Windows PowerShell 使用 `wsl --list --verbose` 确认版本；在 Ubuntu 使用 `uname -r`、`ps -p 1 -o comm=`、`cat /proc/self/cgroup`。输出取决于当前环境，不要求你为本课安装 Docker 或再建虚拟机。

对比 Windows 的 C 盘路径与 Ubuntu 的 `/`，解释两种路径视图怎样相互访问。不要把 WSL 对挂载 Windows 文件的行为当作所有 Linux 原生文件系统的完整代表，权限与性能可能有环境差异。

## 33.4 练习、答案与完成条件

①容器镜像里有很多用户空间文件，就一定有独立运行的内核吗？②命名空间能代替内存配额吗？③WSL 2 中能运行 Linux fork 实验，就说明 MinGW 也有相同接口吗？

答案：①不是；②不能，视图与资源限制不同；③不能，宿主平台与工具链不同。实验可移植性必须按目标接口验证。

完成条件：为自己的实验环境画出“Windows → WSL 2 虚拟化环境 → Linux 内核 → Bash/C 程序”关系；已有原生 Linux 的学习者画对应更短路径。
