# 33 虚拟机、容器与 WSL

> **零基础详细版 · 已重写。** 先修：进程、地址空间、文件路径、第30—32章。建议7—10小时。沿用已有Linux环境，不要求安装Docker、创建虚拟机或修改系统资源配置。

## 33.1 学习目标：分清三个不同问题

打开一个终端，里面都有`/`、Bash和`gcc`，并不意味着底下实现相同。本章用三个问题分析环境：谁提供内核？进程能看见哪些对象？资源消耗受到什么限制？学完应能为自己的环境画层次图，并把每项结论对应到证据。

不要把“虚拟机”“容器”“WSL”当作互相排斥的三个盒子。产品可以组合这些机制，例如Windows中先有Linux虚拟化环境，再在其中运行Linux容器。先理解层次，再认识产品名称。

## 33.2 先复习普通进程已有的隔离

普通进程通常已经有自己的虚拟地址空间、fd表和执行状态。这使两个程序使用相同数值的虚拟地址时，不必指向同一物理页面。普通`fork`也会创建新进程，但不会自动为它创建一个独立运行的内核。

因此“我的程序独立运行”与“我拥有一个完整客户操作系统”是两件事。第21章的地址空间边界、第31章的权限边界仍然适用；虚拟化和容器在这些基础上增加或组合不同机制。

## 33.3 虚拟机：让客户系统看到一套机器环境

**虚拟机**为客户系统提供虚拟化的执行和硬件环境，由虚拟机监控器等机制管理。客户操作系统通常有自己的内核，使用虚拟CPU、内存与设备接口；宿主与客户是相对当前层次的称呼。

“虚拟”不表示里面的计算没有真的执行。程序仍消耗处理器、内存和存储资源，只是访问路径经过虚拟化安排。虚拟磁盘常由宿主上的文件或其他存储后端承载，但不能因此把它理解成客户每次`write`必然对应宿主同一个位置的一次写入。

## 33.4 客户内核和宿主内核如何区分

假设物理机运行系统H，虚拟机里运行系统G。G里的用户程序向G的内核请求`read`；G的驱动可能进一步访问虚拟设备，最终经宿主与真实硬件路径完成请求。这是层次关系，不是程序直接随意调用H的一切接口。

G可以安装适合自身的用户空间工具。能否运行某个二进制，还涉及处理器架构、ABI、库和系统接口，不能仅凭“放进虚拟机”就认为任意程序都兼容。模拟不同指令集又可能包含额外机制，本章不展开这些实现。

## 33.5 Linux容器：围绕进程组合边界

本章所说的普通Linux容器，通常是在已有Linux内核下，用命名空间、权限、文件系统安排和资源控制等机制，为一组进程提供受组织的运行环境。容器内有独立的用户空间文件布局，不等于每个容器都运行一份独立内核。

**容器镜像**主要是准备好的文件系统内容与运行配置等分发材料；**运行中的容器**则包括执行的进程与所配置的边界。镜像中有`/bin`、库和包管理器，只能说明有这些用户空间内容，不能据此断定存在独立启动的内核。

## 33.6 用比较表检查自己是否混层

| 问题 | 典型虚拟机 | 典型Linux容器 |
| --- | --- | --- |
| 谁提供客户程序所用内核 | 客户系统自己的内核 | 运行容器的Linux内核 |
| 基础组织方式 | 虚拟硬件与客户系统 | 受配置约束的进程组及视图 |
| 有无独立用户空间文件 | 通常有 | 通常也有 |
| 是否自动无限安全 | 不是 | 也不是 |
| 是否保证资源上限 | 取决于配置与其他层 | 取决于资源控制配置 |
| 是否一定更快 | 需要工作负载和测量 | 同样需要实际证据 |

表中“典型”很重要。还有结合虚拟机技术的容器运行方案等组合。判断实际系统要看实现与配置，不应把教学分类变成无法容纳现实产品的绝对标签。

## 33.7 命名空间：改变能看到的实例

Linux的**命名空间**为某类系统资源提供分组视图。PID命名空间影响进程编号与可见性，挂载命名空间影响挂载视图，网络命名空间涉及网络设备、协议栈及端口等视图，用户命名空间涉及用户与组ID映射等。

这不是把一份内核复制成很多份。可以类比一幢楼里不同房间各有自己的门牌表，但门牌表的变化本身不代表各自拥有独立发电厂。类比只帮助理解“视图不同”，不能替代不同命名空间的具体权限规则。

## 33.8 容器里的PID 1说明什么

同一个进程在不同层级PID命名空间里可能具有不同编号。在某个容器视图里看到PID 1，说明它在相应视图中的角色，不能直接推出这是物理主机的第一个用户进程。

同理，第30章的`ps -p 1`只观察当前可见环境。普通`fork`默认继承相应命名空间成员关系；创建新进程与创建新命名空间不是同一操作。本章只读取视图证据，不使用`unshare`等命令去建立或改变命名空间。

## 33.9 网络视图会改变“本机”的范围

第32章把TCP监听绑定在`127.0.0.1`。如果进程位于独立网络命名空间，“本机回环”通常属于该网络视图。另一个网络命名空间的同一地址，不会仅凭数字相同就自动连接到它。

跨容器或从宿主访问服务，常需要额外网络连接、路由、端口映射或代理安排。这里没有配置这些功能。所以回环实验通过的准确表述是“当前网络环境中的本机往返成功”，不能扩展成“所有容器与Windows浏览器之间都可访问”。

## 33.10 cgroup：组织与控制资源

**cgroup**是Linux用于按层次组织进程、计量并控制资源分配的机制。cgroup v2使用统一层次及相应控制器。CPU、内存、进程数量等限制各有具体接口与含义，并非只写一个“隔离=true”就全部完成。

命名空间主要回答看到哪个实例；cgroup等资源机制回答如何计量和限制消耗。两者不能互相替代。设置了内存上限也不表示磁盘空间、网络流量、fd数量都已自动得到同一数值的上限。

## 33.11 两个数字例子先手算

某CPU配额配置允许每100毫秒累计使用50毫秒CPU时间。这描述一个周期内的预算关系，不等于程序只运行在“第0.5个CPU”，也不能推出每个请求必然恰好慢两倍。多线程使用、其他负载和调度都会影响实际表现。本段是配额概念演算，不修改本机配置。

再设某组进程有128MiB内存限制，另一组有256MiB。它们看见相同的CPU名称，并不能推翻内存限制；命名空间也不能由此判断。读取一个进程的限制值还应考虑上级层次，局部未设上限不代表所有祖先都无限制。

## 33.12 rlimit与cgroup不要混成一个值

`rlimit`是一组进程资源限制接口。例如`RLIMIT_NOFILE`软限制约束可分配fd编号的范围，硬限制是软限制可调整的上界之一。它不是“机器当前打开了多少个文件”，也不是整个容器的总文件数量限制。

多个进程可以受到相同或不同的rlimit，同时还受cgroup与系统其他限制影响。只看到其中一个数字不足以推断所有可用资源。本章观察软限制而不提高或降低系统配置；后面的测试只在自己的子进程中验证观察结果可变化。

## 33.13 WSL 1与WSL 2的核心区别

WSL是Windows提供Linux环境的产品家族。依据Microsoft官方说明，WSL 2在受管理的轻量虚拟机中使用真实Linux内核；WSL 1采用不同的兼容实现，不是同样的一层独立Linux内核。不要把“WSL”三个字本身当作版本结论。

WSL 2中的发行版和用户空间运行在该Linux环境中，也有相应隔离安排；不能画成“每打开一个Bash窗口，就新建一台物理机”。Linux中的`uname`与Windows端的`wsl --list --verbose`回答不同问题，应该结合使用。

## 33.14 先在正确终端确认环境

仅对**已使用WSL的Windows学习者**，在**Windows PowerShell，任意目录**执行只读命令：

```powershell
wsl --list --verbose
wsl --status
```

列表中的VERSION列用于确认发行版采用WSL 1还是2，STATE描述当前运行状态。已有原生Linux学习者跳过本段；命令不可用时不要为了补截图立即安装新系统，先核对你实际使用的环境。

随后切到**Ubuntu/WSL的Bash，任意目录**：

```bash
uname -r
ps -p 1 -o comm=
cat /proc/self/cgroup
readlink /proc/self/ns/pid
readlink /proc/self/ns/net
```

`/proc/self`指向执行读取操作的那个进程，因此这里`cat`看到的是cat自身的记录，`readlink`看到的是readlink自身的视图；它们通常继承启动它们的Shell环境，但不要把self永远解释成Bash。

## 33.15 完整程序：观察视图与一项资源限制

保存为`view-probe.c`，Linux/POSIX环境。它只读三个命名空间链接与本进程fd软限制，没有可靠识别“是否容器”的万能判定逻辑。

**完整程序：view-probe.c**

```c
#include <stdio.h>
#include <sys/resource.h>
#include <unistd.h>

int main(void) {
    const char *paths[] = {
        "/proc/self/ns/pid", "/proc/self/ns/mnt", "/proc/self/ns/net"
    };
    const char *names[] = {"pid", "mnt", "net"};
    for (size_t i = 0; i < sizeof paths / sizeof paths[0]; ++i) {
        char target[256];
        ssize_t n = readlink(paths[i], target, sizeof target - 1);
        if (n < 0) { perror(paths[i]); return 1; }
        if ((size_t)n == sizeof target - 1) {
            fputs("namespace link may be truncated\n", stderr);
            return 1;
        }
        target[n] = '\0';
        if (printf("%s=%s\n", names[i], target) < 0) { return 1; }
    }
    struct rlimit limit;
    if (getrlimit(RLIMIT_NOFILE, &limit) < 0) {
        perror("getrlimit"); return 1;
    }
    if (limit.rlim_cur == RLIM_INFINITY) {
        if (puts("fd-soft=unlimited") == EOF) { return 1; }
    } else if (printf("fd-soft=%llu\n", (unsigned long long)limit.rlim_cur) < 0) {
        return 1;
    }
    return fflush(stdout) == EOF ? 1 : 0;
}
```

## 33.16 逐句解释readlink与结果

`paths`是三个字符串指针组成的数组，`names`提供对应标签。数组长度由`sizeof paths / sizeof paths[0]`计算；这里数组在当前作用域是真实数组，不是函数形参中退化后的指针。

`readlink`返回实际复制的字节数，**不会自动添加NUL**。程序预留一字节，检查可能截断，再执行`target[n] = '\0'`，然后才能按`%s`输出。若返回值恰好占满提供容量，本例保守拒绝，不把可能截断的文本当作完整证据。

命名空间链接常形如`pid:[数字]`。数字用于比较相应命名空间对象，在合适的同一内核和时间范围内分析；不要把两台机器偶然相同的数字当成共享内核的证明。资源限制单独标成`fd-soft`，没有从链接数字推导它。

## 33.18 文件路径、共享与真实限制

Windows的`C:\...`与Linux的`/...`是不同路径语法。WSL常能通过挂载路径访问Windows文件，但文件权限、大小写、性能及工具行为可能受挂载方式影响。第25—28章的Linux权限实验优先放在Linux个人目录；本批自动验证使用Linux临时目录。

虚拟机和容器可能通过共享目录把宿主文件暴露给内部进程。共享范围、是否可写和身份映射都会影响边界。看到“容器”标签不代表挂载进来的文件自动安全；看到“虚拟机”也不代表网络和共享目录已全部关闭。本章不更改共享或挂载配置。

## 33.19 练习、常见错误与参考答案

**A：** 镜像里有Ubuntu包管理器，所以运行时必有独立内核？**参考答案：** 不成立。用户空间文件与内核是不同层，普通Linux容器共享底层运行内核。

**B：** PID视图独立就等于内存限制已设128MiB？**参考答案：** 不等于。命名空间与资源限制回答不同问题，要查实际配置及上级约束。

**C：** 三个namespace链接值没变，能否证明没有使用虚拟机？**参考答案：** 不能。同一客户内核里的多个进程也可共享命名空间；这些链接不提供完整宿主层次信息。

**D：** 本例fd-soft为1024，是否表示机器只能同时存在1024个文件？**参考答案：** 不是。它是本进程相关的fd分配限制，不能替代系统总量或存储对象数量。

**E：** 常见错误是拿不同机器的链接数字作绝对身份、用`uname`猜WSL版本、用“感觉更快”评价虚拟化性能。改法是什么？**参考答案：** 固定比较范围、结合宿主官方命令、为具体工作负载设计测量。本章没有做性能基准。
