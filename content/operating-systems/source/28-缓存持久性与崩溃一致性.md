# 28 缓存、持久性与崩溃一致性

## 28.1 一次写入经过多层

应用的 C 流缓冲、内核页缓存、设备缓存是不同层。printf/fwrite 成功可能只代表写入流缓冲；fflush 把数据交给底层 I/O；write 成功也不自动表示掉电后必定可恢复。

fsync 要求同步指定文件的数据和相关元数据到存储设备，并报告失败。文件 fsync 不自动保证包含它的目录项也已持久化；创建、重命名等场景还可能需要同步目录。具体保证依文件系统、设备和平台接口而定。[fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)

## 28.2 原子可见与持久是两回事

同一文件系统上使用 rename 替换名字，常用于使读者看到完整旧版本或完整新版本；这与掉电后仍保留新名字是两种性质。跨文件系统 rename 也不能当作同样语义的原子替换使用。

典型的稳健保存设计是：在目标目录创建唯一临时文件 → 写完并检查短写 → fsync 临时文件 → 关闭并检查 → 同目录 rename → fsync 父目录。还要处理权限、并发写入、旧版本、失败清理和设备能力。

```text
写入失败：保留旧文件，报告失败
文件同步成功、替换前失败：旧名字仍有效，可能留下临时文件
替换后目录同步失败：新内容可见，但持久性结果需按平台处理
```

这是一份协议说明，不是可直接复制执行的完整程序。本课不通过真实断电或拔盘验收，也不把某次正常退出当作崩溃一致性的证明。

## 28.3 日志与写时复制

文件系统更新往往涉及多个块，例如分配位图、inode 与目录项。只写完一部分就崩溃，会留下不一致。日志机制先按协议记录更新意图或内容，恢复时重放/撤销相关部分；日志是否覆盖文件数据取决于模式，不能一概说“用了日志就不会丢内容”。

写时复制文件系统倾向先写新位置，再按协议切换引用；依然要考虑顺序、空间与恢复。应用自己的数据格式也可能需要事务或校验，文件系统一致不等于业务数据始终正确。

## 28.4 课堂演练

拿纸画旧内容 A、新内容 B、临时文件、目录项。分别在“写到一半”“文件同步后”“重命名后”“目录同步后”四个位置画崩溃线，回答恢复后允许看到什么，以及哪些结论需要平台保证。这里练的是推导协议，而非制造数据损坏。

练习：①fflush 与 fsync 可以互相替代吗？②rename 成功是否足以宣布掉电后数据必在？③日志保证每个业务事务都完成吗？答案：①不能，层次不同；②不足；③不保证，文件系统日志与应用事务边界不同。

完成条件：在报告中分别写“调用成功”“其他进程可见”“可持久恢复”，不给三个概念使用同一个模糊的“已保存”。
