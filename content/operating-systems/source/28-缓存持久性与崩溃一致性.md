# 28 缓存、持久性与崩溃一致性：把“保存了”拆成可以检查的承诺

> **零基础详细版 · 已重写。** 分清缓冲、可见、文件同步、名字发布与目录同步；先运行小型同步例程，再为综合保存项目建立失败状态表。建议8—11小时。

## 1. 为什么还需要这一章

第10章fwrite成功，第11章write写完，第24章共享映射看到新字节，它们都不自动回答：“突然崩溃以后，哪些内容仍能恢复？”

本章目标是把不同承诺分别命名，解释fflush/fsync/rename/目录同步的作用，推导失败发生在发布前后怎样报告。先会文件流、描述符、错误清理及第26章名字与对象。我们不会真的断电、拔盘或破坏用户文件。

## 2. 一次写入可能经过哪些层

```text
应用对象 → C流缓冲 → 内核页缓存/文件系统 → 设备相关缓存与存储
```

并非每种I/O都逐层使用完全相同路径，例如直接I/O、设备类型和文件系统有所不同。本课普通文件例程用这张图区分职责：库可能暂存格式化或文件流输出，内核可以缓存文件数据，设备还可能有自己的完成与写回策略。

成功返回的含义由对应接口规定，不是所有“写”字开头的函数都承诺相同层次。

## 3. 三种常被混说的成功

| 问题 | 可以用什么证据讨论 | 不能自动推出 |
| --- | --- | --- |
| 调用是否按接口完成 | 返回值、字节数、错误状态 | 其他人已经按需要看见 |
| 新版本是否已发布可查 | 按名字打开、发布操作成功 | 崩溃后名字必然保留 |
| 是否完成要求的同步协议 | 文件及必要目录同步成功 | 任意坏硬件、全部业务事务都安全 |

“已保存”若不说明是哪一项，就无法验收。下文会使用“写完”“发布”“同步完成”等更具体表述，不让一个绿色退出码替代所有结论。

## 4. fwrite和fflush负责哪一段

fwrite按元素数报告写入流的结果，小写入可能还停在库缓冲。fflush请求把待输出内容提交到底层，并能报告这一步的错误；fclose也可能在刷新或关闭时失败。

fflush不等于对设备执行持久同步。若使用FILE流再通过fileno取得fd进行fsync，应先检查fflush成功，避免只同步了内核已知内容、库里却还留着最后一段数据。

不能忽略写入数量，也不能在fclose失败后重复使用旧FILE对象。需要报错时保持错误来源与返回值紧邻，短写与负错误分别解释。

## 5. write成功也不等于抗断电

write返回正数表示相应数量已按接口接受，可能需要循环处理短写。普通文件写入常先更新内核缓存；稍后写回设备的错误，也可能在同步等后续接口才暴露。

因此既要检查写入循环，也要检查需要的fsync和关闭。反过来，fsync失败不表示可以随便重写原文件忽略旧版本；应用必须知道自己已经改变了哪些可见状态。

## 6. fsync请求什么

fsync请求将指定文件的相关内容与必要元数据同步到存储，并等待完成或报告错误。具体保证受到文件系统、设备、挂载和平台实现的约束。

它不是“刷新整个世界”的命令，也不自动同步所有其他文件。文件数据和承载名字的父目录是不同对象：新建、改名等目录项变化，可能需要另外对父目录同步。

本课在当前Linux本地文件系统实际调用这些接口，但正常返回不等于已经验证了掉电恢复。我们记录的是协议步骤与错误行为。

fsync也不是内容校验器。若程序把学习分钟写错了，或者生成了不完整的数据格式，同步成功仍可能只是把错误内容按请求同步。发布前要完成业务校验，保存协议负责另一类问题，不能用其中一项替代另一项。

## 7. 完整程序：流刷新后同步文件

平台Linux/WSL Ubuntu，Bash目录`~/os-lab/files`，lab.h同目录。

**完整程序：sync-stream.c**

```c
#include "lab.h"

static int sync_retry(int fd) {
    while (fsync(fd) < 0) {
        if (errno != EINTR) { return -1; }
    }
    return 0;
}
int main(int argc, char *argv[]) {
    if (argc != 2) { fputs("usage: sync-stream NEW_FILE\n", stderr); return 2; }
    FILE *file = fopen(argv[1], "wx");
    if (file == NULL) { die("create new stream"); }
    const char text[] = "version=1\n";
    int failed = 1;
    if (fwrite(text, 1, sizeof text - 1, file) != sizeof text - 1) {
        fputs("could not write complete version\n", stderr); goto cleanup;
    }
    if (fflush(file) != 0) { perror("fflush"); goto cleanup; }
    int fd = fileno(file);
    if (fd < 0) { perror("fileno"); goto cleanup; }
    if (sync_retry(fd) < 0) { perror("fsync file"); goto cleanup; }
    failed = 0;
cleanup:
    if (fclose(file) != 0) { perror("fclose"); failed = 1; }
    if (!failed) { puts("file_sync_completed"); }
    return failed;
}
```

编译：

```bash
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror -g sync-stream.c -o sync-stream
./sync-stream sync-new.txt
cat sync-new.txt
```

预期报告file_sync_completed，文件为version=1加换行。重复同名拒绝覆盖。wx是本课C17环境支持的排他创建模式，前面文件课已用过同类契约。

## 8. 这份程序还没有承诺什么

它同步了文件，没有同步父目录的新名字，所以输出特意只叫file_sync_completed。失败时新文件可能已存在、含部分内容；它没有实现“只有全部成功才让目标名字出现”的发布协议。

实验只用新文件名，旧文件不会被它覆盖。需要更新一个已有版本时，不要机械把wx换为w后称为稳健保存：w通常一打开就截断旧内容，后续失败可能让旧版本已经丢失。

## 9. 为什么用新对象准备版本

假设旧note.txt内容A，希望更新为完整B。直接截断原对象再写B，读者可能看到空文件或半份B；中途失败也很难保留A。

另一种设计是在同一目录建立新临时对象，先把B写完整并同步，然后一次改变目标名字关联。准备阶段失败时可以清理临时对象，旧note.txt仍指向A。

这能把发布边界收窄，但不自动解决多个写者冲突、权限继承、版本历史或所有设备故障。每种额外需求仍需独立协议。

## 10. rename提供的是名字替换语义

在支持相应语义的同一文件系统中，rename可将临时名字替换目标名字。正常并发查找不会因为“先删目标再改名”的用户代码窗口而暂时看不到目标。

这讨论的是运行中的名字可见性，不等于已经证明崩溃后必有新名字。跨文件系统rename会受到限制，某些Shell移动工具可能改为复制再删除，不能把那种流程当成同样的原子发布。

本批项目让临时名和目标名都相对于同一个目录fd，因此不跨目录树去猜是否属于同一文件系统。

## 11. 已打开读者与后来读者

rename替换目录项后，已经打开旧对象的fd通常继续引用旧版本；后来按目标路径打开者得到新对象。读者不是在同一fd上自动切换版本。

旧对象的其他硬链接也不会神奇地变成新内容。若你本来希望更新所有硬链接看到的同一对象，这和“发布新对象替换一个名字”是不同需求。第26章的四层图在这里直接决定产品行为。

## 12. 常见保存顺序逐步解释

1. 打开自己控制的目标目录，建立不会覆盖已有临时名的新文件。
2. 循环写完整新内容，检查短写与错误。
3. 同步临时文件，确认该请求成功。
4. 关闭临时fd并检查结果。
5. 同目录rename发布到目标名字。
6. 同步目录，再报告协议完成。

这是一种Linux本地文件保存设计入口，不是跨所有平台的万能模板。目录同步不支持或设备不提供相应保证时，不能静默假装成功。综合代码会把步骤与状态对应起来。

## 13. 发布前失败怎样处理

写入、文件同步、关闭或rename以前失败，目标名字尚未被本次发布改变。清理自己创建的临时名，关闭持有的资源，报告失败；若清理也失败，额外报告残留，不能掩盖最初错误。

这里假定旧版本已按原有要求建立，目录由自己控制，没有另一个写者同时替换目标。网络文件系统可能存在“服务器已执行但客户端见到错误”等额外情况，本课项目不声称覆盖这种远端不确定性。

## 14. 发布后同步失败怎样报告

rename成功以后，新内容已经可以按目标名查到。随后目录fsync失败，不能回报成“旧版本肯定还在”；也不应随手删除新目标当作回滚，因为没有保存旧对象供恢复。

本批项目选择退出3表示发布后又发生错误，并打印具体阶段；退出1表示发布以前失败；0表示要求的调用顺序已成功。状态码是项目协议，不是操作系统通用常量。

这让调用者知道应检查当前可见版本与错误，不会在界面上只显示一个模糊“保存失败，原文未改”。

例如业务操作是“学习分钟增加1”：若发布已经发生而后续同步失败，不能不加判断就把业务操作再做一次，否则可能重复加1。应用级重试应结合当前版本或操作标识判断；这与对一次明确未完成的系统调用重试EINTR不是同一个层次。

## 15. 崩溃线怎么画才不超出证据

| 停止位置 | 正常运行到此时的可见性 | 对崩溃恢复能说什么 |
| --- | --- | --- |
| 临时写一部分 | 旧目标仍指原对象 | 需结合原版本和平台保证 |
| 临时文件同步后 | 旧目标未发布改变 | 新临时名字自身未必已持久 |
| rename之后 | 新目标已发布 | 目录尚未同步，恢复结果依平台 |
| 目录同步成功后 | 新目标可见且同步协议完成 | 仍以设备/文件系统兑现保证为前提 |

不把所有中间崩溃都武断归为“必定旧或新，绝不会缺失”，除非相应平台确实给出所需恢复保证。本课不会通过断电来验证这张表。

## 16. 文件系统一致与业务一致

文件系统可能要同时更新分配信息、inode与目录项。只完成部分更新会留下结构不一致，因此需要恢复协议。**日志journaling**按规则记录更新，使恢复能够处理某些未完成步骤；记录元数据或文件数据的范围依模式而异。

**写时复制文件系统**倾向先写新位置，再按顺序切换引用，也需要处理提交、空间和恢复。它不是第21章fork COW的同一个具体接口，只是共享“先保留旧、修改另处”的部分思想。

结构可恢复不保证你的两个业务文件已经同步更新，例如余额记录和索引可能仍处于不同版本。应用格式可能还需事务、版本号和校验。

## 17. 正常测试与故障模拟能证明什么

正常运行验证内容、可见性和调用结果；包装器可以定点让write/fsync/close/rename失败，验证旧版本是否保留、资源是否清理、发布后状态是否如实报告。

这些是程序协议测试，不是模拟真实断电、电池耗尽、固件缓存或文件系统恢复全过程。记录中会把“注入一次EIO”与“真实设备坏了”分开，不能用前者替代后者。

## 18. 常见误解与排错

fflush成功就抗断电：先区分库到内核与存储同步。

rename成功就全部持久：还要看目录及平台要求。

同步失败后直接再报旧版本未变：先判断发布是否已发生。

为了完整文件先删目标：引入目标缺失窗口，应使用相应替换接口。

用文件系统日志替代业务事务：明确日志覆盖范围和应用提交边界。

不检查close，因为之前写过了：延迟错误仍要报告，且不能重用已消费句柄。

## 19. 练习与参考答案

1. sync-stream打印成功，是否已同步新名字的父目录？没有，所以它不作该承诺。
2. 临时文件写失败，如何保留旧目标？在发布前收尾临时对象，不截断旧对象。
3. rename成功、目录fsync失败，应报告哪一类？发布后错误，本项目为3，新版本可能已经可见。
4. 老fd为何仍可读旧版本？它引用旧对象，不按每次read重新找路径。
5. 将临时文件放另一个挂载点是否仍可直接按同样rename协议？不能据此保证，可能跨文件系统失败。

纸面练习：画A、B两个对象与目标/临时名字，逐步标出文件同步和目录同步；每一处错误写“目标是否已发布改变”，不只写“失败”。
