## 20.1 两把锁造成的环

线程 T1 持有 A 等 B，T2 持有 B 等 A，双方都无法继续。死锁与程序只是暂时慢不同：在现有资源释放协议下，环里的参与者无法自行推进。

| 必要条件 | 在两锁例子中的表现 |
| --- | --- |
| 互斥 | 一把锁一次只有一个持有者 |
| 持有并等待 | 拿着 A 时仍等待 B |
| 不可抢占 | 外部不能安全强夺该线程的锁 |
| 循环等待 | T1→B→T2→A→T1 |

四条件是经典资源死锁分析框架；真实锁、I/O 和消息等待也要建立相应模型。不要用重启进程替代对等待环的解释。

## 20.2 用统一顺序破坏循环

规定所有线程先 A 后 B。T1 拿到 A 时，T2 只能在 A 前等待，不能已经拿着 B 等 A，环就断了。解锁通常逆序。跨多个账户等动态资源，可以按稳定编号排序后加锁。

```c
/* 设计片段：所有相关调用者必须遵守同一顺序 */
thread_check(pthread_mutex_lock(&a), "lock a");
thread_check(pthread_mutex_lock(&b), "lock b");
/* 同时保护的状态修改 */
thread_check(pthread_mutex_unlock(&b), "unlock b");
thread_check(pthread_mutex_unlock(&a), "unlock a");
```

这段不是独立程序，需要已有 a/b 声明与完整的错误、资源协议。不要为了演示而运行故意永久等待的程序并把“终端卡住”当唯一证据。

## 20.3 超时、活锁与饥饿

超时可让程序报告失败并释放已有资源，但不自动完成业务恢复；强行解别人的锁会破坏数据。trylock 失败就双方同时放手再同时重试，可能一直互相让路，叫活锁。某个线程长期得不到机会则可能是饥饿。随机退避或公平策略要结合系统约束设计。

银行家算法把最大需求、已分配和可用资源放入模型，判断是否存在让全部任务依次完成的安全序列；不安全状态不等于已经死锁。比如有 3 份同类资源，T1/T2 各持 1、各最多需 2，可用 1，先给任意一个完成即可；若可用 0 且双方都必须再得 1 才释放，就需进一步分析等待条件。

## 20.4 并发复盘流程

对第 19 章写一张表：共享变量 slot/full/done/total，保护它的锁，哪个线程读写，何时通知，退出后谁销毁。确认所有等待都允许另一个参与者推进；确认线程失败或任务结束时还能唤醒等待者。学习版 thread_check 遇不可恢复错误直接退出整个进程；生产程序通常需更细致地传播失败和清理。

## 20.5 练习与答案

①T1 持 A 等 B，T2 仅在等 A、没有持 B，能直接断言死锁吗？②为何 sleep 不能修复两锁反向顺序？③条件变量等待是否会一直占住互斥锁？

答案：①不能，还要确认 B 持有者和推进路径；②时机改变不消除可能的等待环；③wait 在等待期间释放锁，恢复后重新取得。

完成条件：为一个具体并发例子画等待图，提出可以验证的破环方法，并说明该方法对所有参与者的约束。
