# 20 死锁与并发设计：沿等待关系找出不能推进的环

> **零基础详细版 · 已重写。** 用纸面等待图与有限模型分析死锁，运行统一锁顺序和非阻塞探测，不故意挂起程序当作演示。建议8—11小时。

## 1. 为什么有锁还会出问题

第18章解决冲突访问，第19章解决等数据和空位。但“每处都加了锁”不保证整个程序能结束：A拿着别人需要的资源，又等待别人释放另一个资源，就可能相互堵住。

学完应能画具体等待图，识别互斥、持有并等待、不可抢占和循环等待，设计所有参与者一致遵守的锁顺序，区分死锁、活锁、饥饿以及不安全状态。先修是第17—19章，不需要先写复杂系统。

## 2. 慢、等待与死锁怎样区别

一个消费者等生产者下一条数据，生产者仍能继续生成，这是正常等待。一个线程计算量大，仍在前进，是慢。**死锁**表示一组参与者按现有资源与释放规则相互等待，组内无法自行推进。

只看到“终端没输出”不能判断死锁。可能是缓冲、阻塞输入、未来任务没到、无限循环，或者确实有等待环。先列出每个人持有什么、想要什么、谁能使条件改变，再作结论。

本章不靠sleep制造永久卡住的进程；需要错误路径证据时，用有限状态模型或不会阻塞的探测接口。

## 3. 两把锁的经典交错

这是**错误协议的概念演算，不是待运行程序**：

| 步骤 | 线程T0 | 线程T1 |
| --- | --- | --- |
| 1 | 成功取得A | |
| 2 | | 成功取得B |
| 3 | 持A请求B，等待 | |
| 4 | | 持B请求A，等待 |

T0只有得到B才能做完并放A；T1只有得到A才能做完并放B。两边释放都依赖对方先推进，形成环。多加一秒延时可能让某次没走到这个交错，却不消除它的可能性。

## 4. 等待图把依赖写出来

**等待图**以参与者为点，箭头T0→T1表示T0正在等待T1持有的资源。上表得到T0→T1→T0。

对于本章每把锁只有一个持有者、等待成功获取、没有外部撤销的模型，环直接揭示互相等待。分析多实例资源、可取消等待、超时或其他释放协议时，需要更完整模型，不能把任何图中的一个圆圈都叫做已死锁。

问“T1在等A”还不够，必须问“T1是否也持有T0需要的B”。若B空闲，T0仍能取得它完成，随后T1就有机会继续。

## 5. 四个必要条件逐个对照

| 条件 | 本例中的具体事实 | 可考虑的破坏方向 |
| --- | --- | --- |
| 互斥 | 一把mutex同一时刻一个持有者 | 适合的任务改用不可变数据或独立分区 |
| 持有并等待 | 持A继续等B，另一方反过来 | 一次获取所需资源，或失败先归还已有资源 |
| 不可抢占 | 不能安全夺走别人的普通锁 | 设计可撤销操作，不能强行unlock别人 |
| 循环等待 | 彼此持有所需资源 | 为所有锁规定一致顺序 |

这是经典资源死锁框架。实际修改要结合业务，例如“把所有锁都删掉破坏互斥”会引入数据竞争，不能算正确修复。需要同时保持安全性和推进能力。

## 6. 用统一顺序排除环

为锁分配稳定编号A=0、B=1，所有需要两把锁的路径都先0后1，最后反向释放。T0若已拿0，T1只能先在0前等待，不能先拿1再回来等0。

证明思路是：线程持低编号锁时只继续等待更高编号。若存在一圈等待，就要求编号沿圈严格增加，最后又回到原编号，这是不可能的。因此统一顺序排除这一类循环等待。

前提是**所有相关路径**都遵守规则，包括异常处理、回调和辅助函数；只把最容易看到的一段改好不够。锁排序用明确的资源ID，不靠比较两个无关对象的指针大小来发明可移植顺序。

## 7. 完整实验：双向转移但锁顺序一致

Linux/WSL Ubuntu的Bash，目录`~/os-lab/concurrency`，lab.h同目录。

**完整程序：ordered-transfer.c**

```c
#include "lab.h"
#include <pthread.h>

struct Account { int balance; pthread_mutex_t lock; };
static struct Account accounts[2] = {
    {100000, PTHREAD_MUTEX_INITIALIZER},
    {100000, PTHREAD_MUTEX_INITIALIZER}
};
struct Move { int from; int to; };

static void transfer_one(int from, int to) {
    if (from == to) { return; }
    int first = from < to ? from : to;
    int second = from < to ? to : from;
    thread_check(pthread_mutex_lock(&accounts[first].lock), "lock first");
    thread_check(pthread_mutex_lock(&accounts[second].lock), "lock second");
    if (accounts[from].balance > 0) {
        accounts[from].balance--;
        accounts[to].balance++;
    }
    if (accounts[0].balance < 0 || accounts[1].balance < 0 ||
        accounts[0].balance + accounts[1].balance != 200000) {
        fputs("transfer invariant broken\n", stderr);
        exit(EXIT_FAILURE);
    }
    thread_check(pthread_mutex_unlock(&accounts[second].lock), "unlock second");
    thread_check(pthread_mutex_unlock(&accounts[first].lock), "unlock first");
}
static void *move_many(void *arg) {
    const struct Move *move = arg;
    for (int i = 0; i < 10000; i++) { transfer_one(move->from, move->to); }
    return NULL;
}
int main(void) {
    struct Move moves[2] = {{0, 1}, {1, 0}};
    pthread_t workers[2];
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_create(&workers[i], NULL, move_many, &moves[i]), "create");
    }
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_join(workers[i], NULL), "join");
    }
    printf("balances=%d,%d total=%d\n", accounts[0].balance, accounts[1].balance,
           accounts[0].balance + accounts[1].balance);
    for (int i = 0; i < 2; i++) {
        thread_check(pthread_mutex_destroy(&accounts[i].lock), "destroy");
    }
    return 0;
}
```

编译运行：

```bash
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror -g -pthread ordered-transfer.c -o ordered-transfer
./ordered-transfer
```

预期`balances=100000,100000 total=200000`。双方各转10000次，初值足够，任何一方最差只净流出10000，不会因为余额不足跳过。它与第18章初值100、允许跳过的例子不同，预期结果也应重新推导。

## 8. 转移方向不等于加锁方向

T0做0→1，T1做1→0，但它们都先锁账户0，再锁账户1。`from/to`决定改哪一笔数据，`first/second`决定取得资源的顺序，不能为了代码“顺手”把两者混用。

`from == to`直接返回，避免同一普通mutex重复加锁。参数只来自固定有效索引0与1；它不是接受任意外部账户ID的通用函数。真实业务还需范围、金额、溢出、事务和持久化等设计，本例只验证并发不变量及锁顺序。

## 9. 非阻塞探测不等于强行夺锁

`pthread_mutex_trylock`尝试取得锁，若当前不可取得可返回EBUSY，而不一直等待。失败时没有取得锁，不能继续访问受保护状态，也不能替别人unlock。

**完整程序：trylock-probe.c**

```c
#include "lab.h"
#include <pthread.h>

static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static void *probe(void *arg) {
    int *observed = arg;
    *observed = pthread_mutex_trylock(&lock);
    if (*observed == 0) {
        thread_check(pthread_mutex_unlock(&lock), "unlock probe");
    }
    return NULL;
}
int main(void) {
    thread_check(pthread_mutex_lock(&lock), "lock main");
    int observed = 0;
    pthread_t worker;
    thread_check(pthread_create(&worker, NULL, probe, &observed), "create");
    thread_check(pthread_join(worker, NULL), "join");
    thread_check(pthread_mutex_unlock(&lock), "unlock main");
    printf("busy=%d\n", observed == EBUSY);
    thread_check(pthread_mutex_destroy(&lock), "destroy");
    return observed == EBUSY ? 0 : 1;
}
```

编译为trylock-probe，预期busy=1。main在探测期间始终持锁，worker只做立即返回的trylock，所以不靠时机碰EBUSY。这里持锁join是这个受限探测的刻意安排：worker不会阻塞等待该锁。不要把它照搬到实际需要阻塞lock的工作函数。

## 10. join也可能成为等待环的一条边

如果main拿着A后join worker，而worker必须先lock A才能完成，main等worker结束，worker等main释放A，也形成无法推进的环。

第9节之所以能结束，是因为worker在忙时直接返回，不要求获得A。分析依赖应该看具体等待语义，而不是看到join就一律判死锁，或看到没有两把mutex就断言不会死锁。

相同道理也适用于管道和队列：生产者等空间、消费者尚未创建；消费者拿着队列锁等额度、生产者需要该锁才能提供额度；这些都需要把推进关系画全。

## 11. 可执行的等待图模型

**完整程序：deadlock-model.c**

```c
#include <stdio.h>

static int has_cycle(const int owner[2], const int request[2]) {
    for (int start = 0; start < 2; start++) {
        int seen[2] = {0, 0};
        int current = start;
        while (current >= 0) {
            if (seen[current]) { return 1; }
            seen[current] = 1;
            int wanted = request[current];
            current = wanted < 0 ? -1 : owner[wanted];
        }
    }
    return 0;
}
int main(void) {
    const int opposite_owner[2] = {0, 1};
    const int opposite_request[2] = {1, 0};
    const int ordered_owner[2] = {0, 0};
    const int ordered_request[2] = {-1, 0};
    printf("opposite_order_cycle=%d\n", has_cycle(opposite_owner, opposite_request));
    printf("ordered_state_cycle=%d\n", has_cycle(ordered_owner, ordered_request));
    return 0;
}
```

编译为deadlock-model，预期先1后0。owner按资源索引保存持有者，request按线程索引保存等待的资源，-1表示不等待或无持有者。固定输入只用0、1、-1，不接受未经校验的外部索引。

沿current走：先记录见过这个线程，再根据它想要的资源找到持有者；再次遇到同一个线程说明有环。ordered输入表示T0持有两把锁且不再等，T1等T0，没有回边。这个有限模型核对两个状态，不单凭它证明任意程序无死锁；第6节的全局顺序理由才覆盖相应协议。

## 12. 超时可以退出等待，但不能自动回滚

超时接口让调用者在期限后报告失败，随后需要释放自己已取得的资源并处理业务中间状态。若已经扣款却未入账，简单返回“超时”不会自动把余额恢复。

某些接口使用绝对时间而非相对几秒，时钟选择也影响期限语义；使用前要查具体契约。本批不增加靠实际时钟凑出的超时实验。它也不是通过强行解别人的普通mutex来“恢复”，后者破坏持有者与数据状态。

## 13. 活锁与饥饿

**活锁**表示参与者一直在执行和改变尝试，却没有完成有效工作，例如双方同时放手、同时重试、又同时冲突。**饥饿**表示某个参与者长期得不到需要的机会，而其他人可以持续完成。

trylock失败后无休止重试，可能制造忙循环、活锁或不公平；加随机退避可能改变碰撞情况，但不是不加条件的完成保证。普通mutex也不承诺本课期待的严格轮流顺序。正确总数与每个线程分到相同比例，是不同性质。

## 14. 安全性和活性分别问什么

**安全性**问“不应发生的坏事会不会发生”，例如同一任务不能消费两次、余额不能变负。**活性**问“在相应环境假设下，任务是否还能继续并最终结束”。

锁可能维护余额总和，却因为反向顺序而死锁；一个程序也可能一直快速推进，却重复消费项目。测试需要分别覆盖状态不变量与终止协议，不能用其中一项替代另一项。

## 15. 安全状态的小型资源演算

有5份相同资源，P0/P1/P2当前各持1份，所以可用Work=2；最大总需求依次3、2、3，尚可能需要Need=2、1、2。寻找一种顺序，让每个人的剩余需求都能由当前可用量满足，完成后归还已有分配。

| 选择 | 当时Work | 是否足够Need | 完成后Work |
| --- | --- | --- | --- |
| P1 | 2 | 2≥1 | 2+已分配1=3 |
| P0 | 3 | 3≥2 | 3+已分配1=4 |
| P2 | 4 | 4≥2 | 4+已分配1=5 |

这给出一个**安全序列**P1→P0→P2。演算中Work增加的是该参与者原先已经分配的数量，因为临时满足Need后又全部归还，净增加已有分配；不能把最大需求再额外加一次。银行家算法的基本想法就是在已知最大需求等前提下，用类似安全性检查决定是否允许分配。

## 16. 不安全不等于已经死锁

再换成总资源3份，两个参与者各持1，可用1，最大需求各3，Need各2。没有任何Need≤Work，按最坏需求模型找不到安全序列，属于不安全状态。

这不自动说明此刻已经死锁：最大需求是上界，实际下一步可能不再申请全部额度，也可能还没有人阻塞。若另外明确双方都正等待再取得2份、且都不在满足前释放，才可根据当前规则判断无法推进。不要把“无法保证未来安全”与“现在已经互等”混为一谈。

这个演算不修改Linux实际资源分配，也不表示操作系统普遍要求每个应用提前申报最大内存和锁需求。它是有清楚前提的避免策略模型。

## 18. 常见错误与排查顺序

“没有数据竞争，所以一定不会死锁”：分别分析冲突访问和等待依赖。

“超时后直接返回就恢复了”：检查已有资源、未完成业务与等待者通知。

“只修改转移方向就能解决反向锁”：独立规定资源获取顺序。

“死锁必须恰好两线程两锁”：join、消息和额度也可形成依赖，多参与者也可成环。

“模型输出无环就证明产品无死锁”：检查模型是否包含真实所有等待路径与资源数量。

## 19. 练习、提示与参考答案

1. T0持A等B，T1等A但没持B，能立即判死锁吗？不能，先找B的持有者或确认B可用。
2. 所有路径先编号小的锁再大的锁，破坏哪个条件？循环等待；需要全体遵守。
3. 线程在trylock返回EBUSY后，可以unlock该锁吗？不能，它没有取得锁。
