# 19 条件变量、信号量与生产消费：等到可以继续

> **零基础详细版 · 已重写。** 先区分互斥与条件等待，再沿单槽状态表读完整代码，最后比较条件变量与信号量。建议9—12小时。

## 1. 从“谁能改”走向“什么时候能做”

互斥锁解决同一时刻谁可以访问受保护状态，但不能单独回答“队列为空时消费者怎么办”。让消费者拿着锁反复查看，会让需要同一锁的生产者无法放入数据；解锁后不停重查又浪费CPU，还需要自己保证访问正确。

本章目标是写出等待条件、状态变化和通知的完整协议。先会第17章创建/join、第18章同一锁保护共享状态。平台Linux/WSL Ubuntu，Bash目录`~/os-lab/concurrency`，lab.h在同目录。

## 2. 生产者、消费者与有界通道

**生产者**产生待处理数据，**消费者**取出并处理数据，**通道或队列**在两者之间暂存。**有界**表示容量有限；满了生产者要等待，空了消费者要等待。

先使用容量1：一个slot保存整数，一个full表示当前是否有数据，一个done表示生产者以后不会再放新数据。这里不把特殊整数例如-1混作结束消息；数据值与关闭状态分开，方便解释最后一项和空输入。

## 3. 条件变量不是保存条件的变量

**条件变量**是协调等待与唤醒的同步对象。真正的条件保存在full、done等共享状态里；条件变量本身不保存“第3条消息”或累计通知次数。

**谓词**是能够判断真假的条件，例如`full != 0`表示有数据，`!full && !done`表示还没有数据且未来可能会有。先写清谓词，再选择何时等待；不是先加一个cond对象，希望它自动理解业务。

本章所有相关状态读写使用同一mutex。检查条件时持有它，修改条件时也持有它，等待接口负责把“释放锁并进入等待”衔接起来。

## 4. wait的三个阶段

下面是**接口流程模型**：

```text
已持有mutex → cond_wait原子地释放mutex并等待
              → 被唤醒后重新取得mutex
              → cond_wait返回，仍持有mutex → 再检查谓词
```

原子衔接避免“刚解锁、还没开始等，生产者已经通知完”的漏通知空隙。等待期间不持有mutex，所以生产者可以取得它改变状态。

被唤醒不等于条件已经满足，也不等于马上得到CPU。等待者要先重新取得mutex；别的线程也可能已经改变了条件。因此必须在while中检查，而不是用if检查一次后永远信任通知。

## 5. 第一个可运行的门闩

**完整程序：cond-latch.c**

```c
#include "lab.h"
#include <pthread.h>

static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t changed = PTHREAD_COND_INITIALIZER;
static int ready = 0;
static int result = 0;

static void *work(void *unused) {
    (void)unused;
    thread_check(pthread_mutex_lock(&lock), "lock worker");
    while (!ready) {
        thread_check(pthread_cond_wait(&changed, &lock), "wait");
    }
    result = 42;
    thread_check(pthread_mutex_unlock(&lock), "unlock worker");
    return NULL;
}

int main(void) {
    pthread_t worker;
    thread_check(pthread_create(&worker, NULL, work, NULL), "create");
    thread_check(pthread_mutex_lock(&lock), "lock main");
    ready = 1;
    thread_check(pthread_cond_broadcast(&changed), "broadcast");
    thread_check(pthread_mutex_unlock(&lock), "unlock main");
    thread_check(pthread_join(worker, NULL), "join");
    printf("result=%d\n", result);
    thread_check(pthread_cond_destroy(&changed), "destroy condition");
    thread_check(pthread_mutex_destroy(&lock), "destroy mutex");
    return 0;
}
```

编译并执行：

```bash
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror -g -pthread cond-latch.c -o cond-latch
./cond-latch
```

预期`result=42`。main先设置ready还是工作者先进入等待，都允许。若main先完成通知，工作者稍后持锁看到ready已经为1，根本不必等待。正确性来自持久状态，不来自“通知一定有人接住”。

## 6. 先修改状态，再通知

通知不替代赋值。若只broadcast却不设ready，工作者醒来仍应继续等；这是正确的while行为。若修改ready却不遵守同一锁的访问规则，又可能产生数据竞争或漏掉需要的等待协调。

本课选择在锁内修改状态并通知，随后解锁。通知不会自动释放锁，醒来的线程要等到能够重新取得mutex才从wait返回。`pthread_cond_wait`按pthread规则直接返回错误码，不套用read或sem_wait的errno/EINTR重试模板。

## 7. 单槽状态怎样变化

| full | done | 消费者动作 | 解释 |
| --- | --- | --- | --- |
| 0 | 0 | 等待 | 暂时空，未来还有可能产生 |
| 1 | 0 | 取数据 | 正常有数据 |
| 1 | 1 | 先取数据 | 已关闭但仍有最后一项 |
| 0 | 1 | 结束 | 关闭且已经读空 |

把最后两行混在一起，会丢数据。done表达“不再新增”，不表达“现存数据已经消费完”。这和第14章管道写端关闭以后仍须读完已有字节有相似之处，但实现接口与数据模型不同。

## 8. 主线完整单槽程序

[完整源码：queue.c](示例代码/queue.c)

```c
#include "lab.h"
#include <pthread.h>

static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t changed = PTHREAD_COND_INITIALIZER;
static int slot = 0, full = 0, done = 0, total = 0;

static void *producer(void *unused) {
    (void)unused;
    for (int value = 1; value <= 5; value++) {
        thread_check(pthread_mutex_lock(&lock), "lock");
        while (full) { thread_check(pthread_cond_wait(&changed, &lock), "wait"); }
        slot = value;
        full = 1;
        thread_check(pthread_cond_broadcast(&changed), "broadcast");
        thread_check(pthread_mutex_unlock(&lock), "unlock");
    }
    thread_check(pthread_mutex_lock(&lock), "lock");
    done = 1;
    thread_check(pthread_cond_broadcast(&changed), "broadcast");
    thread_check(pthread_mutex_unlock(&lock), "unlock");
    return NULL;
}

static void *consumer(void *unused) {
    (void)unused;
    thread_check(pthread_mutex_lock(&lock), "lock");
    for (;;) {
        while (!full && !done) {
            thread_check(pthread_cond_wait(&changed, &lock), "wait");
        }
        if (!full && done) { break; }
        total += slot;
        full = 0;
        thread_check(pthread_cond_broadcast(&changed), "broadcast");
    }
    thread_check(pthread_mutex_unlock(&lock), "unlock");
    return NULL;
}

int main(void) {
    pthread_t p, c;
    thread_check(pthread_create(&p, NULL, producer, NULL), "create producer");
    thread_check(pthread_create(&c, NULL, consumer, NULL), "create consumer");
    thread_check(pthread_join(p, NULL), "join producer");
    thread_check(pthread_join(c, NULL), "join consumer");
    printf("sum=%d\n", total);
    thread_check(pthread_cond_destroy(&changed), "destroy condition");
    thread_check(pthread_mutex_destroy(&lock), "destroy mutex");
    return 0;
}
```

使用第5节选项编译为queue，运行`./queue`，预期`sum=15`。先手算1+2+3+4+5，再追踪full的0→1→0。不是五个值都挤进同一个slot，后写者覆盖前写者；生产者每次都等上一项被取走。

## 9. 把一次交接展开

初始full=0，消费者若先执行便在while里等待，并释放lock。生产者取得锁，写slot=1、full=1、通知、解锁。消费者醒来重新拿锁，看到full=1，取出1并设full=0，通知可能在等空位的生产者。

消费者随后继续循环，若没有新项且未结束，就再次wait，等待接口在此释放锁。不要因为源码中consumer只在函数开头lock一次，就误认为它从头到尾占住锁；wait会在每次等待时释放并重新取得。

## 10. 最后一项为什么不会丢

生产者放入5后，可以在消费者取走以前设done=1。此时full=1、done=1，消费者的等待条件为假，退出条件`!full && done`也为假，因此先累计5。

它设full=0后继续循环，才看到full=0且done=1并退出。生产者设done时再通知，是为了唤醒可能仍在等数据的消费者，让它有机会观察结束状态。结束事件也需要纳入正常协议，而不是最后在main里猜线程应该结束了。

## 11. while、防虚假唤醒与多等待者

**虚假唤醒**表示wait可以在没有你期待的状态变化时返回；此外，一个消费者被唤醒后，另一个消费者可能先取得锁取走唯一项目。这两种理由都要求重查谓词。

把while改成if，醒来以后可能在空槽读取旧值，或者向满槽覆盖。重复运行没有撞上这种交错，也不使if版本满足接口契约。本批测试会受控模拟几次“返回但条件未变”的wait，正确代码应重新检查并继续等待。

## 12. signal与broadcast怎样选择

`pthread_cond_signal`唤醒至少一个相应等待者；`pthread_cond_broadcast`唤醒所有当前相应等待者。它们都不是消息队列，也不保证下一位实际运行者的公平顺序。

本单槽程序用一个changed协调不同谓词并broadcast，便于解释，代价是可能唤醒暂时不能工作的参与者。扩展成多消费者或多生产者时，可用not_empty与not_full两类条件减少无关唤醒；关闭时常需广播，让所有可能等待者重新检查退出状态。本批综合项目使用两类条件。

## 13. 信号量：保存可用额度

**信号量**维护一个非负可用额度。`sem_wait`成功取得一份额度；没有额度时等待。`sem_post`增加一份。与条件变量通知不同，先post后wait，额度仍可以留在那里供后来取得。

它不是一个普通int加减：等待、唤醒及相应同步由接口提供。**互斥锁**通常有持有者概念，要求持有者解锁；信号量可由另一个线程post来交付额度，语义不同，不把所有场景都叫“锁”。

## 14. 一个没有线程也能看的额度实验

**完整程序：semaphore-credit.c**

```c
#include "lab.h"
#include <semaphore.h>

static void take(sem_t *credit) {
    while (sem_wait(credit) < 0) {
        if (errno != EINTR) { die("sem_wait"); }
    }
}

int main(void) {
    sem_t credit;
    if (sem_init(&credit, 0, 0) < 0) { die("sem_init"); }
    if (sem_post(&credit) < 0) { die("sem_post"); }
    take(&credit);
    puts("credit_consumed=1");
    if (sem_trywait(&credit) != -1 || errno != EAGAIN) {
        fputs("expected no remaining credit\n", stderr);
        return 1;
    }
    puts("empty=would_block");
    if (sem_destroy(&credit) < 0) { die("sem_destroy"); }
    return 0;
}
```

编译为semaphore-credit，预期两行`credit_consumed=1`、`empty=would_block`。`sem_init`的第二个参数0用于本进程线程间共享，第三个0是初始额度。先post产生1份，take用掉，trywait不阻塞而报告无额度。

sem系列这里遵守成功0、失败-1并设置errno的规则，与pthread不同。sem_wait被信号打断报告EINTR时，本例继续等；其他错误失败。不要把所有负结果都无限重试。

## 15. 用两份额度协调单槽

空位信号量empty初值1，数据项信号量available初值0。生产者先取空位额度，再写入，最后发布数据项额度；消费者先取数据项额度，再读取，最后归还空位。

本例明确固定生产5项、消费5项，所以不需要额外结束消息。若项目不知道未来总量，必须设计关闭协议，不能让消费者第6次wait后永远等不到通知。

**完整程序：sem-channel.c**

```c
#include "lab.h"
#include <pthread.h>
#include <semaphore.h>

static sem_t empty, available;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static int slot = 0;
static int total = 0;

static void take(sem_t *credit) {
    while (sem_wait(credit) < 0) {
        if (errno != EINTR) { die("sem_wait"); }
    }
}
static void post(sem_t *credit) {
    if (sem_post(credit) < 0) { die("sem_post"); }
}
static void *produce(void *unused) {
    (void)unused;
    for (int value = 1; value <= 5; value++) {
        take(&empty);
        thread_check(pthread_mutex_lock(&lock), "lock");
        slot = value;
        thread_check(pthread_mutex_unlock(&lock), "unlock");
        post(&available);
    }
    return NULL;
}
static void *consume(void *unused) {
    (void)unused;
    for (int i = 0; i < 5; i++) {
        take(&available);
        thread_check(pthread_mutex_lock(&lock), "lock");
        int value = slot;
        thread_check(pthread_mutex_unlock(&lock), "unlock");
        total += value;
        post(&empty);
    }
    return NULL;
}
int main(void) {
    if (sem_init(&empty, 0, 1) < 0) { die("sem_init empty"); }
    if (sem_init(&available, 0, 0) < 0) { die("sem_init available"); }
    pthread_t p, c;
    thread_check(pthread_create(&p, NULL, produce, NULL), "create producer");
    thread_check(pthread_create(&c, NULL, consume, NULL), "create consumer");
    thread_check(pthread_join(p, NULL), "join producer");
    thread_check(pthread_join(c, NULL), "join consumer");
    printf("sum=%d\n", total);
    if (sem_destroy(&available) < 0) { die("destroy available"); }
    if (sem_destroy(&empty) < 0) { die("destroy empty"); }
    thread_check(pthread_mutex_destroy(&lock), "destroy mutex");
    return 0;
}
```

编译为sem-channel，预期sum=15。total只有消费者在工作期间读写，main在join以后读；slot使用lock。这里为延续队列结构协议保留mutex，单槽严格交接本身也提供了额外顺序，暂不据此删掉同步来推广复杂多槽设计。

## 16. 先等额度，再取得队列锁

若消费者先持队列锁再wait(available)，而生产者需要同一锁才能放入数据并post，双方就可能互等。正确模板是先等额度，再锁结构，完成修改后解锁，再发布对应额度。

它不是让empty、available和count在任意执行瞬间都能套同一条简单等式：线程可能已经预留额度但还没入队。对多个生产者/消费者，要区分可用额度、已预留操作和队列中的实际项。综合项目主线采用条件变量表达count和关闭状态，避免同时引入两套复杂协议。

## 17. 对比两种机制

| 问题 | 条件变量 | 信号量 |
| --- | --- | --- |
| 状态放哪里 | 应用自己的谓词与数据 | 额度在信号量中，数据结构仍需协议 |
| 先通知后等待 | 通知本身不累计，靠状态避免漏等 | post的额度可以保留 |
| 等待前是否持mutex | cond_wait要求已持对应mutex | sem_wait不要求先持队列锁 |
| 唤醒后怎么办 | 重新取得锁并检查谓词 | 成功wait表示取得一份额度 |
| 本课结束方式 | closed/done且读空后结束 | 固定项数；未知项数需另设计 |

第15章的SIGINT等信号、pthread条件变量、POSIX信号量名字相近，但不是同一个机制。先问它传递事件、协调谓词还是管理额度，不按中文名字相似来互换接口。

## 18. 错误与终止也属于协议

本章简短例程遇不可恢复接口错误会结束整个实验进程。长期服务若只让一个工作者悄悄返回，却留下其他人在等它永远不会产生的数据，就可能卡住；需要共享失败/关闭状态、通知等待者、join、最后销毁资源。

不能先destroy条件变量再希望等待者自己发现结束，也不能任意取消持锁线程来代替协议。下一份综合项目会处理消费者创建一半失败：主线程设closed并广播，等待已创建者结束，随后销毁。

## 19. 练习、提示与参考答案

1. 为什么wait返回时还要while？答案：可能虚假唤醒，或别的线程先消耗了条件。
2. full=1、done=1时取还是退？先取，关闭不等于已读空。
3. 生产者已经结束、消费者此时等空队列，需要哪次通知？设置done以后广播，让消费者检查退出。
4. 把semaphore-credit的post删掉，还能直接运行take吗？不能照抄执行等待版；额度0会阻塞，若想观察空状态应使用trywait。
5. 条件变量signal能当“累计收到5条任务”吗？不能，任务应存入受保护的数据结构。
6. sem-channel把消费者循环改成6次为什么错误？生产量5与消费协议不匹配，第6份额度永远不存在；修正协议而非加sleep。

纸面练习：容量改为4，需要数组、head、tail、count，条件分别为有空位与有数据或已关闭。写出count的0≤count≤4，再看[本批完整项目](详写第五批-练习与参考答案.md)。
