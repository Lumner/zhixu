# 16 组合电路实验与穷举验证

> 零基础详细版。先修：第12章的测试平台与波形，第14章的ALU标志，第15章的位宽边界。建议5–7小时，包括手算、运行、改错和整理验收记录。

**本章目标：** 从功能合同独立写出预期；估算并遍历输入空间；在新增操作后同时检查旧功能、保留编码和全部标志；从一条失败日志定位错误；准确区分功能仿真与综合、时序、上板结果。

## 16.1 测试是拿什么和什么比较

第14章手算九组输入，写死预期值。这样容易跟着做，但四位a、四位b、两位op共有16×16×4=1024组二值输入。若改成八位a/b，手工逐条填写就很容易遗漏。

**被测设计**是我们实际要检查的电路，常叫DUT；**参考模型**根据规格算出应有输出；**测试平台**负责给输入、等待、读取、比较、记录失败。三者的职责要分开：打印y是观察，把y与预期比较才是检查。

参考模型也可能写错。为了减少两边共享同一错误，本章不复制DUT的溢出位公式，而先把补码转成普通整数，做数学加减，再判断结果是否越界。不同推导并不能保证绝对无错，但能让一种错误不那么容易同时出现在两边。

## 16.2 先改规格：给ALU增加按位或

需求变化：保留加、减、与、异或，再增加按位或。原来两位op只有四个编码，已经全部用完，装不下第五种操作。因此本实验建立新模块`alu_extended`，op扩成三位，同时增加一位`valid_op`说明操作码是否受支持。

这是一份**明确的新接口**；第14章与旧工程示例的两位ALU不改。不能把新设计悄悄覆盖到旧目录，再让所有旧实例靠截断或自动补位“猜着接”。

| 三位op | 本次定义 | y | C | V | valid_op |
| --- | --- | --- | --- | --- | --- |
| 000 | 加法 | 低四位和 | 无符号进位 | 补码加法溢出 | 1 |
| 001 | 减法 | 低四位差 | 无借位 | 补码减法溢出 | 1 |
| 010 | 按位与 | a&b | 0 | 0 | 1 |
| 011 | 按位异或 | a^b | 0 | 0 | 1 |
| 100 | 按位或 | a\|b | 0 | 0 | 1 |
| 101、110、111 | 保留，不支持 | 0000 | 0 | 0 | 0 |

zero仍然对所有输出判断y是否为0，所以保留编码时zero=1。valid_op=0说明这不是一次受支持操作，接收端不应把y=0误解成“成功完成了某个合法计算”。这与第13章“空请求也可能编号为0，必须看valid”是同一种接口思想。

本章规定的保留编码是确定的二进制101、110、111，不是在说输入X/Z也已完整验收。含未知位时的协议检查需要另行定义。

## 16.3 第一份完整文件：design.sv

在`logic-lab/16-alu-regression/`建立两文件，或复制下载包`source/组合实验/16-alu-regression/`。下面是[design.sv](组合实验/16-alu-regression/design.sv)完整内容。

```systemverilog
module alu_extended(
  input logic [3:0] a, b,
  input logic [2:0] op,
  output logic [3:0] y,
  output logic carry, overflow, zero, valid_op
);
  logic [4:0] wide;
  always_comb begin
    wide = 5'b00000;
    y = 4'b0000;
    carry = 1'b0;
    overflow = 1'b0;
    valid_op = 1'b1;
    case (op)
      3'b000: begin
        wide = {1'b0, a} + {1'b0, b};
        y = wide[3:0];
        carry = wide[4];
        overflow = ~(a[3] ^ b[3]) & (y[3] ^ a[3]);
      end
      3'b001: begin
        wide = {1'b0, a} + {1'b0, ~b} + 5'd1;
        y = wide[3:0];
        carry = wide[4];
        overflow = (a[3] ^ b[3]) & (y[3] ^ a[3]);
      end
      3'b010: y = a & b;
      3'b011: y = a ^ b;
      3'b100: y = a | b;
      default: begin
        y = 4'b0000;
        valid_op = 1'b0;
      end
    endcase
  end
  assign zero = (y == 4'b0000);
endmodule
```

相对第14章有三处实质变化：op改为[2:0]；新增100的OR分支；新增valid_op，默认1但保留分支置0。加减公式、无借位含义和zero定义均沿用明确合同。

默认值不是“上次的输出”。每次组合过程重新计算时，wide、y、C、V先获得0，valid_op先为1，再由本次分支覆盖。保留分支不另外写C/V，它们仍为本次默认0。

## 16.4 先估算穷举需要多少输入

现在a有16种，b有16种，op有8种，总数16×16×8=2048。合法操作占5×256=1280组，三个保留编码占3×256=768组。保留码没有被“因为不支持”而跳过，它们的拒绝行为也是规格的一部分。

**穷举**是把声明范围中的每一种输入都试一遍。本章穷举的是该接口的全部二值输入，不包含X/Z，也不代表验证了硬件传播延时、毛刺、工艺条件和所有参数版本。

规模增长很快：16位a与16位b，仅两路数据就有2^32=4,294,967,296种组合，还没有乘操作码数量。这里小接口适合穷举；更大设计常要结合边界、随机、覆盖分析、断言或形式方法，不能把本章的三层for照搬到任何规模。

## 16.5 把位模式转换成整数参考值

循环中的ai、bi是0…15的整数，a、b取它们的低四位。无符号加法直接ai+bi，最大30，普通整数足够；无符号减法ai−bi，范围−15…15，整数也装得下。

若按四位补码解释，0…7保持；8…15要减16：

| 循环整数ai | 接到a的位模式 | 补码数值signed_a |
| --- | --- | --- |
| 0 | 0000 | 0 |
| 7 | 0111 | 7 |
| 8 | 1000 | 8−16=−8 |
| 15 | 1111 | 15−16=−1 |

所以写`signed_a=(ai>=8)?ai-16:ai;`。signed_a是integer变量，能保存这些负数。b同理。这里没有把四位端口声明成signed，而是让参考模型显式完成数值解释，便于检查。

## 16.6 数据与标志分别怎样建立预期

以加法为例，先算`math_value=ai+bi`，低四位就是预期y；carry由math_value>15判断。再算`signed_math=signed_a+signed_b`，若小于−8或大于7，预期overflow为1。

减法算`math_value=ai-bi`。integer采用补码表示，取`math_value[3:0]`得到所需模16结果。例如3−5=−2的整数低四位是1110。carry不是取负数整数的最高位，而直接按本课程语义判断ai≥bi。overflow则判断signed_a−signed_b是否在−8…7内。

逻辑操作的参考直接按定义用整数位运算，并取低四位；C、V保持0。这里与DUT使用同一基础AND/OR/XOR运算符，独立性主要体现在操作选择、数学范围与标志推导，不声称整个模型完全不同算法。

| 输出项 | 参考模型依据 | 没有复制什么 |
| --- | --- | --- |
| 加法C | 整数和是否>15 | 五位wide的切片 |
| 减法C | ai是否≥bi | 反码加1的最终进位 |
| 算术V | 有符号整数结果是否越界 | 最高位异或公式 |
| Z | 预期y是否0 | DUT的实际zero输出 |
| valid_op | oi是否小于5 | DUT的实际有效标志 |

zero必须根据**预期y**计算。若用实际y去算expected_zero，设计把y和Z一起算错时可能互相掩盖。这是写参考模型时很常见的依赖错误。

## 16.7 第二份完整文件：tb.sv

下面是[tb.sv](组合实验/16-alu-regression/tb.sv)完整内容。先读三层循环与case，再看比较和日志；不必一次记住所有变量名。

```systemverilog
`timescale 1ns/1ps
module tb;
  logic [3:0] a, b, y, expected_y;
  logic [2:0] op;
  logic carry, overflow, zero, valid_op;
  logic expected_carry, expected_overflow, expected_zero, expected_valid;
  integer signed_a, signed_b, math_value, signed_math, count;
  alu_extended dut(.a(a), .b(b), .op(op), .y(y), .carry(carry),
    .overflow(overflow), .zero(zero), .valid_op(valid_op));
  initial begin
    $dumpfile("alu.vcd");
    $dumpvars(0,tb);
    count=0;
    for (int oi=0; oi<8; oi++) begin
      for (int ai=0; ai<16; ai++) begin
        for (int bi=0; bi<16; bi++) begin
          a=ai[3:0]; b=bi[3:0]; op=oi[2:0];
          signed_a=(ai>=8) ? ai-16 : ai;
          signed_b=(bi>=8) ? bi-16 : bi;
          math_value=0; signed_math=0;
          expected_carry=1'b0;
          expected_overflow=1'b0;
          expected_valid=(oi<5);
          case (oi)
            0: begin
              math_value=ai+bi;
              signed_math=signed_a+signed_b;
              expected_carry=(math_value>15);
            end
            1: begin
              math_value=ai-bi;
              signed_math=signed_a-signed_b;
              expected_carry=(ai>=bi);
            end
            2: math_value=ai & bi;
            3: math_value=ai ^ bi;
            4: math_value=ai | bi;
            default: math_value=0;
          endcase
          if (oi<2)
            expected_overflow=(signed_math < -8 || signed_math > 7);
          expected_y=math_value[3:0];
          expected_zero=(expected_y==4'b0000);
          #1;
          if ({y,carry,overflow,zero,valid_op} !==
              {expected_y,expected_carry,expected_overflow,expected_zero,expected_valid})
            $fatal(1, "alu op=%03b a=%h b=%h actual y/C/V/Z/valid=%h/%b/%b/%b/%b expected=%h/%b/%b/%b/%b",
              op,a,b,y,carry,overflow,zero,valid_op,
              expected_y,expected_carry,expected_overflow,expected_zero,expected_valid);
          count++;
        end
      end
    end
    $display("PASS extended ALU: %0d binary input cases including 3 reserved opcodes",count);
    $finish;
  end
  initial begin #3000; $fatal(1, "ALU regression timeout"); end
endmodule
```

oi最外层遍历0…7，ai、bi分别0…15。输入端明确取[2:0]、[3:0]。每次循环都重新设置预期标志，防止参考模型自己残留上一项的结果。

case判断的是整数oi，数学运算在足够宽的integer里进行。只有最后将math_value低四位放到expected_y。若参考模型一开始就把所有计算压成四位，它也可能丢掉需要判断carry的数学信息。

`||`在overflow判断中是逻辑或：小于−8或大于7。这里没有要求每一位逐位做或。`count++`对每个已完成比较计一次数；只有全部比较未触发fatal，才打印PASS。

## 16.8 驱动、等待、检查，三个动作不要合并

每次先赋a、b、op，再计算参考值，再`#1`推进虚拟时间，最后读取DUT。参考计算本身不需要等待，但DUT的组合关系需要获得仿真调度机会。若刚改输入就立即读取，可能读到上个组合结果。

这个1ns是本教学测试的采样间隔，**不是测得真实ALU只需1ns**。本设计没有标注门级延时，也没综合到具体板卡。RTL功能仿真中“等一次再检查”和真实电路能跑多高频率，是两种验证。

另一个initial在3000ns触发超时。主测试2048次，每次1ns，总计2048ns，正常应先结束；若主过程意外卡住，超时会非正常退出，避免把“没输出也没结束”当成通过。

## 16.10 什么叫回归测试

**回归测试**指修改后重新运行已有检查，确认旧功能仍满足原先合同，同时补上新功能的检查。增加OR时，不是只试a=1、b=2得到3就结束；还要重新检查加减、与、异或、C/V/Z，并检查新出现的保留码。

本实验0…3的操作含义与旧两位版本对应，但op端口已变成三位，测试也显式改变。不要把旧tb未经阅读直接拿来编译，依赖工具替你补零，然后宣布新接口完全兼容。

将规格表、设计端口、实例连接、参考模型、遍历范围一起检查，才能形成闭环。若以后新增第六种操作，可以使用101，但必须把它从保留行移到合法行，修改valid与预期，且保留110、111的拒绝测试。

## 16.11 故意把overflow错写成carry

先复制一份实验目录用于改错，保留正确文件。在副本中仅把加法分支的overflow公式改成`overflow=carry;`，保存、重新编译、运行。实际故障检查得到的关键消息如下，省略了本机路径：

```text
alu op=000 a=1 b=7 actual y/C/V/Z/valid=8/0/0/0/1 expected=8/0/1/0/1
```

按顺序定位：op=000是加法；输入1与7，数学和8；结果y=8正确，C=0正确，Z=0正确，valid=1正确；唯一不同是V。补码+1与+7的和超出+7，所以预期V=1，设计却给0。错误集中到加法overflow，不必先怀疑MUX或OR。

这条输入是循环按顺序发现的第一个失败，不代表唯一失败。1+7与7+1都能说明问题；日志保留第一个有助于快速重现。恢复正确公式并重新编译后，应再次得到2048组PASS。

## 16.12 从失败时刻回到波形

三层循环的输入序号可写成：

```text
序号 = oi×256 + ai×16 + bi
该输入保持区间 = [序号 ns, 序号+1 ns)
```

例如op=000、a=1、b=7，序号=0×256+1×16+7=23。输入在23ns装入，测试在24ns比较。打开该故障仿真的alu.vcd时，可看23.5ns附近的稳定值；在24ns边界要区分比较动作与接下来输入切换，第12章讲过这种边界。

按[第12章GTKWave步骤](12-测试平台时间与波形.md)加入tb.a、tb.b、tb.op、tb.y、tb.carry、tb.overflow、tb.zero、tb.valid_op；需要时再看dut.wide。先确认时间单位，VCD可能用ps刻度，23000ps才是23ns。

本批维护检查实际解析了正常仿真VCD中的八组数据与标志，例如7+1、F+1、8−1、OR和保留码，全部与独立预期一致。GTKWave桌面界面未实际操作，不把“生成/解析VCD”写成“已完成GUI检查”。

## 16.13 常见错误与故障注入检查

| 故意引入的错误 | 典型失败 | 为什么该测试有价值 |
| --- | --- | --- |
| 加法V直接等于C | 1+7，V漏报 | 不是只检查y |
| 减法C反相 | 0−0，无借位被写成0 | 相等边界也检查 |
| OR错写AND | 0 OR 1应为1 | 新增操作不是摆在表里没执行 |
| 保留码valid_op保持1 | op=101、a=b=0 | y都是0仍能查有效标志 |

这些是自动维护验证中实际检出的四项ALU扩展故障。加上第13章优先级反向、第14章减法漏1、第15章地址上界放行，共七项。它们都是缓存中的错误副本，正确源文件没有被保留为错误版本。

故障注入的目的，是证明某些检查确实能失败，不是证明测试已经发现所有可能的bug。你可以再试漏清逻辑标志，但要记录具体修改、失败输入和恢复结果，不把“计划试”填成“已通过”。

## 16.14 为什么还要人工检查设计结构

自动功能比较之外，逐项读RTL：组合输出是否每条路径赋值；单一信号是否只有一个驱动；切片和拼接宽度是否准确；符号解释是否明确；有没有组合反馈；设计里是否混入测试用的延时、打印和finish。

这些检查不是让你重复抄一份实现。它们关注代码是否表达了需要的电路结构和可维护接口。仿真正确并不自动给出综合资源、最高频率、真实引脚电压或板卡正确接线；后面的FPGA阶段才讨论相应工具与依据。

## 16.16 练习与过程答案

练习1：如果忘把oi循环上界从4改为8，会漏掉多少？只运行4×16×16=1024组，漏新OR的256组和保留码768组，共1024。即使最后打印PASS，也只对应实际执行到的范围。

练习2：op=101、a=F、b=F，预期是什么？查保留行，不做F+F：y=0，C=0，V=0，Z=1，valid_op=0。输入数据不改变保留码的固定拒绝行为。

练习3：8−1的独立预期怎样算？无符号8−1=7，所以y=7、C=1；补码a=−8、b=1，数学差−9超出范围，所以V=1；y非0，Z=0；op合法，valid_op=1。

练习4：为什么不能令expected_overflow等于dut.overflow？那就把待检查的实际值直接当答案，比较永远相同，无法发现溢出公式错误。模型应来自规格，不来自DUT输出。
