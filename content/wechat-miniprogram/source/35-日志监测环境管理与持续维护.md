# 第35章：日志、错误监测、环境管理、版本回退与持续维护

一个应用能运行，只说明眼前的操作成功了。维护应用还要回答：谁受到了影响？问题从哪个版本开始？失败发生在哪一层？还能不能重试？旧版本是否能安全地接回现有数据？

本章在第34章工程上继续，新增 [16-studyhub-operations](示例代码/16-studyhub-operations/README.md)。你会得到默认关闭的本地诊断、调用观察层、启动目标检查、维护练习页、源码制品清单和回退准备检查器。主工程继续WebView：16个主包页、11个普通分包页，共27页；独立Skyline探针保留。

本章不新增云集合，不改变云函数和数据协议，不自动上传日志、不发送告警、不部署、不备份或回退真实资源。完整数据权利与期限机制仍沿用第34章的待办，不能因增加维护页就当作完成正式交付。

配套阅读：[20组练习](第十五阶段-练习与参考答案.md)、[运行与实际验收](第十五阶段-维护演练与实际验收.md)、[完整源码附录](第十五阶段-完整源码附录.md)、[本地验证记录](验证/第十五阶段验证记录.md)。

## 35.1 本章学习路线

建议分五次完成：

1. 画出错误从按钮到云数据库的路径，理解日志、指标和告警的区别。
2. 手写允许字段的内存记录器，练习Set、数组、闭包和复制。
3. 理解观察包装器，确认日志失败不能破坏业务。
4. 配置明确的环境目标，生成可核对的源码清单。
5. 完成固定故障演练，阅读回退受阻报告并填写真实验收表。

本章结束时，你应能解释每个诊断字段的用途、哪些内容不能进入记录、为什么客户端超时不表示云端没写入，以及为什么备份与回退不是同一件事。

## 35.2 先画出排错链路

```text
用户点击
  → 页面校验/防重入
  → task-session、仓储与outbox
  → cloud-client观察层
  → invoke-core等待与回调
  → 微信云调用
  → 云函数校验、身份和业务事务
  → 数据库/云存储/外部发送
  → 响应返回
  → 页面是否仍活动、结果是否仍属于本次请求
```

“按钮没有成功提示”可能发生在任意一层：点击未进入、字段不合法、等待超时、服务器拒绝、事务提交但回包丢失，或页面已经离开。

不要一看到错误就重启、清缓存或再创建一次。先保留版本、操作时间、步骤、界面状态和原操作编号的受控核对记录，再确定下一步。

## 35.3 日志、指标、告警、追踪分别是什么

| 概念 | 初学者的理解 | 示例 |
| --- | --- | --- |
| 日志 | 记录一次事件发生了什么 | 一次RPC得到TRANSPORT分类 |
| 指标 | 对一段范围内的事件做统计 | 某时间段调用数、失败数、耗时分布 |
| 告警 | 条件满足后提醒负责人处理 | 某指标持续超过约定阈值 |
| 追踪关联 | 把同一处理链的证据联系起来 | 在受控后台用请求编号定位对应调用 |
| 事件复盘 | 解释影响、原因、处理与改进 | 某候选误配环境，怎样发现并防止再发 |

本章实现本地分类事件和固定样本线索，提供真实监控的配置与验收方法。它没有搭建线上日志平台或完整分布式追踪系统。

## 35.5 什么内容不应该进入普通诊断

反例：

```js
// 反例：不要复制到项目
console.log('提交失败', formData, userIdentity, filePath, error);
```

这可能同时暴露标题、正文、OPENID、临时文件路径、请求参数和堆栈里的URL。再把它上传第三方平台，接收方、权限、期限和用户告知的范围都会变化。

本章采用“从零构造允许字段”。不先复制整个对象再尝试删除敏感字段；新增业务字段时，允许名单之外的内容自然不会进入记录。

“匿名”也不能随便承诺。少量字段组合可能仍有上下文含义；真实上报方案要重新盘点。本例默认关闭且仅内存，不据此推导其他日志系统也没有数据。

## 35.6 本例记录的事件结构

```js
{
  seq: 1,
  event: 'rpc-fail',
  action: 'list',
  code: 'CLOUD_TIMEOUT',
  elapsed: '>=12000ms'
}
```

seq只是本进程队列里的数字，不是用户ID、云请求ID或持久操作编号。event来自固定四种分类；action和code经过允许名单，不认识的值映射other/OTHER。

elapsed保存耗时桶，不保存精确时间戳。因而这些记录不能独立还原真实发生时刻，也不能直接和云日志逐条关联；需要在受控排错中另行记录测试时间范围等材料。

实际代码位于miniprogram/services/diagnostics-core.js。

## 35.7 基础语法：Set与has

```js
const EVENTS = new Set([
  'rpc-ok', 'rpc-fail', 'runtime-error', 'unhandled'
]);
if (!EVENTS.has(event)) return false;
```

Set保存不重复的成员；has判断是否属于固定集合。本例拒绝任意事件名，防止把私人标题当作“事件名称”送进日志。

动作名单只收录部分课程动作。例如笔记扩展动作可能映射成other，这是有意限制诊断粒度，不影响实际云请求。要增加分类，先说明必要用途并更新测试，不能直接保留任意字符串。

## 35.8 基础语法：闭包管理队列

```js
function createJournal({ enabled = false, capacity = 80 } = {}) {
  let events = [], accepted = 0, dropped = 0, sequence = 0;
  function record(event, fields = {}) {
    // 下面小节解释
  }
  return {
    record,
    snapshot: () => ({
      enabled: enabled === true,
      capacity, accepted, dropped,
      events: events.map(row => ({ ...row }))
    }),
    clear() {
      events = [];
      accepted = 0;
      dropped = 0;
      sequence = 0;
    }
  };
}
```

events等变量属于createJournal这一次调用。返回的方法保留对它们的访问，这就是闭包。两个记录器有两份独立状态：真实调用队列和固定练习队列不会混在一起。

默认参数让调用方不填配置时保持关闭。只接受enabled===true，字符串"true"不会启用。

## 35.9 为什么不返回内部数组

如果snapshot直接返回events，调用方可以把第一条事件的code改成任意值，或push很多对象破坏容量约定。

本例用map加对象展开复制每一条记录。当前每个字段都是原始值，所以这层复制已足够；如果后来加入嵌套对象，要重新设计复制和允许字段。

“只读快照”在这里指与内部状态脱离，不代表返回对象被Object.freeze冻结，也不代表调用方不能修改自己的那份副本。

## 35.10 从零构造一条记录

```js
const row = {
  seq: ++sequence,
  event,
  action: ACTIONS.has(fields.action) ? fields.action : 'other',
  code: CODES.has(fields.code) ? fields.code : 'OTHER',
  elapsed: bucket(fields.elapsedMs)
};
```

没有...fields，因此payload、openid、URL、stack、message、filePath等额外字段不会被复制。原始错误码不在名单中，也不会原样输出。

记录器不是用来接受任意不可信对象的通用安全沙箱。本项目调用方传普通内部对象；观察层还隔离记录器异常，避免观测失败影响业务。

## 35.11 有界内存与样本挤出

```js
events.push(row);
accepted++;
if (events.length > capacity) {
  events.shift();
  dropped++;
}
```

push加到末尾；shift移除最旧一条。容量默认80，允许1—200的整数，防止误传小数、负数或无限值。

accepted是当前进程自清空以来接受的总数，dropped是挤出数；events只包含保留下来的最近样本。不能用accepted作分母、只用events里的失败数作分子，这会把两种范围混在一起。

该实现适合很小的教学队列；更大规模应评估真正的循环缓冲结构。进程结束会丢失这些记录，本例没有上传、写缓存或持久日志。

## 35.12 耗时分桶与未知值

```js
function bucket(value) {
  if (!Number.isFinite(value) || value < 0) return 'unknown';
  if (value < 250) return '<250ms';
  if (value < 1000) return '250-999ms';
  if (value < 3000) return '1000-2999ms';
  if (value < 12000) return '3000-11999ms';
  return '>=12000ms';
}
```

边界采用左闭右开思路：249属于第一桶，250属于第二桶。桶宽是课程选择，不是平台性能达标线。

Date.now是墙钟，用户或系统校时可能导致差值为负，因此未知不改成0。若真正测量性能，应结合当前平台支持的能力和一致的采样方案；第31章的限制仍然适用。

## 35.13 观察包装器为什么单独一层

invoke-core已经负责等待、超时、响应校验和错误语义。现在只想观察结果，不应顺手改掉重试、原编号和载荷。

新文件observed-call.js接受三个依赖：

```js
createObservedCall({
  invoke,           // 原来的业务调用
  record,           // 记录分类事件
  clock: Date.now   // 测试可换成固定时钟
});
```

这层不负责鉴权、不生成新的opId、不把观察序号发给云函数，也不改变数据库事务。

## 35.14 成功与失败都保持原结果

```js
try {
  const result = await invoke(name, data);
  emit('rpc-ok', { action, code: 'OK', elapsedMs: now() - started });
  return result;
} catch (error) {
  let code;
  try { code = error && error.code; } catch (_) {}
  emit('rpc-fail', { action, code, elapsedMs: now() - started });
  throw error;
}
```

成功返回原result对象；失败抛出原error对象。这样调用方仍能按原code处理CLOUD_TIMEOUT、CONFLICT或TRANSPORT，任务草稿和outbox恢复协议不变。

error.code也可能由特殊getter提供，所以提取时做隔离；动作元数据与时钟读取也采用受控保护。该防护只保护观测层，不宣称能执行任意不可信代码。

## 35.15 日志失败不能把业务成功变成失败

```js
const emit = (event, fields) => {
  try { record(event, fields); } catch (_) {}
};
```

如果不隔离，云端已成功创建任务后，日志器抛错会让页面以为提交失败。用户可能再点一次，排错也更困难。

这里静默忽略的是辅助记录失败，业务失败仍然抛出。生产监测系统如果需要跟踪自身故障，应采用独立、有限的机制，避免在日志失败时无限递归记录“日志又失败了”。

## 35.16 接入实际cloud-client

原createInvoker仍保持原实现。cloud-client只是把它交给观察层：

```js
const rawInvoke = createInvoker({
  envId: ENV_ID,
  ready: () => ({
    ready: getApp().globalData.cloudReady,
    message: getApp().globalData.bootError
  }),
  callFunction: options => wx.cloud.callFunction(options)
});
const invoke = createObservedCall({
  invoke: rawInvoke,
  record: diagnostics.record
});
```

实际发送仍是原name、data和config.env，没有额外追踪字段。FUNCTION_NAME换成其他名字时，分类可以退回other，不影响请求。

本例只观察这条封装链；独立订阅函数调用、所有原生API、后台网络或第三方SDK并不会自动全部纳入。

## 35.17 全局错误钩子怎样使用

App新增：

```js
onError() {
  diagnostics.record('runtime-error', { code: 'UNCAUGHT' });
},
onUnhandledRejection() {
  diagnostics.record('unhandled', { code: 'UNHANDLED' });
}
```

没有保存回调的原始参数、堆栈或reason。默认诊断关闭时不保留事件。真实项目若要上报堆栈，需要先设计内容过滤、接收方、访问权限、期限和指引更新。

已经被业务catch处理的错误通常应在对应业务层观察；不能指望全局钩子包办。原生崩溃、设备终止进程或断电也不能由两个JS回调保证捕获。

## 35.18 失败次数不等于服务故障次数

本项目云函数常把业务失败编码为ok:false；函数执行本身可能正常结束。平台“函数执行错误次数”和客户端“业务调用失败次数”因而不必一致。

反过来，用户输入非法、正常版本冲突也不一定代表服务不可用。TRANSPORT和CLOUD_TIMEOUT还含“结果未确认”的含义。

本地统计刻意称为“RPC样本失败比例”，只作为排查线索，不命名为线上可用率或服务承诺。

## 35.19 分母必须说清楚

本章summarize先选出队列里rpc-ok和rpc-fail，再计算：

```js
const attempts = rows.length;
const failures = rows.filter(row => row.event === 'rpc-fail').length;
const ratio = attempts ? failures / attempts : null;
```

没有请求时ratio为null，不伪造“100%成功”。runtime-error和unhandled不混入RPC分母。

统计只覆盖当前保留的最多80条事件，不是最近5分钟、当天全部用户或所有网络请求。用户多开几个页面会挤出旧样本，因此不能用它绘制真实日趋势。

## 35.20 一个可解释的教学阈值

```js
const signal = attempts < 20
  ? 'insufficient'
  : failures >= 3 && ratio >= 0.2
    ? 'investigate'
    : 'no-threshold-hit';
```

至少20条样本，再看失败数和比例。20条里5次失败得到25%，提示investigate；19条全失败仍显示样本不足，避免把课堂阈值误当统计结论。

样本不足不等于系统健康，也不意味着严重故障可以不处理。真实告警通常还需绝对量、影响等级、持续周期、资源状态与用户反馈，不应只照搬20%。

## 35.21 延迟分位数怎样理解

平均耗时会掩盖少数很慢的请求。作为课堂计算，若精确耗时数组排序后用“最近秩”定义P95：

```js
// 说明性片段，不是本项目内存桶的实际统计函数。
function p95(samples) {
  const values = samples.filter(x => Number.isFinite(x) && x >= 0)
    .slice().sort((a, b) => a - b);
  if (!values.length) return null;
  return values[Math.ceil(values.length * 0.95) - 1];
}
```

5个值[100,120,140,180,5000]按该定义P95为5000。不同工具可能采用不同分位数算法，比较前要确认定义和范围。

本项目保存耗时桶，不能从桶恢复精确P95。不要为了画漂亮数字假装拥有没有采集的数据。

## 35.22 真实告警应该包含哪些要素

在自己的真实环境中，至少确定资源、指标定义、统计周期、持续周期、最小请求量、阈值、严重程度、接收人、通知频率、解除条件和处理手册。

例如“连续几个统计周期出现大量超时且用户无法保存”，应指向原编号核对、函数状态、数据库和网络排查。阈值要结合真实基线，不能把课堂数值当平台推荐。

首次启用要验证“触发一次、重复抑制、恢复一次、接收人确实收到”。本章没有替你创建策略或发送消息，记录表保持待执行。

## 35.23 本机日志与云日志各自看什么

| 证据 | 可以帮助定位 | 不能单独证明 |
| --- | --- | --- |
| 页面错误/草稿状态 | 用户当前看到什么、是否封存 | 云端一定没有提交 |
| 本机RPC分类 | 经过该封装的本进程结果 | 全部用户失败率 |
| 云调用/系统日志 | 某次调用是否执行、资源报错 | 页面实际可见结果 |
| 业务回执 | 某原编号已记录的结果 | 当前记录仍存在或处于相同状态 |
| 数据与文件核对 | 当前归属、引用及实际对象 | 跨系统原子一致 |
| 用户反馈 | 真实步骤与感受 | 完整根因 |

服务端原操作回执与客户端观察序号不是一回事。需要关联时在受控权限下使用必要材料，不把OPENID、正文和所有参数拼成公开日志。

## 35.24 环境不是一个开关

开发、预发布、正式环境通常应分别管理云资源、权限、域名、模板、配额、数据和人员访问。具体资源能力及费用以实际账号为准。

不同ENV_ID不自动证明资源真正隔离；同一云环境内换一个集合名，也不自动得到完整隔离。还应检查函数变量、存储、外部服务、备份和操作权限。

本例只保存一个构建目标，不提供用户点选“切换正式库”的页面。

课程采用明确允许表：

| 构建STAGE | 允许的发行类型 | 目的 |
| --- | --- | --- |
| development | develop | 本地开发目标 |
| staging | develop、trial | 预发布开发与体验验收 |
| production | trial、release | 正式候选先体验，再正式发布 |

允许production+trial并不建议体验人员随意写正式数据；要按真实发布方案限制测试范围。规则是课程选择，可按已审查的流程调整，但不能靠trial反向猜测ENV_ID。

## 35.27 启动目标检查如何实现

environment-core的checkEnvironment比较：

1. STAGE在已知集合中。
2. RELEASE_VERSION符合课程格式。
3. 预期AppID、ENV_ID已填写。
4. 实际云配置与预期ENV_ID相等。
5. 平台元数据可得，AppID与预期一致。
6. 平台发行类型在该阶段允许表中。

返回只含ok、阶段、可展示版本、问题代码和说明，不把真实标识复制进维护页。

这是避免误连的本地防护；客户端可被修改，不能替代云函数可信身份、所有者条件和实际资源权限。

## 35.28 未核对就不初始化云

App.onLaunch在wx.cloud.init之前：

```js
const target = environment.inspect();
if (!target.ok) {
  this.globalData.bootError = '环境核对未通过：' +
    target.problems.join('、') +
    '；请核对runtime/cloud配置与平台版本。';
  return;
}
```

默认预期值为空，云业务不会初始化成功。先按自己的隔离教学环境配置，而不是删除检查。

元数据能力不存在或抛错时保留PLATFORM_UNKNOWN，不默认按develop通过。原来的cloudReady依然只表示本地init完成，不能证明云部署、网络、规则和身份都有效。

## 35.29 维护练习页怎样操作

“身份与环境”页新增“日志与维护练习”按钮。页面读取公开运行阶段和本地快照，提供三种动作：

1. 生成20条固定样本：5条超时失败、15条成功。
2. 刷新快照：查看当前进程中的真实诊断是否启用。
3. 清空本次样本：清空两个内存队列。

固定练习创建独立记录器，即使真实诊断关闭也能学习。它不会故意抛未处理异常、发送请求或向云写测试数据。页面销毁清除练习队列。

清空按钮不删除任务、云文件、回执或平台日志，不能称为清除全部个人数据。

## 35.30 版本清单为什么拆成三部分

tools/build-manifest.cjs生成：

| component | 覆盖目录 | 用途 |
| --- | --- | --- |
| client | miniprogram | 客户端源码与配置 |
| cloud | cloudfunctions | 云函数源码和依赖声明 |
| controls | database、security | 规则、索引和权限计划文件 |

每部分有文件数、源码字节数和SHA-256，再组合为fingerprint。相同客户端、不同规则计划不能被误认为完全相同候选。

规则计划仍需实际应用，依赖声明也不等于依赖已安装；这里不包含微信编译结果、真实云部署、数据库内容或备份。

## 35.31 怎样稳定计算源码摘要

工具先遍历固定目录，统一相对路径分隔符，按确定的字符串顺序排序，再依次输入“路径、分隔符、字节长度、分隔符、实际字节”。

它跳过node_modules和报告目录，对密钥类文件或符号链接报受阻，不跟随任意链接读取其他位置。普通代码内嵌秘密仍需人工检查与发布扫描。

摘要能帮助发现输入变化，但不是签名、证书、审核结果或可信来源证明。有人同时修改文件和摘要，仍需要其他发布审查机制才能识别。

## 35.32 在电脑上生成源码清单

进入16-studyhub-operations项目目录：

```powershell
node tools/build-manifest.cjs
```

成功退出0，写operations/reports/artifacts.json，compiled和deployed均为false。没有真实AppID也能计算学习源码清单，因此退出0不代表云业务可用。

读取失败时退出2，并写不可用报告，不能继续拿旧清单作为当前证据。输出没有文件正文或密钥值。

## 35.33 三种摘要各自的范围

| 名称 | 来源 | 关联什么 |
| --- | --- | --- |
| sourceDigest | 第33章测试入口 | 约定代码、配置、页面、测试输入与标准50报告 |
| codeFingerprint | 第34章发布检查 | 客户端与云函数源码 |
| 三组件fingerprint | 本章源码清单 | 客户端、云函数及规则计划 |

范围、序列化方式不同，数值无需一致。不能把一种摘要复制进另一种字段。实际发布材料、云部署版本、备份与恢复记录还要分别管理。

修改源码后重测、更新相关清单；不要手工改JSON报告里的摘要来绕过过期检查。

## 35.34 备份、恢复、回退分别解决什么

备份保存某个范围在某个时刻的副本；恢复把选定副本按规则重新建立；回退将应用或配置调整到经过验证的旧候选。

客户端回退不会自动回退数据库，也不会撤回已发送消息。数据库恢复可能覆盖备份之后的新修改；存储文件与数据库文档又不共享事务。

在“学伴”里，任务、笔记、ops、迁移映射、资产引用、会话槽、本机草稿和outbox都有关联。只备份tasks不能称为全应用可恢复备份。

## 35.35 备份演练至少验证什么

先明确范围、时间点、访问人、保存期限、加密与密钥管理、恢复目标、允许丢失的变更范围和可接受恢复时长。这些应由实际需求确定，不在本章承诺固定指标。

在隔离环境中恢复后，不只数文档：验证归属、版本、笔记附件引用、精确文件可读、会话槽关系、回执与旧编号、防重复迁移，以及必要索引和规则。

备份含私人数据，同样要控制访问与期限。不要把真实备份放进课程ZIP或随意发送给排错人员。本章没有创建任何真实备份。

## 35.36 数据变化后为何不能盲目退旧代码

假设新版把某字段从字符串改成数组，旧版仍按字符串写回，可能损坏数据。又如新版允许删除回执，旧版仍接受老编号，幂等协议可能失效。

更稳妥的思考顺序是：先兼容读取新增字段，再逐步迁移，再观察旧客户端，最后才考虑移除旧字段。具体方案依赖业务，不能只靠改版本号。

本章云端源码保持上一版一致，但仍需核对真实部署是否同版；未来涉及schema、规则或清理协议变化时，必须重新做兼容与恢复演练。

## 35.37 回退计划文件

operations/recovery-plan.json保留：

- 当前与目标指纹、目标环境和阶段。
- 实际负责人。
- 云端兼容、数据兼容核对状态。
- 备份、恢复演练、停止相关写入与人工审查四组证据。

operations/rollback-target.json应登记真实旧候选清单，默认空白。不要把当前清单复制进去假装“可回退”，也不要用任意64位字符串冒充已验证制品。

这些字段只是登记；工具不会查材料真伪或确认真实写入已停止。

## 35.38 运行回退准备检查

```powershell
node tools/recovery-check.cjs
```

默认退出2，写operations/reports/recovery.json。工具重新计算当前源码，避免仅凭过期清单继续判断。

它检查清单格式与组合摘要、目标是否不同、环境与阶段、当前与目标指纹、负责人、兼容性和证据日期。日期按固定UTC+08:00，未来日期不算完成。

输入损坏时写新的INPUT_INVALID受阻报告。没有部署、删除、停写、还原数据或发送通知的执行代码。

## 35.39 材料齐全也只到人工审查

```json
{
  "decision": "manual-review-only",
  "canExecute": false,
  "remoteVerified": false,
  "dataRestored": false
}
```

上面是固定完整测试夹具能得到的状态。真实默认项目仍是blocked。manual-review-only意味着格式规则不再阻止进入人工核对，不代表已经具备真实回退权限或执行条件。

实际负责人应再次确认影响、在途操作、数据兼容、备份可恢复性、目标版本和处理窗口，再按真实平台流程操作。本课程不会自动替你回退正式服务。

## 35.41 一次固定故障演练

案例：“某个版本后，用户说保存任务超时。”

先确认影响范围、版本、环境和时间；提醒用户保留原编号与草稿状态。客户端超时仍可能已经提交，不直接另建编号。

检查对应云调用、回执与当前任务；若已提交，按原协议恢复界面；若结果未知，继续核对同一指令。再看是否误配环境、函数不可达、索引/资源异常或版本不兼容。

固定练习页只模拟“20次中5次超时”的样本，不模拟真实保存；真实故障演练应在隔离环境、有受控数据和负责人时执行。

## 35.42 持续维护清单

| 周期/触发 | 要做什么 | 保存证据 |
| --- | --- | --- |
| 每次发布 | 固定版本/目标、测试、清单、材料与回退准备 | 候选记录与实际部署版本 |
| 发布后 | 核心路径、错误、资源和用户反馈 | 观察范围、结果、负责人 |
| 定期 | 权限、索引、备份恢复、日志期限与费用核对 | 实际控制台/演练记录 |
| 依赖更新 | 查变更、隔离验证、回归与兼容 | 版本、锁文件、测试和风险 |
| 数据模型变化 | 迁移、旧客户端、幂等、删除和回退 | 协议与演练材料 |
| 指引/服务变化 | 重新盘点数据与适用要求 | 更新后的材料与真机结果 |
| 故障后 | 影响、时间线、根因、修复和防复发 | 复盘与具体改进负责人 |
