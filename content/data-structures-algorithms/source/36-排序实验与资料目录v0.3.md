# 36 排序实验与资料目录v0.3

## 36.1 目标与先修

先完成31—35章、第16章文件目录和第30章索引关系，建议6—9小时。目标是设计可比较的实验，分别验证有序、记录多重集和稳定性，解释测量边界，再交付可导入导出、按ID查找和按分钟稳定展示的目录v0.3。

本章两组工程独立运行：排序实验台回答“同一输入各算法做了多少事”；目录工程回答“排序怎样成为可用功能，同时保护已有数据关系”。不是把两个main一起编译。

## 36.2 同一数据、同一口径、各自重新开始

公平对照至少需要相同记录、相同键定义、相同统计口径。每种算法开始前都从original复制一份，不能让后一种拿到前一种已经排好的数组。

实验台固定32项，有五种数据：sorted键0—31；reverse键31—0；equal全部5；nearly从sorted交换前两条；mixed键由`(i*17)%23-11`确定，含负数和重复。tag跟随记录，数据生成与复制不计入算法统计。

这些是可复现的具体输入，不是“覆盖所有随机分布”的证明。仅用一份32项数据的耗时更不能推出渐近复杂度；复杂度仍来自前几章的分析。

## 36.3 三个正确性问题分别问

第一，有没有相邻降序？第二，每条输入记录是否恰好在输出出现同样次数？第三，对承诺稳定的算法，同键项是否保留原输入先后？

实验台用独立匹配已用标记逐项核对完整记录，最坏O(n²)；检查成本在排序返回后发生，不进入comparisons/writes。被检查的输入tag只是负载，不必数值递增。相等键顺序判断靠原输入中的位置，不靠tag大小。

自动验证还用独立参考排序：把key与原位置一起作比较依据，得到唯一参考顺序，再核对键序、完整身份和稳定承诺。没有假设标准库qsort本身稳定，也没拿它的名字推断内部算法。详细测试实现属于维护者工具，初学者先看本章的检查思想即可。

## 36.4 运行排序实验台

保留累计源码包的目录布局，在 **UCRT64 Bash、解压后的`source/示例代码`目录**，按 [实验台README](示例代码/stage6-lab/README.md) 编译，然后：

```bash
./sort-lab.exe all mixed
./sort-lab.exe insertion sorted
./sort-lab.exe insertion reverse
./sort-lab.exe quick equal
```

后三次预期分别是：

```text
insertion sorted n=32 comparisons=31 writes=31 verified=1
insertion reverse n=32 comparisons=496 writes=527 verified=1
quick equal n=32 comparisons=32 writes=0 verified=1
```

all mixed输出9行，每种算法一行。verified=1只表示该次实验的检查通过，不代表所有输入或全部平台都通过；未知算法/数据名称返回非零并报错，不静默换成默认算法。

## 36.5 把算法结论放在同一张表上

下表对应本课具体实现，n为项数；扩展预算讨论复杂度，不把128项上限用来把所有算法说成常数。

| 算法 | 时间说明 | 额外空间 | 稳定 |
| --- | --- | --- | --- |
| 选择 | 最好/最坏Θ(n²)，写入O(n) | Θ(1) | 否 |
| 冒泡 | 有提前停止，最好Θ(n)，最坏Θ(n²) | Θ(1) | 是 |
| 插入 | 最好Θ(n)，最坏Θ(n²)，受逆序对数影响 | Θ(1) | 是 |
| 希尔 | 折半步长，本版最坏O(n²)，依赖步长 | Θ(1) | 否 |
| 归并 | 本版各类顺序均Θ(n log n) | Θ(n)，另有递归栈 | 是 |
| 三路快排 | 平衡Θ(n log n)，全相等Θ(n)，最坏Θ(n²) | 小边递归栈O(log n) | 否 |
| 计数 | Θ(n+R)，R为值域大小 | Θ(n+R) | 是 |
| 桶 | O(n+B+Σnᵢ²)，本版桶内插入 | O(n+B) | 是 |
| LSD基数 | Θ(d(n+b))，当前4趟、每趟10桶 | Θ(n+b) | 是 |

空/单项可能走快速返回，表中增长结论主要讨论n增大。R/B/d/b不是同一个参数；固定10桶不意味着任意分布下桶排序线性。

## 36.6 计数、耗时与选择限制

本台报告键比较器调用和记录数组写入，不测墙钟时间。计数排序可能显示比较0，却要初始化1999个频数；归并把完整记录多写几遍，而实际大记录的复制成本还会增加。编译优化、内存布局、记录大小也影响耗时，不能按单列数字宣布“永远最快”。

若以后测时间，应把生成/复制/验证/打印移出测量区，使用足够规模、重复多次并报告环境与分布。当前128项教学预算不适合声称测出了大数据性能，不通过偷偷提高本版上限来改写已有实验协议。

## 36.7 目录排序为什么采用视图

第30章主数组位置与ID索引对应。直接把records按分钟重排却不修索引，会让查询指错记录。本版做**排序视图**：先建临时SItem数组，key取minutes，tag取原位置；稳定归并后，用tag取回完整IRecord到调用者输出数组。

例如主顺序17/30、1/45、9/30、3/20，视图应为3/20、17/30、9/30、1/45；主数组仍是17、1、9、3，ID9索引仍指主位置2。同分钟17在9前，来自主顺序，不是按ID17与9数值排序。

视图输出是记录副本，不是独立会自动更新的第二数据库。之后改分钟，应重新生成视图；旧副本不会跟着变，也不应该再用来覆盖主数组。

## 36.8 完整视图实现与失败保证

完整文件view.c：

```c
#include "view.h"
SortStatus catalog_view(const IndexedCatalog *catalog, IRecord *out, size_t capacity, SortStats *stats)
{
    if (stats == NULL || (catalog->count != 0 && out == NULL)) { return S_INVALID; }
    if (capacity < catalog->count) { return S_RANGE; }
    SItem order[H_MAX_ITEMS];
    for (size_t i = 0; i < catalog->count; i++) {
        order[i].key = catalog->records[i].minutes;
        order[i].tag = (int)i;
    }
    SortStats measured;
    SortStatus status = merge_sort(order, catalog->count, &measured);
    if (status != S_OK) { return status; }
    for (size_t i = 0; i < catalog->count; i++) { out[i] = catalog->records[order[i].tag]; }
    *stats = measured;
    return S_OK;
}
```

接口在 [view.h](示例代码/stage6-catalog/view.h)。catalog必须有效且已初始化；输出数组容量>=count，统计和数组为独立存储，均不与目录重叠。空目录允许out=NULL；stats仍不能为空。容量不足S_RANGE，NULL等错误S_INVALID，辅助申请失败S_MEMORY；这些失败保留输出数组、统计和主目录。

先在局部order排序，成功后才写出记录并更新统计；整个过程不改目录的records、count或index。目录最多48项，原位置转int有界；算法最多128项，足够容纳这份视图。分钟可达1440，因此这里选允许完整int键的归并，不能直接套第35章-999—999版本。

## 36.9 让文件与索引接起来

新工程复用v0.2的文件解析器和v0.3a的索引接口，通过 [io.c](示例代码/stage6-catalog/io.c) 做适配，不改旧文件。**适配层**是把一种模块的数据与返回值转换成另一种模块能使用的形式。

加载路径：文件→临时Catalog解析/验证→候选IRecord数组→indexed_replace建新索引并提交。任一步失败，清理临时Catalog，原索引目录保留；文件流位置已向前读取，不承诺回滚流。load不关闭调用者流，main在输出前检查fclose，关闭失败则报告错误并丢弃本次内存结果。

保存路径：索引目录→临时Catalog→原catalog_save。先成功准备全部记录，才开始写流；准备时的申请失败不会写文件。但真正写流/刷新失败仍可能留下部分输出，不提供原子替换或崩溃恢复。

项目版本v0.3沿用文件头DSA-CATALOG-1，二者编号不同：前者标应用功能，后者标文件格式。本适配层最多32条，保持旧协议；内存v0.3a的48项预算不修改。直接给save超过32条内存记录会CAT_LIMIT，并在写文件前拒绝。标题、分钟、LF/CRLF、UTF-8字节约定沿用第16章，不新造不兼容格式。

## 36.10 完整工程运行与可见结果

目录布局、完整编译命令在 [v0.3运行说明](示例代码/stage6-catalog/README.md)，全部新文件在 [源码附录](示例代码/stage6-common/完整源码.md)。这是跨模块工程，要保留源码包的相邻目录，不能把两份都叫catalog.h的旧头文件互相覆盖。

在 **UCRT64 Bash、解压后的`source/示例代码`目录**，编译后执行：

```bash
./catalog-v3.exe view stage6-catalog/sample.txt
./catalog-v3.exe find stage6-catalog/sample.txt 9
./catalog-v3.exe title stage6-catalog/sample.txt "C"
./catalog-v3.exe save stage6-catalog/sample.txt 1 30 > updated.txt
./catalog-v3.exe view updated.txt
./catalog-v3.exe remove updated.txt 17 > removed.txt
./catalog-v3.exe find removed.txt 9
```

第一条view输出：

```text
id=3 minutes=20 title=Arrays
id=17 minutes=30 title=C basics
id=9 minutes=30 title=Queues
id=1 minutes=45 title=Pointers in C
```

修改ID1为30分钟后，view中的三个同分钟项为17、1、9，仍按主数据顺序。删除17并重载后，查9仍得到`id=9 minutes=30 title=Queues`，说明主记录搬动后索引重建正确。title查询逐条KMP，大小写敏感，空模式匹配所有标题，不使用ID索引来假装加速子串。

view/find/title输出人读文本，save/remove输出可重载文件协议；不要把view输出当文件格式导入。重定向使用不同的新文件名，不能用输入同名目标，shell会先截断它。API仍支持新增，当前CLI提供上述五种模式，不声称实现了交互菜单。

## 36.11 常见错误

后一算法拿前一算法的已排序结果；将验证时间混进排序耗时；只检查数字和总长度；用tag大小代替原位置判断稳定；把计数0比较等同0工作；直接排序主记录却不更新索引；把人读视图导入为协议；把32条文件边界与48条内存边界混淆；正常运行就声称验证了内存/设备故障；保存成功前就提示成功。

## 36.12 练习与参考答案

练习一：为什么基数writes大于计数仍不能据此判定一定更慢？答案：两者未计的频数初始化范围不同，真实时间还受记录大小、实现与环境影响。

练习二：生成视图后把ID9分钟改为5，旧视图会自动变吗？答案：不会，输出是副本，重新生成才反映变化；主索引不依赖分钟，修改本身无需重建ID索引。

练习三：加载文件中最后一项重复ID，旧目录会被替换一半吗？答案：不应，临时解析及indexed_replace成功后才提交；配套测试覆盖失败保留。普通I/O错误仍须按流接口检查，不能从这个内存保证推断原子文件保存。
