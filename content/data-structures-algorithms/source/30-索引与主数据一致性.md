# 30 索引与主数据一致性

## 30.1 目标与先修

先完成第16章资料目录、第20章二分边界和本阶段匹配、散列。建议6—8小时。目标是按需求选择查找表示，区分键与位置，写出索引不变量，并让新增、删除、批量替换在失败时保留旧目录。

本章提供独立的**内存索引目录v0.3a**。它完成ID散列查询、标题字节子串查询、修改分钟和保持顺序的删除；未接入v0.2文件协议，也未实现按分钟稳定排序。后续 [第36章](36-排序实验与资料目录v0.3.md) 已提供整合v0.3，本章保留独立内存版便于分步学习。旧v0.2代码与运行方式保留，可分别重跑。

## 30.2 三种查找表示怎样选

| 需求与表示 | 查询 | 改动成本与限制 |
| --- | --- | --- |
| 无序顺序表 | 顺序扫描，最坏O(n) | 简单，保持加入顺序；中间删会移动 |
| 按ID有序数组 | 精确查询O(log n)，有序前提须维护 | 插入/删除最坏O(n)；范围遍历方便 |
| 主记录数组加ID散列表 | 分散良好时可讨论短探测；最坏仍可能长 | 需维护索引；按槽遍历不保证顺序；范围查询不自然 |

选结构先问：查什么、怎样比较、是否需要范围与有序输出、写入多不多、资源和失败怎样处理。只有两条记录，顺序查找通常更容易维护；不能只看到O(1)字样就为所有任务加索引。

散列ID索引不能直接回答“标题包含C”或“分钟在20到40间”：这些条件不是ID相等。本章标题查询仍扫描每条主记录，用KMP判断子串；排序与其他索引是不同工作。

## 30.3 主数据、索引、键与位置

**主数据**是资料真正内容：IRecord{id,minutes,title[64]}。**索引index**是帮助定位它的辅助映射：id→records数组下标。例子：

```text
records[0] = {17,30,"C basics"}     索引17 -> 0
records[1] = { 1,45,"Pointers in C"} 索引 1 -> 1
records[2] = { 9,20,"Queues"}       索引 9 -> 2
```

ID17始终标识这份资料，位置0只表示当前放在哪。删掉第一条后，ID1、9的位置分别变0、1。若只从散列表删17而不更新余下位置，查9可能读到旧下标2，出现逻辑错误甚至越界。

本版不保存指向数组元素的指针，避免将来动态扩容后地址失效；但保存下标也不是自动安全，搬动记录后仍须修复。公开find将完整记录复制给调用者，不提供跨更新仍有效的借用指针。

## 30.4 要保持的双向关系

每次公开操作完成后都满足：count<=48，ID唯一；index.count==count；对每个i<count，index[records[i].id]==i；反过来每个LIVE索引项的位置都小于count，并指向相同ID。两个方向都检查，才能排除多余索引和丢失索引。

记录ID0—9999，分钟0—1440，标题1—63字节并在64格内有零终止；拒绝ASCII控制字节1—31和127。高位字节允许，但不验证完整UTF-8。valid_record最多读64格，找不到零就拒绝，不对可能无终止的标题直接strlen。

所有对象参数为已初始化的有效对象，输出为独立IRecord变量；不手改公开字段，不复制拥有索引堆数组的整个目录后分别释放。replace的输入是有效IRecord数组，不与目录存储重叠；count=0可传NULL。超48的replace返回H_INVALID，add到48项返回H_FULL，二者是不同接口的约定。

## 30.5 事务式替换：先准备，后提交

这里的**事务式**只指本函数的失败保证：失败后调用者仍看到原主数据和索引。不是数据库事务，也没有文件持久化、并发隔离或崩溃恢复。

1. 在局部candidate数组准备记录，next散列表从空表开始。
2. 逐条验证并复制；以ID和当前位置加入next。遇重复、坏记录或分配失败，清理next，返回；旧目录没有改动。
3. 所有步骤成功后，复制候选记录到主数组，释放旧索引，将next的所有权移交目录，最后更新count。

提交区只有普通赋值和free，没有需要再分配的步骤。因此正常单线程调用返回时，两套数据一致；不能据此允许其他线程在提交中途读取。

```text
准备前：旧记录 + 旧索引 仍有效
准备中：旧记录 + 旧索引 | 候选记录 + 新索引
失败：清新索引，返回旧状态
成功：候选记录和新索引成为正式状态，旧索引释放
```

结构体赋值会复制指针，这里是实现内部一次**所有权转移**：next是局部临时对象，交出资源后不再clear它。一般业务代码随意复制目录仍会造成两个拥有者，不能照抄这一个赋值就认为任意复制安全。

## 30.6 新增、删除与修改分别怎样做

add先验证记录、查重复、查预算，复制旧记录并在末尾追加，然后调用replace。remove先按ID取得位置，按原顺序复制除此项以外的记录，再replace；这样顺序保持，所有下标重新生成。删除最后一项得到空目录，不需要申请索引数组。

set_minutes只改变不参与索引的分钟字段，不改变ID或位置，因此无需重建；先检查分钟，再查ID，失败不改。当前没有单条改ID接口；需要改键时用完整候选数组replace，重新检查唯一性，不能直接改records[i].id。

这是一种偏重可解释性与失败保留的设计。新增、删除每次重建，不能声称写入都是O(1)。更高效的局部修复需要另外设计完整的回滚或预留策略，本版先让关系清楚、可测试。

## 30.7 完整C文件

建立自己的`~/dsa-labs/ch30`。下载本目录 [catalog.h](示例代码/stage5-indexed-catalog/catalog.h)、[catalog.c](示例代码/stage5-indexed-catalog/catalog.c)、[main.c](示例代码/stage5-indexed-catalog/main.c)，以及 [hash_status.h](示例代码/stage5-common/hash_status.h)、[open_map.h](示例代码/29-open-addressing/open_map.h)、[open_map.c](示例代码/29-open-addressing/open_map.c)、[matching.h](示例代码/27-matching/matching.h)、[matching.c](示例代码/27-matching/matching.c)。八个文件放同一目录，**只用本工程的main.c**。

完整文件catalog.h：

```c
#ifndef DSA_INDEXED_CATALOG_H
#define DSA_INDEXED_CATALOG_H
#include "open_map.h"
#define TITLE_BYTES 64
typedef struct { int id; int minutes; char title[TITLE_BYTES]; } IRecord;
typedef struct { IRecord records[H_MAX_ITEMS]; size_t count; OpenMap index; } IndexedCatalog;
void indexed_init(IndexedCatalog *catalog);
void indexed_clear(IndexedCatalog *catalog);
HStatus indexed_replace(IndexedCatalog *catalog, const IRecord *records, size_t count);
HStatus indexed_add(IndexedCatalog *catalog, const IRecord *record);
HStatus indexed_remove(IndexedCatalog *catalog, int id);
HStatus indexed_find(const IndexedCatalog *catalog, int id, IRecord *out);
HStatus indexed_set_minutes(IndexedCatalog *catalog, int id, int minutes);
#endif
```

完整文件catalog.c：

```c
#include "catalog.h"
#include <string.h>

static int valid_record(const IRecord *record)
{
    if (record->id < 0 || record->id > H_KEY_MAX || record->minutes < 0 || record->minutes > 1440) {
        return 0;
    }
    for (size_t i = 0; i < TITLE_BYTES; i++) {
        unsigned char byte = (unsigned char)record->title[i];
        if (byte == 0) {
            return i != 0;
        }
        if (byte < 32 || byte == 127) {
            return 0;
        }
    }
    return 0;
}
void indexed_init(IndexedCatalog *catalog)
{
    catalog->count = 0;
    open_init(&catalog->index);
}
void indexed_clear(IndexedCatalog *catalog)
{
    open_clear(&catalog->index);
    catalog->count = 0;
}
HStatus indexed_replace(IndexedCatalog *catalog, const IRecord *records, size_t count)
{
    if ((count != 0 && records == NULL) || count > H_MAX_ITEMS) {
        return H_INVALID;
    }
    IRecord candidate[H_MAX_ITEMS];
    OpenMap next;
    open_init(&next);
    for (size_t i = 0; i < count; i++) {
        if (!valid_record(&records[i])) {
            open_clear(&next);
            return H_INVALID;
        }
        candidate[i] = records[i];
        HStatus status = open_put(&next, candidate[i].id, (int)i);
        if (status != H_OK) {
            open_clear(&next);
            return status;
        }
    }
    for (size_t i = 0; i < count; i++) {
        catalog->records[i] = candidate[i];
    }
    open_clear(&catalog->index);
    catalog->index = next;
    catalog->count = count;
    return H_OK;
}
HStatus indexed_add(IndexedCatalog *catalog, const IRecord *record)
{
    if (record == NULL || !valid_record(record)) {
        return H_INVALID;
    }
    int position;
    if (open_get(&catalog->index, record->id, &position) == H_OK) {
        return H_DUPLICATE;
    }
    if (catalog->count == H_MAX_ITEMS) {
        return H_FULL;
    }
    IRecord candidate[H_MAX_ITEMS];
    for (size_t i = 0; i < catalog->count; i++) {
        candidate[i] = catalog->records[i];
    }
    candidate[catalog->count] = *record;
    return indexed_replace(catalog, candidate, catalog->count + 1);
}
HStatus indexed_remove(IndexedCatalog *catalog, int id)
{
    int position;
    HStatus status = open_get(&catalog->index, id, &position);
    if (status != H_OK) {
        return status;
    }
    IRecord candidate[H_MAX_ITEMS];
    size_t n = 0;
    for (size_t i = 0; i < catalog->count; i++) {
        if (i != (size_t)position) {
            candidate[n++] = catalog->records[i];
        }
    }
    return indexed_replace(catalog, candidate, n);
}
HStatus indexed_find(const IndexedCatalog *catalog, int id, IRecord *out)
{
    if (out == NULL) {
        return H_INVALID;
    }
    int position;
    HStatus status = open_get(&catalog->index, id, &position);
    if (status != H_OK) {
        return status;
    }
    *out = catalog->records[position];
    return H_OK;
}
HStatus indexed_set_minutes(IndexedCatalog *catalog, int id, int minutes)
{
    if (minutes < 0 || minutes > 1440) {
        return H_INVALID;
    }
    int position;
    HStatus status = open_get(&catalog->index, id, &position);
    if (status != H_OK) {
        return status;
    }
    catalog->records[position].minutes = minutes;
    return H_OK;
}
```

`(int)i`安全是因为i最多47，int可表示该范围；不能在没有容量证明时随意把size_t转成int。candidate数组有空间，但count之外的格子不属于有效记录，不读取或输出它们。

## 30.8 运行并核对两条查询路径

在 **UCRT64 Bash、`~/dsa-labs/ch30`目录**：

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic main.c catalog.c open_map.c matching.c -o catalog.exe
./catalog.exe
./catalog.exe "Queues"
./catalog.exe ""
```

默认完整程序输出：

```text
id=9 minutes=25 title=Queues
title_match=1 byte=12
count=2 index_count=2
```

先导入17、1、9三条，删17，再把9分钟从20改25。ID查询依靠新索引9→1，正确输出Queues。默认标题模式C只匹配`Pointers in C`，其C在字节12。查`Queues`时输出title_match=9 byte=0；空模式匹配剩下两条标题，顺序是ID1再ID9，因为遍历的是主数组。

main只用固定样本与可选命令行标题模式，不读取文件、不提供菜单。完整入口、跨目录编译与独立练习路径说明见 [工程README](示例代码/stage5-indexed-catalog/README.md) 和 [完整源码](示例代码/stage5-common/完整源码.md)。

## 30.9 成本与选择理由

ID查找成本是散列表探测加一条记录复制；标题上限固定63字节。若推广到可变长记录，复制成本应计入记录长度。标题扫描r条、每次调用当前KMP，成本O(标题字节总数+r*m)，不是ID索引的O(1)期望讨论。

结构修改先复制O(n)记录，再反复放入散列表。分散良好时重建可接近线性；刻意碰撞时总探测最坏O(n²)，还要计新槽初始化。每次提交保留旧索引直到成功，因此同时占旧、新两张表及局部记录副本。这里预算48项，选择额外空间和较慢写入来换取清楚的失败保证。

有序数组的二分也要求维护排序不变量；不能只排序一次后随便追加。将来按分钟排序时，本课优先输出视图或副本，避免突然打乱ID索引。若真的重排主数组，必须同步重建索引并验证关系。

## 30.10 常见错误

把ID当下标；删主记录只删一个索引项；给索引存会因扩容失效的内部地址；先改主记录再申请索引，失败后无法回滚；新索引成功却又清理它造成悬空；只检查两个count相等，不检查对应关系；把标题扫描说成走ID索引；把当前内存实验写成已经支持文件保存与稳定排序。

## 30.11 练习与参考答案

练习一：删第一个记录，剩下的旧位置1、2应变多少？答案：0、1；ID不变，索引值变。

练习二：只把9的分钟改25，需要重建吗？答案：当前索引只依赖ID和位置，无需；若另有按分钟组织的索引，就需要额外维护。

练习三：准备新索引的第三次分配失败，旧目录可用吗？答案：应可用，清理临时索引即可；这正是先准备后提交的目的。需要实际故障注入证明，不是只看正常演示。
