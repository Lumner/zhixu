# 22 动态数组、扩容与摊还

## 22.1 目标与先修

先掌握第21章接口、第13章realloc与所有权、第18章摊还。建议4—6小时。本章把内嵌数组换成动态分配的连续区，保留同样的按位置操作，并实际对照逐一扩容与倍增。

本教学实现最大64条，这是可改的实验预算，不表示动态数组或链表天然只能存64条。预算让容量错误与分配失败都可复现。

## 22.2 状态多了一个容量与拥有的指针

Vector包含data、count、capacity。不变量是`0 <= count <= capacity <= 64`；capacity为0时data为NULL，否则指向至少capacity个int的分配。只有前count个是有效元素。

init只给尚未持有资源的对象建立空状态；clear释放已有分配并恢复空状态，可以重复调用。对非空Vector再直接init会丢失地址并泄漏，所以“初始化”与“清空”不是可随意互换的名字。

Vector不能按值复制后当成两个独立拥有者；那样只有地址被复制。若要真正复制序列，需要另一段分配和明确的失败处理，本章不把浅拷贝当作完整克隆功能。

## 22.3 reserve只准备格子，不添加数据

vec_reserve(list,k)保证成功后容量至少k，必要时精确扩到k；请求不大于已有容量则不操作。它不会把count改为k，也不初始化新增业务元素。

请求超过64返回DS_FULL，计算字节前再检查乘法范围；使用临时grown接收realloc，失败时原data/count/capacity保持。成功后才保存新地址和容量。

成功扩容使旧分配上的借用地址不能继续依赖。即使地址数值看起来没变，也改用新data重新按下标取元素。中间插入删除还会搬动值，位置对应的业务元素可能变化，稳定身份仍应使用ID。

## 22.4 插入与删除怎样复用旧思路

插入先检查p≤count及数量上限。只有count==capacity才选下一容量：空时4，之后8、16、32、64。reserve成功后，按第21章从右向左搬动，再写值、增加count。

扩容可能失败，但元素搬动与整数赋值在本规格中没有业务失败分支。因此所有可能失败的检查放在修改序列之前，才能承诺失败保留旧内容。

删除仍左移元素、count减1，**本版不自动缩容**。删光后count=0、capacity可能仍64，这是合法空序列。clear才释放存储。若每删一条就缩容，反复插删可能频繁分配；四分之一阈值等收缩策略留作延伸，不在本例声称已经实现。

#define DSA_VECTOR_H

typedef struct { int *data; size_t count; size_t capacity; } Vector;
void vec_init(Vector *list);

完整文件vector.c：

```c
#include "vector.h"
#include <stdint.h>
#include <stdlib.h>

void vec_init(Vector *list)
{
    list->data = NULL;
    list->count = list->capacity = 0;
}

void vec_clear(Vector *list) {
    free(list->data);
    vec_init(list);
}

DsStatus vec_reserve(Vector *list, size_t capacity)
{
    if (capacity > DS_MAX_ITEMS) {
        return DS_FULL;
    }
    if (capacity <= list->capacity) {
        return DS_OK;
    }
    if (capacity > SIZE_MAX / sizeof *list->data) {
        return DS_MEMORY;
    }
    int *grown = realloc(list->data, capacity * sizeof *list->data);
    if (grown == NULL) {
        return DS_MEMORY;
    }
    list->data = grown;
    list->capacity = capacity;
    return DS_OK;
}

DsStatus vec_get(const Vector *list, size_t position, int *out)
{
    if (out == NULL) {
        return DS_INVALID;
    }
    if (position >= list->count) {
        return DS_RANGE;
    }
    *out = list->data[position];
    return DS_OK;
}

DsStatus vec_set(Vector *list, size_t position, int value)
{
    if (position >= list->count) {
        return DS_RANGE;
    }
    list->data[position] = value;
    return DS_OK;
}

DsStatus vec_insert(Vector *list, size_t position, int value)
{
    if (position > list->count) {
        return DS_RANGE;
    }
    if (list->count == DS_MAX_ITEMS) {
        return DS_FULL;
    }
    if (list->count == list->capacity) {
        size_t next = list->capacity == 0 ? 4 : list->capacity * 2;
        if (next > DS_MAX_ITEMS) {
            next = DS_MAX_ITEMS;
        }
        DsStatus status = vec_reserve(list, next);
        if (status != DS_OK) {
            return status;
        }
    }
    for (size_t i = list->count; i > position; i--) {
        list->data[i] = list->data[i - 1];
    }
    list->data[position] = value;
    list->count++;
    return DS_OK;
}

DsStatus vec_erase(Vector *list, size_t position, int *out)
{
    if (out == NULL) {
        return DS_INVALID;
    }
    if (position >= list->count) {
        return DS_RANGE;
    }
    int saved = list->data[position];
    for (size_t i = position; i + 1 < list->count; i++) {
        list->data[i] = list->data[i + 1];
    }
    list->count--;
    *out = saved;
    return DS_OK;
}
```

main的完整代码在下载文件和 [源码附录](示例代码/stage4-common/完整源码.md)。它创建两个独立Vector，循环追加0—16：一份依赖自动倍增，另一份每次先reserve恰好所需格数。任一失败都走清理，不能因为演示出错就漏掉另一份分配。

## 22.6 实际对照与计数口径

在 **UCRT64 Bash、`~/dsa-labs/ch22`目录**：

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic main.c vector.c -o vector.exe
./vector.exe
```

预期：

```text
doubling count=17 capacity=32 copy_model=28
exact count=17 capacity=17 copy_model=136
```

copy_model是“每次扩大都搬动全部旧元素”的**概念复制计数**。它不是测出了realloc真实搬了多少字节；分配器可能原地扩大，优化与平台行为也不同。程序根据每次容量请求前的有效数量累计模型成本。

倍增在加入第1、5、9、17条时扩容，旧元素复制模型为0+4+8+16=28。逐一准备1、2、...、17格，每次旧元素数为0、1、...、16，总136。两者都还各有17次新元素写入。

## 22.7 摊还结论究竟覆盖什么

在不限64的同类倍增模型中，m次末尾追加的旧元素搬动是几何和，总计O(m)，加上m次新写入，追加的元素处理摊还Θ(1)。这是对整串操作的确定性分摊，不是假设随机输入。

前提是**末尾追加且使用自动倍增策略**。本接口没有第16章那种每次线性查重，因此不用把查重成本算进来；如果调用者自己添加查重，又要另行计算。

在中间插入仍需要移动后缀，最坏Θ(n)，不会因为容量倍增就变成常数。get/set是Θ(1)，erase最坏Θ(n)。reserve的成本模型按被移动元素计算，不给真实分配器内部时间作跨平台保证。

容量存储按capacity计算，不能总说当前内存一定小于2*count：显式reserve可以多准备很多，删除又不缩容。只有限定“只进行从空开始的自动追加”时，才可推导容量与数量的倍数关系，还要考虑初始最少4格。

## 22.8 失败路径手工推演

已有4个元素，count=capacity=4；在位置2插新值，下一容量8。若realloc返回NULL，应仍是原地址、原4个值、count=4、capacity=4。不能先右移再申请，也不能先count++。

实际内存不足不容易稳定重现，本课程测试替身会让指定一次申请失败，检查这些字段和数据。不会耗尽真实系统内存来猜测。保存旧地址作比较只适用于失败后旧分配仍有效的路径；成功后不拿旧指针继续访问或比较。

## 22.9 常见错误

- reserve后把数量一起改大，读取没有初始化的备用格子。
- 直接覆盖唯一地址，realloc失败后丢失原资源。
- 中间插入也称摊还常数，漏掉元素搬动。
- 把copy_model当实际内存复制测量。
- 删除后还拿count推断实际分配大小。
- init覆盖已有拥有者，或浅拷贝后两份各自free。

## 22.10 练习与参考答案

练习一：从空自动追加到第9条，容量和旧元素复制模型是多少？

答案：容量16，复制0+4+8=12次；加9次新写入共21次。

练习二：capacity=32、count=17，reserve(20)会怎样？

答案：已经足够，无需分配，数量仍17，容量仍32。

练习三：删除到空后，data一定NULL吗？

答案：本实现不缩容，所以不一定。空由count=0表示；调用clear后才恢复NULL、0、0。
