## 一、匹配

| 模式 | pi |
| --- | --- |
| aaaa | 0,1,2,3 |
| ababa | 0,0,1,2,3 |
| aabaaab | 0,1,0,1,2,2,3 |

`aabaaab`下标5的当前段是`aabaaa`，最长边界为`aa`，长度2。不是顺着前一格2必然写3：当前a与候选pattern[2]=b失配，退到pi[1]=1，再比较pattern[1]=a，才得到2。

KMP主例的j在每个正文字符处理后为1,2,3,4,5,4,5,4,5,6。下标5与7处失配，从5退3，再用当前b延长到4；整个模式完成的起点4。可保留的`aba`既是已匹配段后缀，也是模式前缀。

| 正文 / 模式 | found | index |
| --- | --- | --- |
| 空 / 空 | 1 | 0 |
| 空 / a | 0 | 0 |
| a / 空 | 1 | 0 |
| abc / abcd | 0 | 3 |
| aaaaa / aaa | 1 | 0 |
| abc / z | 0 | 3 |

内部零字节实验应找到index=3。strlen在第一个零处停止，不能代表5字节缓冲区或2字节模式的实际长度；显式长度协议与C字符串协议不能混用。

## 二、拉链

插入完成：bucket2→18→10→2，count=3。查10得100。删10让18.next指2，释放10，count=2；删18改桶头为2，释放18，count=1；删2将桶头设NULL，count=0。再删或查2都是H_MISSING，get失败保留out=777。

0—376每隔8的48个键都在桶0，α=48/8=6，最长链48；不存在的同桶键查找会走完整链，最坏O(n)。其他桶为空，不因为平均链长6就让最长链也等于6。满表put原键H_DUPLICATE，put新键H_FULL，原值不变。

## 三、墓碑

加入7、15、23分别占7、0、1。删15：槽0为DELETED，count=2、used=3。查23从7过0到1成功；再次put23先查到已有键，拒绝，不能在槽0再放一个23。put31查无后复用槽0，此时count=3、used仍3。

第二个实验：加0—5后6/6/8，删0—4后1/6/8，再加6前触发同容量清理，清后1/1/8，加完2/2/8。若清理申请失败仍是1/6/8，键5仍可查到原值，键6尚不存在，旧slots地址保持。

本版超过48有效项才报H_FULL，合法操作不会把64格全占满；测试应尊重这个资源协议。探测仍设置capacity次上界，不能以“本版总有空格”为理由写无限循环。

## 四、索引与目录

原17→0、1→1、9→2；删17后1→0、9→1。ID不随搬动改变，但下标改变。只删除17索引会让另外两个索引留在旧位置，因此必须重新建立对应关系。

重复候选ID报H_DUPLICATE；晚出现的非法分钟报H_INVALID；候选准备已经申请的资源都要清理，旧目录仍有效。63字节标题加末尾零有效；64格没有零无效。高位字节允许不等于已经验证Unicode正确性。

48条候选记录从空表构建，容量依次8、16、32、64，发生4次申请。任意一次失败都应H_MEMORY，旧主记录、顺序、count、旧索引地址和内容保持；临时申请无残留。配套测试分别注入这4个位置，并对删除重建与新增重建做同类验证。测试不是通过真的耗尽电脑内存实现的。

分钟只改非索引字段，不必重建；改ID或主数组顺序必须同步维护索引。当前公开接口没有单条改ID，可以构建完整候选记录列表后replace；不能直接写公开字段绕开接口。

## 五、选择理由示例

小表经常整体替换，顺序扫描结构简单，可能已经足够；大表读多、键较短、分布合适时，散列索引可能降低精确查询工作量，但仍需容量、冲突和失败策略。需要范围查询或按键输出时，有序数组等表示也值得考虑，其有序前提与写入搬动成本必须计入。

ID索引只能回答ID相等。标题子串需扫描标题或另设计索引；分钟范围需要按分钟组织的视图/结构或扫描；加入顺序应保存在主序列中，不能指望散列表槽顺序保持。测试覆盖正常结果、空、重复、缺失、边界和申请失败；不要用运行时间很短替代正确性验收。
